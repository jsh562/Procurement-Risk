# Procurement Risk Copilot Project Instructions

## Core Principles

### I. Traceable or It Does Not Ship

Every extracted value MUST carry a page citation and a per-field confidence, and every published figure MUST resolve to the artifact it was computed from — an unattributable number is a defect, not a rough edge. Provenance MUST be derived deterministically from parsing and enforced at the storage boundary, never asserted by a language model. — The product's entire claim is that a coordinator can check the system's reasoning; a number nobody can trace back is worth less than no number at all, because it invites trust it has not earned.

### II. Uncertainty Is the Product

The system MUST communicate distributions and intervals, never a bare point estimate. Collapsing a forecast to a single date anywhere in the interface is a regression. Every reported metric MUST be published together with **either its interval or an explicit declaration that it has none**, and which of the two applies is decided by what the metric measures, not by convenience: a proportion **estimated from a sample** MUST carry an interval, while a **census** — a figure computed over the whole of its own population, where every element is observed and nothing is sampled — MUST carry its exact denominator together with a declaration of why no interval applies. That declaration MUST name a reason drawn from a closed set, and the artifact publishing the figure MUST declare the set it draws from — an open-ended reason field is satisfied by any string and enforces nothing. — Replacing the submittal log's single optimistic integer with an honest distribution is the reason this product exists; a lone number reintroduces exactly the false confidence it was built to remove. The census clause is not a relaxation of that, and reading it as one inverts it: attaching an interval to a census asserts a sampling frame the figure does not have and a population it does not generalize to, while publishing a census with no declaration at all leaves it indistinguishable from an estimate whose interval was quietly dropped. Both are the false confidence this principle exists to remove. The **declaration** is the load-bearing part — it is what keeps a reader able to tell the two apart, which is why it is required rather than merely permitted.

### III. Precision Over Recall Where a Mistake Is Silent

Where an incorrect result would be invisible — cross-document identity merges above all — the system MUST bias toward refusal. Uncertain pairs MUST be withheld and routed to review rather than merged, and a value failing validation MUST be recorded as absent rather than stored wrong. — A wrong merge corrupts the record silently and propagates; a missing link is visible and recoverable. Optimize for the failure a human can see.

### IV. Agent Output Style

All agent output MUST be concise and outcome-oriented. This principle supersedes any verbose defaults.

- **Progress reports**: Facts and outcomes only — no narration, no restating the task.
- **Artifacts**: Emit required sections only — no preamble paragraphs, no summary epilogues.
- **Reasoning**: Omit unless the user asks "why" or the decision is non-obvious.
- **Errors / blockers**: State the problem, the attempted fix, and the result — nothing else.
- **Phase-boundary reports**: ≤ 5 bullet points.
- **Preserve without compressing**: Artifact template structure and required sections; explicit decision / registration / validation guidance in shared skills; delegation constraints and sub-agent role definitions; existing size limits (spec ≤ 1000 KB, research ≤ 400 KB, stories ≤ 200 words).

### V. The Model Extracts, Code Computes

Language models MUST only identify and structure information. All date arithmetic, ranking, and probability computation MUST happen in deterministic, testable code, enforced by an architecture test that fails the build when computation appears in a model-facing module. Exactly one module may reach the model provider, enforced by an import contract. — Model output is not reproducible and cannot be unit-tested; anything that must be defensible has to be computed somewhere that can be.

### VI. Evaluate Before You Tune

Evaluation sets MUST be frozen, hashed, and committed before any tuning run touches them, and the evaluation harness MUST verify the hash and abort on mismatch. — Small evaluation sets invite tuning to the test set. Making the freeze an exit code rather than a promise is the only version of this rule that survives schedule pressure.

### VII. Publish the Miss

A target that is not met MUST be published with its cause. Targets MUST NOT be retroactively adjusted to match results, and a limitation MUST be recorded as scope decision, supporting evidence, reversal trigger, and production-scale alternative. — A project that only ever reports its wins tells a reader nothing about whether the measurements were honest. Disclosed shortfalls are what make the successes credible.

### VIII. Honest Opponents

Every model claim MUST be reported against a baseline strong enough that beating it means something, and where a weak baseline is also reported it MUST be labeled as such. — Beating a deliberately poor comparison is a rhetorical move, not a result. A baseline that could plausibly win is the only one whose defeat carries information.

## Source Code Layout

- **Policy**: ENFORCE_SRC_ROOT
- **Convention**: All project source code MUST live under `/src`, organized into four entries: three source boundaries — `/src/web` (interface), `/src/api` (request serving), `/src/model` (offline modeling package) — plus `/src/gateway`, a shared package holding the model-provider client with its validation and tracing wrapper. Each entry keeps an independent dependency manifest; this is what makes serving/modeling isolation mechanically assertable rather than conventional. Neither Python boundary may declare the other as a dependency, and both depend on the gateway package, so exactly one module in the repository imports the provider client. The gateway package carries no web framework. It carries no modeling stack either, with one narrow exception admitted by {SAD:ADR-0023}: a shared local-inference runtime and its tokenizer, together with NumPy, which that runtime pulls transitively. **PyMC, ArviZ and pandas remain forbidden in the gateway** — the exception is a named narrowing, not a general relaxation, and the clause still binds every distribution that makes the modeling boundary heavy. As an *explicitly listed* term the exception is NumPy alone: the runtime and its tokenizer leave the derived denylist of their own accord once the gateway declares them instead of `/src/model`, and naming them as exclusions would trip the companion assertion that every excluded name is still declared by the modeling boundary. NumPy is different only because `/src/model` goes on declaring it for modeling work while it also reaches the serving image transitively, so it is the one name that has to be admitted rather than relocated. Tests live alongside the code they cover within each entry. The one exception is cross-entry verification that has no single owning entry — comparing one entry's dependency set against another's, or asserting on a built image — which lives under `/tests` at the repository root, because assigning it to any one entry would be arbitrary and a fifth entry under `/src` would contradict the four-entry rule above. Entry-local tests MUST NOT be moved there to claim the exception. Specification artifacts live under `specs/`; data, corpus manifests, and datasheets under `data/`.

## Development Workflow

- **Branching**: Feature branches cut from `main`, squash merged. Branch names MUST match `#####-feature-name` so the Feature Workspace resolves from the branch.
- **Commit Convention**: Conventional Commits.
- **CI Requirements**: Lint clean, no type errors, all tests passing, and coverage at or above target before merge. Architecture contracts must pass — a violation of the source layout, the single-provider-import rule, or the computation boundary fails the build rather than raising a review comment. The evaluation reproduction job must confirm published metrics within the stated tolerance before a release tag.
- **Temporary Files**: Every command run against this repository MUST direct temporary files into the checkout's own gitignored `.tmp/` — `TMPDIR`, `TEMP` and `TMP` set to `$PWD/.tmp`, and `--basetemp` pinned there in the root and in each entry's pytest configuration. **A library that keeps its own *scratch* MUST be pinned by name, because `TMPDIR` does not reach it**: `NUMBA_CACHE_DIR` is `$PWD/.tmp/numba`, set wherever the other three are. **A compiled-artifact cache is exempt and MUST NOT be redirected** — PyTensor's `base_compiledir` holds a C++ extension built against the interpreter, is keyed by platform and Python version, is bounded, and is shared correctly between checkouts. Redirecting it forces every checkout to rebuild the same binary, and on a machine where that build fails the redirect converts a working test tier into a broken one. Where a path is redirected on Windows it MUST use forward slashes: PyTensor strips backslashes from a value and creates the flattened result relative to the working directory rather than failing. No virtual environment, model download, or package build may be created outside the checkout; a one-off environment the project does not depend on belongs under `.tmp/`. — Several checkouts of this repository share one disk, and the system temp directory is shared with everything else on the machine. A one-off task once installed roughly a gigabyte of unsigned native libraries there and the host's antivirus blocked it as a dropper; the small unsigned executables a compiler emits when probing CPU features are flagged the same way. The heuristic is not wrong — a process compiling and running unsigned binaries in a user-profile temp path is indistinguishable from an attack by behaviour alone. Keeping the scratch inside the checkout removes the ambiguity and keeps work that belongs to this project visible inside it. **The rule binds the writers inside the process; it does not bind the tool harness running the command.** A command that is backgrounded, or that reaches its execution timeout and is backgrounded automatically, has its output captured by the harness to a path of the harness's choosing — outside the checkout — and redirecting output *within* the command does not prevent that, because the capture wraps the command rather than running inside it. Commands MUST therefore be sized to finish inside their timeout, splitting a long test run into per-tier invocations rather than running the whole suite in one call, and background execution MUST NOT be used for work whose output matters. Where a full-suite run is genuinely needed, it belongs in continuous integration, which runs on a disposable machine where no such path is shared.

## Data Provenance

- All data MUST be public domain or synthetic. No proprietary, confidential, or customer content enters the repository at any point.
- Every corpus document MUST carry a manifest entry recording its layer — REAL or SYNTHETIC — its license basis, and provenance appropriate to that layer. A retrieved document records source, issuing body, and retrieval date. A generated document records generator identity, seed, generation date, and the content hash of every fixture it was generated from. Neither half is optional, and a generated document MUST NOT carry retrieval provenance it does not have: a fabricated issuing body is indistinguishable downstream from a verified one, which is the failure Principle I exists to prevent.
- Copyrighted reference standards MUST be cited, never included. Licenses MUST NOT be mixed within a corpus location.
- Every synthetic dataset MUST ship a datasheet disclosing its generative assumptions.

## Governance

- Project instructions supersede all other documentation and practices.
- Amendments require a version bump with ISO-dated changelog entry.
- All implementations MUST pass the Instructions Check gate during planning.
- Complexity beyond these principles MUST be justified and documented.
- The registered Product Document, Technical Context Document, and Project Plan are the canonical sources for scope, architecture, and sequencing. Where a downstream artifact conflicts with one of them, the registered document wins and the downstream artifact is corrected.
- Project-level architectural decisions live as standalone records under `specs/adrs/`. Decision records are append-only: any change to a chosen option, its drivers, or its consequences MUST supersede rather than edit. Numbers are monotonic and never reused.
- Constraints recorded as architectural — offline-only forecast fitting, the request-time compute envelope, single-path model invocation, and the deterministic computation boundary — MUST NOT be relaxed by a feature-level decision. Relaxing one requires a superseding decision record.
- Amendments to the documents named in this section are serialized. At most one amendment is in flight at a time, it is performed on the default branch, and it lands before the next begins. A feature branch records the need for an amendment and does not perform it. — These documents are single files on fixed paths, the amendment procedure re-derives whole managed sections rather than patching lines, and the version counter admits no concurrent writer. Serializing is the only discipline that survives more than one epic running at a time.
- Decision record numbers, migration numbers, and Feature Workspace numbers are all claimed at epic start. — Numbers are allocated by scanning for the highest already in use, so two epics branching from one baseline will otherwise allocate the same number and both be right. Workspace numbers were omitted when this clause was written and collided exactly as predicted: prefix `00002` was taken by both `specs/00002-public-corpus-and-manifest` (E002) and E003's workspace, because E003 allocated the next free *sequential* number while every other epic matched its workspace number to its epic number. That collision was resolved by renaming E003's workspace to `specs/00003-core-data-schema`, which was only clean because the epic had already completed: no work was in flight, the reference set was finite, and a green suite proved the result. **Renaming mid-flight is what cannot be done cheaply** — a workspace number is embedded in every path its plan, tasks, and reports cite, including test modules that read those artifacts — so the claim still has to precede the directory. The convention the collision revealed is now explicit: **a workspace number matches its epic number.**

  **A claim MUST be made where the allocator looks.** Until now it was not, and that is the whole of why the clause failed. Allocation is verified by scanning `specs/adrs/` and this document *on the default branch*, while a claim lived in a feature workspace on a branch that may stay unpushed for hours. The next allocator scanned, saw the number free, and was correct to. The clause named a place the scan does not reach, so it read as a promise while behaving as nothing — it forbade nothing, blocked nothing, and was violated by conduct that was itself correct. Therefore: claiming a decision-record number MUST mean **committing a placeholder record to the default branch** — `specs/adrs/NNNN-<slug>.md` carrying status `claimed`, the claiming epic named, and no decision content — so the directory scan that allocates the next number sees it. Claiming a migration block MUST mean the same idea in whatever form the migration directory can carry: a reserved-prefix marker committed to the default branch, not a sentence in a plan. A Feature Workspace number is claimed the same way, by the directory existing on the default branch, which is what "the claim still has to precede the directory" above was always reaching for. **A claim recorded only in a feature workspace is not a claim**, and an allocator that finds a number free on the default branch MAY take it regardless of what any unmerged branch asserts. An unused claim is released by removing the placeholder or setting its status to `withdrawn`; either way **the number is not reused**, because numbers are monotonic and a withdrawn claim is still a number that once meant something. — Four renumbers in a single day measured the old mechanism, and no participant was wrong at any step, which is exactly the point. ADR-0022 was claimed by three parties — a landed amendment, E008, and E009 — and ADR-0023 by two: E008 renumbered 0022→0023; E009 gave up 0022, took 0023, then renumbered to 0024 when E008's 0023 landed first; and E009's Principle II amendment was authored as v1.2.9 and became v1.2.10 when a different v1.2.9 landed. Every allocator scanned correctly; the scan simply could not see the claims. The cost is not the renumber itself but everything that cites the number — the record, its catalog row, its traceability tags, and every artifact referencing it all have to be walked, and a missed reference is a dangling citation nothing detects.
- A feature whose recorded compliance audit names a superseded version of this document MUST re-run its compliance gate before passing its next phase gate. — An amendment moves the ground under every epic already in flight, and their branches keep validating against the version they were cut from. Recording the audited version is what makes that drift detectable rather than merely regrettable.
