# Feature Specification: Risk-Ranked Coordinator Worklist

**Feature Branch**: `00010-risk-ranked-coordinator-worklist`
**Created**: 2026-07-28
**Status**: Draft
**Spec Type**: product
**Spec Maturity**: clarified
**Epic ID**: E010
**Epic Sources**: {PRD:CAP-006}{SAD:ADR-0004}
**Product Document**: specs/prd.md

## Problem Statement

A procurement coordinator opens each day with a few hundred open purchase-order lines and no defensible
basis for choosing which to chase. The submittal log offers one optimistic promised date per line, which
is a point estimate with no error bar, so every line looks equally certain and the coordinator falls back
on whichever vendor called most recently. The forecasting work in earlier epics produces an honest
distribution for each line, but until it reaches a screen it changes no decision. Without this surface
the project has a calibrated model and a coordinator who still guesses.

## Scope

### Included

- A worklist of open purchase-order lines ordered by expected schedule harm
- Per line: median and eightieth-percentile delivery durations, and the probability of missing the need-by date
- Read-time computation of every figure from the active forecast run's stored artifacts, with no model call
- Immediate re-ranking when a coordinator adjusts a line's need-by date
- The eight degraded states named in FR-018, each stated rather than rendered as a figure
- Scoping the list by project and sorting it by a stated, enumerated set of keys

### Excluded

- **Persisting a criticality override** — E017 owns override persistence and override-aware ranking. This
  feature reads criticality and never writes it.
- **The single-line detail view** — E012 owns the posterior plot, the covariates behind a forecast, and
  navigation to source pages. This feature decomposes a line's ranking inputs within its row and stops there.
- **Producing forecasts** — E007 fits the model and writes the artifacts. This feature only reads them.
- **Answering questions about lines** — E011 owns grounded chat.
- **Alerting, digests, or any notification** — no epic in the current plan owns them, and a notification
  carrying a delivery date would be the easiest place to reintroduce a point estimate.
- **An export, download, or printable report** — this feature emits no file. FR-007 names an export among the
  surfaces its prohibition binds because the prohibition binds every surface later added, not because one
  exists here. Recording the exclusion keeps that clause a standing rule rather than a reference to nothing,
  and an export is the surface where a delivery date is easiest to reintroduce once the row no longer polices it.
- **Distinguishing a failed forecast run from a stale one** — `forecast_run` records no status or outcome,
  so a failed run leaves no row and is observationally identical to the previous run having aged. Reporting
  a state the data cannot support would be a fabricated distinction; the stale state covers both.

### Edge Cases & Boundaries

- A need-by date falls beyond the forecast horizon, so the survival array does not reach it and only a bound on the probability is available.
- A line has no posterior in the active forecast run, because it was created after the run was fitted.
- No forecast run is active at all, so the system has produced no figures for any line.
- The active run is older than the staleness threshold, so its figures describe a world that has moved on.
- A need-by date falls before the active run's as-of date, making the probability of missing it 1 by construction.
- A need-by date falls after the as-of date but before today, so the run still forecasts it while the coordinator's calendar says it has passed.
- A probability rounds to 0% or 100% at the displayed precision, which would present a forecast as a certainty.
- The median and eightieth-percentile durations are equal, because the posterior is nearly degenerate.
- Two lines tie exactly on expected harm.
- A coordinator adjusts a need-by date and the resulting order is unchanged, so the interface appears not to have responded.
- The model provider is unreachable — which must not matter, because this surface never calls it.
- A line's lifecycle state is terminal, so it is no longer open and does not belong on the worklist.
- A line's roster hash disagrees with the active run's, meaning the run was fitted against a different population.

## User Scenarios & Testing

### User Story 1 - See What to Chase First (Priority: P1)

A coordinator opens the worklist and sees open lines ordered by how much schedule damage each is expected
to cause, worst first. Each row carries the line's identity, its need-by date, the probability of missing
that date, and the median and eightieth-percentile delivery durations presented as one labelled pair. The
ordering is not an opaque score: the row also shows, subordinate to those figures, the criticality and the
calendar margin that placed the line where it is — so a coordinator can see a line ranks highly because it is both
likely to slip and consequential, rather than being asked to trust a number.

Every figure is read from artifacts a previous forecast run already stored. Opening the page issues no
model call, which is what makes it fast, reproducible, and unaffected by the provider being down.

**Why this priority**: This is the product's core value proposition and its primary surface. Without it
the forecasting work changes no decision, and five downstream epics have nothing to attach to.

**Independent Test**: Load the worklist against a frozen forecast fixture and confirm the rendered order,
figures, and per-row explanation match expected values exactly, with no model invocation recorded.

**Acceptance Scenarios**:

1. **Given** an active forecast run covering every open line, **When** the coordinator opens the worklist, **Then** open lines appear ordered by expected schedule harm, worst first, each showing probability of missing the need-by date and the median and eightieth-percentile durations.
2. **Given** a displayed line, **When** the coordinator reads the row, **Then** the criticality and the calendar margin that produced its position are present and visually subordinate to the primary figures, and neither is derived from a predicted delivery date.
3. **Given** each displayed quantile, **When** the coordinator reads it, **Then** it is accompanied by its reference class and complementary frequency, so it reads as a proportion of comparable orders rather than a commitment.
4. **Given** a displayed probability of missing a need-by date, **When** the coordinator reads it, **Then** both the chance of missing and the chance of arriving in time are stated.
5. **Given** the model provider is unreachable, **When** the coordinator opens the worklist, **Then** the page renders completely with every figure present.
6. **Given** a line whose lifecycle state is terminal, **When** the worklist is assembled, **Then** that line does not appear.
7. **Given** two lines with identical expected harm, **When** the list is ordered, **Then** the tie is broken by a stated rule and the order is stable across reloads.
8. **Given** a line whose median and eightieth-percentile durations are equal, **When** the row renders, **Then** both are shown rather than collapsed to one figure.

### User Story 2 - Ask What Happens If a Date Moves (Priority: P1)

A coordinator adjusts a line's need-by date to reflect what the project team now needs, and the worklist
reorders immediately. No model runs, nothing is refitted, and the response is fast enough to feel like
direct manipulation. The probability of missing the date and the line's rank both update, because both are
functions of the date and the stored distribution rather than of a model call.

This is what makes the ranking usable rather than merely correct. A coordinator who cannot interrogate an
ordering has no recourse except to ignore it, and the ability to adjust an input and watch the consequence
is what converts a computed list into one they will act on.

**Why this priority**: The adjustment is the trust mechanism for the ranking, not a convenience. Research
into operator behaviour finds people adopt an imperfect algorithm far more readily, and use it better,
when they can modify its output. A worklist nobody trusts is not a viable surface.

**Independent Test**: Change one line's need-by date and confirm the list reorders, the probability
changes in the expected direction, and the invocation record gains no new row.

**Acceptance Scenarios**:

1. **Given** a need-by date inside the forecast horizon, **When** the coordinator moves it earlier while it remains inside the horizon, **Then** that line's probability of missing the date does not decrease and the list reorders accordingly.
2. **Given** the same adjustment, **When** the reorder completes, **Then** the model-invocation record contains no row created during the interaction.
3. **Given** an adjustment that leaves the ordering unchanged, **When** the reorder completes, **Then** the interface states that the adjustment was applied and the order did not change.
4. **Given** a need-by date moved before the active run's as-of date, **When** the row re-renders, **Then** it states the line is already late rather than presenting a probability of missing the date.

### User Story 3 - Know When the System Has Nothing to Say (Priority: P1)

The coordinator can always tell the difference between a low risk and an unknown one. When no forecast run
is active, the worklist says so plainly and shows no figures at all rather than zeros or dashes. When a
line is not covered by the active run, it appears in a separate group marked as not forecast, still
showing its identity and need-by date so it cannot be forgotten, but carrying no risk figures and taking
no place in the ranking. When a need-by date falls beyond the forecast horizon, the row says so and shows
the residual probability as a bound rather than extrapolating past where the model was fitted. Every
populated row states the date the active forecast run was fitted as of.

**Why this priority**: A missing figure rendered as a zero is worse than no interface, because the
coordinator acts on it. This is the honesty guarantee the entire product rests on — a silent absence
causes the exact wrong decision.

**Independent Test**: Load the worklist in each of the eight degraded states and confirm each renders its
own distinct wording with no risk figure fabricated.

**Acceptance Scenarios**:

1. **Given** no active forecast run, **When** the coordinator opens the worklist, **Then** the interface states that no forecast is available and displays no risk figures for any line.
2. **Given** an active run that does not cover a line, **When** the worklist renders, **Then** that line appears in a separate group marked as not covered, outside the ranking and without risk figures.
3. **Given** a need-by date beyond the forecast horizon, **When** the row renders, **Then** it states the date is beyond the horizon, presents the residual probability as a bound rather than a point value, and the line remains in the ranking.
4. **Given** an active forecast run, **When** any populated row renders, **Then** the date the run was fitted as of is visible without hovering or opening anything.
5. **Given** an active run older than the staleness threshold, **When** the worklist renders, **Then** it states the figures are stale and reports the run's age.
6. **Given** a probability that rounds to 0% or 100% at display precision, **When** the row renders, **Then** it displays a bounded form rather than asserting certainty.
7. **Given** the active run's roster hash disagrees with a line's, **When** the worklist renders, **Then** the mismatch is stated rather than the figures being shown as though current.
8. **Given** a need-by date after the as-of date but before today, **When** the row renders, **Then** it shows the forecast probability and separately flags that the date has passed on the coordinator's calendar.
9. **Given** a line whose **stored** need-by date precedes the active run's as-of date, with no session adjustment applied, **When** the worklist renders, **Then** the row states the line is already late, remains in the ranking, and shows its quantile pair with no miss probability.
10. **Given** an active run past the staleness threshold and a row whose need-by date lies beyond the horizon, **When** the worklist renders, **Then** the stale banner and the beyond-horizon row label are both present, each in its own wording, with neither replacing the other.

### User Story 4 - Narrow and Reorder the List (Priority: P2)

A coordinator working one project scopes the worklist to it, and can reorder the list by a small set of
keys other than expected harm — for instance by need-by date when planning a week rather than triaging a
day. The available sort keys are stated on screen along with which is active, and the set deliberately
excludes any key that would order lines by a single delivery figure.

**Why this priority**: The P1 stories deliver a usable surface without this; a coordinator can read a
combined list. Scoping and sorting increase throughput but nothing depends on them, and E012, E013, E016,
E017 and E019 all attach to the P1 behaviour.

**Independent Test**: Filter to one project and confirm only its lines appear; change the sort key and
confirm the order changes and the active key is displayed.

**Acceptance Scenarios**:

1. **Given** lines across five projects, **When** the coordinator scopes to one project, **Then** only that project's lines appear and the ranking is recomputed within that scope.
2. **Given** the worklist, **When** the coordinator inspects the ordering control, **Then** the active sort key and direction are stated.
3. **Given** the set of available sort keys, **When** it is inspected, **Then** it contains no key that orders lines by a single delivery date or by one quantile alone.
4. **Given** a filter that matches no lines, **When** the list renders, **Then** it states that the filter matched nothing, using different wording from the no-forecast state.

## Requirements

### Ranking

- **FR-001**: The worklist MUST display open purchase-order lines ordered by expected schedule harm, defined as the mean over the stored draws of the delivery overrun past the need-by date, counting zero where a draw delivers on time, multiplied by the line's criticality.
- **FR-002**: Every risk figure MUST be computed at read time from the active forecast run's stored artifacts. The worklist MUST NOT depend on a model call to render.
- **FR-009**: Each row MUST present the criticality and the calendar margin that contributed to its rank, visually subordinate to the primary figures, so the ordering is inspectable rather than opaque. Calendar margin renders negative when a need-by date precedes the as-of date and takes no forecast input — see Glossary. A margin derived from a predicted delivery date is forbidden, because subtracting it from the need-by date would reconstruct that date and defeat FR-007. The score has exactly three inputs and the row carries all three: the line's delivery-duration distribution, summarised on the row by the FR-004 quantile pair; the calendar margin, which is what a draw must exceed before any of it counts as overrun; and the criticality the overrun is multiplied by. Naming only two would leave SC-004 asking a coordinator to account for a position from a partial decomposition, when the third input is already on the row under FR-003. The score itself stays off the row under FR-041 -- with criticality displayed beside it, publishing the score would surrender the mean overrun to a division.
- **FR-010**: Ties in expected harm MUST be broken by need-by date ascending, then criticality descending, then line identifier ascending. The identifier terminates the order so it is total and reproducible across reloads. **Line identifier** here means the line's stable generated key, not its human-readable identity of project, purchase order, line number and description: the two produce different orders, and only the generated key is unique by construction, which is the whole reason it can terminate. The Glossary records the distinction, and the row displays the identity while the ordering uses the key. Ties are not an edge case: expected harm is exactly zero for every line whose draws all land on or before its need-by date, so at a full horizon a large block of comfortable lines shares a harm of zero and this rule is the sole ordering within it.
- **FR-013**: While a need-by date remains within the interval from the active run's as-of date to the end of its horizon, moving it earlier MUST NOT decrease the displayed probability of missing it. The interval is open at its lower end and closed at its upper: it is the set of dates `d` with `as_of_date < d <= as_of_date + horizon_days`, which is exactly the set of offsets `k = 1..horizon_days` the survival grid stores. The lower end is open because `d == as_of_date` resolves to already late under FR-030 and displays no probability at all, so the property would have no subject at its own endpoint; the upper end is closed because `k = horizon_days` is an in-grid day, and the next day is beyond the horizon and displays a bound under FR-017. The comparison is over displayed forms, not over the stored probability: where both dates render as integers the integers are compared, `<1%` ranks below every integer and `>99%` above every integer. A move from `<1%` to `7%` and a move from `93%` to `>99%` are both increases, so the property stays decidable at exactly the bounded forms FR-008 introduces rather than becoming undefined there.
- **FR-013a**: The ranking function MUST be monotonic in criticality — holding all else equal, a higher criticality MUST NOT move a line further from the top of the list. This is a property of the ranking computation; this feature provides no interaction that changes criticality, and E017 owns the one that will. The subject is the harm-ordered sequence the ranking computation produces under the default sort key and a line's position within it, not the rendered row order: FR-026 admits three further keys under which criticality does not determine position, and asserting the property against a list ordered by need-by date would make it hold vacuously. "Holding all else equal" ranges over the line's stored draws, its effective need-by date and its identifier, and over every other line in the list, with criticality alone raised; FR-010's tiebreak inputs are held fixed with the rest. The property is weak rather than strict and MUST still hold across the zero-harm block: where every draw lands on or before the need-by date, harm is exactly zero at every criticality, so raising criticality changes no score and the order inside that block is decided by FR-010's second key, criticality descending -- which moves the line toward the top or leaves it where it was, and never further from it.

### Presentation honesty

- **FR-003**: Every populated row MUST display the probability of missing the need-by date, and the median and eightieth-percentile delivery durations. The durations MUST be labelled as counted from the active run's as-of date. Unanchored, a median of thirty days on a ten-day-old run reads ten days more optimistic than it is -- a silent error of exactly the kind this specification targets. Both quantiles MUST be read under the normative convention E003 publishes in `schema_constants.percentile_convention` -- nearest rank, one-based, no interpolation, `draws[ceil(p x draw_count)]` -- and that convention MUST travel with the displayed figures rather than being compiled into either tier. Naming a median and an eightieth percentile without the rank rule leaves a frozen draw array admitting more than one expected pair, which is the one thing a frozen fixture exists to exclude. Where the convention and the draw count behind it are published twice -- once at page scope and again with each figure -- the copy carried with the figure is authoritative, because it is the one attached to the figure it describes, and the two MUST agree within a single response. A page-scope copy disagreeing with a figure's own is a provenance defect under Principle I rather than a display choice: both cannot be the rule the figure was computed under, and the reader has no way to tell which is.
- **FR-004**: The median and eightieth-percentile durations MUST be presented as a single labelled pair, and MUST NOT be independently sortable.
- **FR-005**: Each quantile MUST be accompanied by a statement of its reference class and complementary frequency, so it reads as a proportion of comparable orders rather than as a commitment. The reference class MUST name a population a coordinator would recognise -- comparable orders, as the Glossary defines the term -- rather than the artifact the figure was computed from: a single-event figure with no stated reference class is read in mutually contradictory ways, which is why "a 30% chance of rain" has been found to be read as 30% of the time, of the area, and of forecasters. The `posterior_predictive_draws` basis, the draw count and the percentile convention that travel in the payload are provenance and MUST NOT stand in for the rendered statement. The complementary frequency MUST be rendered as a natural frequency over a stated denominator -- "half of comparable orders land by this day"; "four in five land by this day, one in five later" -- rather than as a bare percentage, because frequency-framed displays produced measurably better incentivized decisions than the percentage and text-only alternatives. Naming the covariates behind a particular line's forecast is E012's; the class named here is the population, not the conditioning.
- **FR-006**: Wherever a probability of missing the need-by date is displayed, it MUST be stated in both directions, so neither the chance of lateness nor the chance of arriving in time is left to be inferred. The two directions MUST carry equal prominence -- the same type scale and the same weight, adjacent within one statement -- and MUST appear in a fixed order on every row, the chance of missing first. Positive and negative framings are not behaviourally equivalent, so a pair in which one direction is set larger, heavier, or first on some rows and second on others is not the dual framing this requirement asks for; it is a single framing with a footnote. Both directions together count as one comparison quantity under FR-027, exactly as the quantile pair does.
- **FR-007**: The system MUST NOT render a single predicted delivery date for a line anywhere — in a row, a label, a sort control, a tooltip, an export, or the response the interface renders from. The enumeration binds every surface this feature defines and every surface later added to it; it is not a description of the surfaces that exist. This feature defines no export and no notification (Scope § Excluded), so those two clauses are standing prohibitions on adding one that carries a date rather than references to nothing. The response is named explicitly because it is the one surface no coordinator reads directly and therefore the one an enumeration of screens silently omits: an interface renders only what it is given, so a date withheld from the row but present in the payload is one component away from the screen, and a prohibition that stops at the rendered row is enforced by whoever writes the next client. FR-041 extends the prohibition from a date the interface renders to one its displayed figures yield by arithmetic, and its set is taken over what the response admits as well as over what the row renders.
- **FR-008**: Probabilities MUST be displayed to whole percent -- the precision several thousand draws honestly support, since a single draw is a fraction of one percent and a finer figure would assert resolution the artifact does not have. A probability that rounds to 0% or 100% MUST render as a bounded form, `<1%` or `>99%`. Rounding is half-up at the percent scale -- the stored probability multiplied by one hundred, then rounded half-up to an integer, so a stored `0.125` renders `13%` and not the `12%` a half-to-even rule produces -- and the complementary direction MUST be computed as one hundred minus the displayed integer rather than rounded independently, so a mandated FR-006 pair always sums to one hundred. When one direction renders as a bound, its complement MUST also render as a bound, so a bounded value never pairs with a flat certainty and reintroduces through FR-006 what this requirement removes. A stored probability of exactly zero or exactly one takes the same bounded form as one that merely rounds there, and this is a rule rather than an omission: several thousand draws cannot evidence a certainty, an exact zero in the array is itself an estimate at the resolution the draw count supports, and the displayed forms `0%` and `100%` are unrepresentable in the contract for that reason. There is no endpoint at which the bounded form is skipped.
- **FR-027**: A row MUST carry at most four **comparison quantities**. A comparison quantity is defined by where it sits rather than by what a coordinator is presumed to scan: it is a member of the primary region FR-032 names, so two reviewers counting the same row reach the same total. The four are the line identity, the need-by date, the probability of missing it -- whose two FR-006 directions count as one, exactly as the pair does -- and the quantile pair, which counts as one. Explanatory context required by FR-009 and FR-019 is not a comparison quantity and MUST be visually subordinate. It is not offered as a sort key except for the criticality and calendar-margin keys FR-026 enumerates, which are admitted deliberately because both are inputs a coordinator may reasonably triage by.
  The cap is decidable only if the row's other content is closed as well, or a fifth scannable figure could be parked in the secondary region and satisfy both this rule and FR-032 as written. It is closed, in three classes and no fourth. **Comparison quantities**: the four above, in the primary region. **Explanatory context**: exactly the three items FR-009 and FR-019 require -- the as-of date, the criticality, and the calendar margin -- in the secondary region and nothing else. **Row status**: at most three marks and the class closed at exactly these -- the row's position in the ordering, its resolved degraded-state label, and FR-031's unsaved mark -- none of which is a figure read from the forecast, each carried as text under FR-048 and FR-050, and none counting against the cap. A row carries whichever of the three apply to it; an excluded row has no position and an unadjusted row has no unsaved mark. Anything outside these three closed sets is a fifth comparison quantity whatever region it is rendered in, and that is the counting procedure SC-014 is evaluated by.
  This feature offers no opt-in quantity at all: the response's primary object is closed over exactly the four, so the cap here is unconditional rather than a default with an open path beside it. The opt-in clause binds whatever adds one later -- at most one opt-in comparison quantity may be active at a time, so a row never carries more than five, and it MUST itself satisfy FR-005 through FR-008 and FR-041, so an opt-in column cannot reintroduce a bare point estimate or a derivable one.
- **FR-041**: No set of figures a row displays may combine arithmetically into a single predicted delivery date, or into a single central summary of a line's delivery distribution -- a mean, a mode, an expected overrun, or one quantile standing alone. FR-007 enumerates the surfaces a date may not be rendered on and FR-009 states the rule for one figure; this states it for the set, because the defect is a combination rather than a field. The check is finite rather than a matter of judgment: FR-027 closes the row's content in three enumerated classes, so the combinations are taken over that enumeration rather than over whatever an interface happens to render.
  What separates the permitted case from the forbidden one is the shape of the result, not whether arithmetic is possible. FR-003 and FR-019 deliberately put an as-of date and durations counted from it on the same row, and adding them yields the day by which half of comparable orders land and the day by which four in five do -- two labelled quantiles of a distribution, each carrying the reference class and complementary frequency FR-005 requires, which is the honest reading of the artifact stated in the units a coordinator plans in. Adding a need-by date to a mean overrun yields one date with no proportion attached to it, which reads as *the* delivery date. The rule follows: a forecast-derived figure may be displayed alongside a date it can be added to only where it is a member of the FR-004 pair and carries its FR-005 labelling, so the arithmetic yields a labelled quantile rather than a bare date. Subtracting the calendar margin from the need-by date is permitted for the complementary reason -- it yields the as-of date, which the row already shows, because the margin takes no forecast input whatever.
  The rule binds the ranking quantity as tightly as it binds a field. Expected harm is the mean overrun multiplied by criticality and criticality is on the row, so publishing the score would surrender the mean overrun to a division and the delivery date to one further addition. That is why the ordering reaches the coordinator as a position under FR-048 rather than as a number.
- **FR-052**: A response carrying figures MUST identify the artifact set those figures were computed from: the active run's identifier, its model version, and the schema version of its stored arrays, alongside the as-of date FR-019 already places on every populated row. Principle I requires a published figure to resolve to the artifact it came from, and the as-of date alone does not resolve it -- two runs can carry the same as-of date, a refit against the same anchor produces a second run with different draws, and neither the model version nor the artifact schema version is derivable from a date. The division of labour is deliberate: the as-of date is the coordinator-facing part of the identification, which is why FR-019 puts it in the row, and the run identifier and the two versions are the auditable part, which is why they travel in the response rather than on the screen. Together they are what makes a reported figure reproducible -- given the identifier and the schema version, the same arrays can be read again and the same figure recomputed -- and FR-043 is what happens when the schema version is one the reader does not recognise.
- **FR-053**: The response MUST carry finished figures rather than the arrays and raw values they were computed from. Three clauses, each with its own defect behind it.
  **No per-line arrays.** The stored draw array and the survival array MUST NOT appear in the response. A consumer holding either can compute a mean, a mode, or any quantile it chooses and render exactly the delivery date FR-007 removes, so withholding them is what keeps FR-007 enforceable against a client this feature does not write. The prohibition is scoped to this surface rather than to the arrays themselves: E003 stores them, E007 writes them, and the project plan records E012 as a second consumer of the same arrays for a single-line detail view whose presentation obligations are that feature's to state. This requirement binds the worklist response and asserts nothing about theirs -- a scope stated here rather than left as the silence that would either over-reach into another epic or read as permission.
  **No raw probability.** A probability MUST reach the interface already rounded under FR-008, as the displayed integer together with the finished display string, and never as the stored value. FR-008 fixes half-up rounding at whole percent and derives the complement from the displayed integer; a raw value in the payload hands the interface a second rounding, and two independent roundings of 0.4951 and 0.5049 produce the FR-006 pair summing to 101 that FR-008 exists to prevent. The arithmetic happens once, on the side of the boundary where it is unit-testable (Principle V).
  **No numeric value in the bounded form.** Where FR-008's bounded form is in use, neither direction may carry a numeric value at all, and the displayed forms `0%` and `100%` MUST have no representation in the response. A bounded pair whose numerals survive beside the bound leaves a certainty a renderer can reach for, and unrepresentability is the only version of this rule that fails a regression at the boundary rather than on a screen.

### Degraded states

- **FR-018**: The worklist MUST distinguish eight degraded states, each by its own wording: no active forecast run; the active run is stale; a line is not covered by the active run; a need-by date is beyond the horizon; a filter matched no lines; a line's roster hash disagrees with the active run's; a need-by date falls before the as-of date, making the line already late; and a need-by date has passed relative to Today while remaining inside the forecast frame. This enumeration is canonical and is what "the degraded states" means elsewhere in this specification. Where this specification says "the coordinator's calendar" it means Today exactly as the Glossary defines it -- the request-time date in the single configured time zone -- and never the clock of the device the page is opened on, so the same line carries the same state for every coordinator. A failure to read the stored artifacts is not among the eight and is not a ninth: see FR-043. Each of the eight MUST be reported as a successful outcome carrying its state, never as a fault. All eight are reached by a successful read and describe what the system knows, so reporting one as an error would make an honest answer indistinguishable from an outage -- the same defect in the opposite direction to rendering an outage as an empty state, and FR-043's condition is the only one this feature reports as a fault.
- **FR-018a**: Where more than one state applies to a line, exactly one wins, chosen by this precedence: roster mismatch, then not covered, then beyond horizon, then already late, then calendar-passed. The winning state's owning requirement governs the row in full -- its label, whether the line is ranked, and which figures are suppressed. Losing states contribute no behaviour, so a line is never simultaneously required to be ranked and excluded. The order runs from states that leave no figure that may be shown, through states that make one only partially available, to states that merely annotate a figure that is sound. Every state that undermines trust in a figure outranks every state that merely annotates one, generalising the rule FR-021 already applies alone. The first class is stated as *no figure may be shown* rather than as *the figure cannot be trusted* so that not covered belongs to it without strain: there is no figure to distrust, which is the limiting case of one that cannot be relied on, and both refuse identically. A state added later is placed by two questions rather than by extending this list ad hoc -- which of the three classes it falls in, and, within that class, whether it names a more specific cause than its neighbours, since the label is what tells a coordinator what to do and the more specific cause is the more actionable one. That second question is why roster mismatch precedes not covered: both refuse, and only roster mismatch names why. The axis partitions the enumeration rather than merely ordering it, so SC-009's second clause has a decidable subject: **roster mismatch, not covered, and the page-scope no-active-run are the states that compromise trust in a figure**, and a row under any of them displays no risk figure whatever; **beyond horizon** makes a figure only partially available and displays it as a bound; **already late, calendar passed, and the page-scope stale run and empty filter** annotate a figure that is sound, and suppress only what is uninformative -- in the single case of already late, the miss probability that is 1 by construction. The three page-scope states -- no active run, stale run, and empty filter -- render as banners and compose with a row label rather than competing with it. Combinations are reachable rather than theoretical: a run old enough makes a line simultaneously beyond horizon and calendar-passed. Staleness is necessary for that pair but nowhere near sufficient -- it requires today to fall past the as-of date plus the whole horizon, so `age_days > horizon_days`, which at a 365-day horizon is a run more than fifty times the seven-day threshold's age. FR-033 records the condition; FR-038's injected today is what makes the pair constructible in a fixture without waiting a year for it.
- **FR-033**: The states that can co-occur on one line MUST be enumerated, because a check over FR-018a's precedence has to know which pairs are jointly constructible before it can assert which one wins. Roster mismatch and not covered are independent of each other and of every date-derived state, so either combines with any of them and with the other. The three date-derived states are pairwise exclusive by their own arithmetic -- already late is `need_by <= as_of`, calendar passed is `as_of < need_by <= today`, beyond horizon is `need_by > as_of + horizon_days` -- with one exception: beyond horizon and calendar passed co-occur exactly when `today > as_of + horizon_days`, which is the stale-run combination FR-018a already names. That condition is `age_days > horizon_days`; it entails staleness and is far stronger than it, so a fixture realising this pair sets FR-038's injected today past the run's whole horizon rather than merely past the staleness threshold, and a fixture that only exceeds the threshold does not reach it. Not covered does combine with beyond horizon: beyond horizon is a comparison of the need-by date against the run's horizon and needs no posterior to hold, the posterior is only what the resulting figure would need, and precedence gives that row to not covered before any figure is read. Stale run and empty filter compose with every row state; no active run does not compose with any, because with no run there is no as-of date, no horizon and no roster hash, so no row state is defined and the page-scope state governs every row alone.
  The three page-scope states have their own admissible combinations, and they are not free either. **No active run and stale run are mutually exclusive**: staleness is the age of a run, and where no run is active there is no as-of date to age from, so a response asserting both would report a run and no run at once. **No active run and empty filter compose**: whether a scope filter matched an open line is decided over the line set and is independent of whether a forecast exists, so a scope holding no open line reports both. **Stale run and empty filter compose**, which is the pair the contract's own example carries. The admissible sets are therefore exactly six -- none of them, each of the three alone, and the two composing pairs -- and no set of three is admissible, because every triple contains the excluded pair. This is stated because a payload that admits any subset of three states admits two that contradict each other's own required content, and an unstated combination is one an implementation resolves by accident.
- **FR-042**: When a scope filter is applied and matches no open line, the worklist MUST state that the filter matched nothing, in wording distinct from FR-015's, and MUST leave the scoping control and its full set of selectable projects on screen so the coordinator can leave the scope without reloading or guessing. Both groups are empty and no figure is displayed, because there is no line to display one for. This is the state's owning requirement: FR-018 enumerates it and FR-018a routes a row's behaviour to the winning state's owning requirement, so until now it had none and only a US4 acceptance scenario described it. It is page-scope and composes with any other page-scope state rather than competing with one -- a stale run and an empty filter both banner at once. An unfiltered worklist holding no open lines is **not** this state and MUST NOT borrow its wording: the claim that a filter matched nothing would be false, and FR-018's enumeration is canonical, so no ninth state may be invented for it either.
- **FR-043**: When the stored artifacts cannot be read at all -- the datastore is unreachable, the request fails before a worklist can be assembled, or the active run's artifact schema version is one this reader does not recognise -- the interface MUST state that it could not read the forecast data, MUST display no row and no figure, and MUST carry an identifier that correlates the failure to its record. The third condition is a refusal rather than a breakdown, and it is deliberate: the registered architecture requires a reader meeting an unfamiliar artifact schema version to fail loudly rather than misread array offsets (`specs/sad.md` § Data Management), and a misread offset yields a figure wrong in a way no coordinator could see. It belongs here rather than among FR-018's eight for the same reason the other two do -- the system did not read the artifacts, so it holds no knowledge about any line to report -- and it is reported with its own cause rather than as a generic fault, because "this run was written by a schema this build does not know" names what would change it and a bare failure does not. Its wording MUST differ from FR-015's: one means the system looked and there was nothing there, the other means it could not look, and rendering them alike presents an outage as an honest empty state -- the same defect in the opposite direction to a missing figure rendered as a zero. This is deliberately **not** a ninth entry in FR-018, which stays canonical at eight. Those eight are states of what the system knows, each reached by a successful read and each carried inside a successful response; a failure to read is not knowledge about a line. SC-009's distinctness obligation therefore ranges over the eight, and the one distinction that matters here -- from FR-015 -- is stated in this requirement instead.
- **FR-044**: The wording of each of FR-018's eight states MUST be fixed in a single committed copy table keyed by state, and each entry MUST name the cause and what would change it, which is the difference between a refusal a coordinator can act on and a dead end. Distinctness is then a property of that table rather than of the implementer's judgment, which is what SC-009 needs to be decidable at all: no entry may be a substring of another, and every entry MUST contain at least one phrase occurring in no other entry, so the check is a comparison over the table rather than a reading of a screen someone has already built. A state whose copy is composed at the render site is a state whose wording no test can pin, and "distinguishable by wording alone" would be evaluated only after the implementer had invented the copy it judges.
- **FR-015**: When no forecast run is active, the worklist MUST state that plainly and MUST NOT display risk figures for any line. Every open line in scope MUST still be listed, carrying its identity and its need-by date and nothing else, so the coordinator's inventory of what is outstanding does not vanish with the forecast. "Plainly" is discharged by the property FR-032 states -- a page-scope banner carrying this state's committed copy under FR-044, present before any row content in the reading order -- and never by the absence of figures alone, which is indistinguishable from a page that failed to load one.
- **FR-016**: A line not covered by the active forecast run MUST appear in a separate group, marked as not covered, excluded from the ranking, and carrying no risk figures. The row MUST still carry the line's identity and its need-by date: that is what makes the group an inventory the coordinator cannot forget rather than a discard pile, and it is the row content US3 promises. It MUST carry nothing further -- not criticality, not calendar margin -- because with the risk figures withheld those would be the only numbers on the row and would be read as risk. The separation binds the response as well as the rendered screen: excluded lines travel as a collection disjoint from the ranked one rather than as a flag inside a single list, so no consumer can sort an excluded line into the ranking and the exclusion survives every ordering (SC-008, FR-045). A group that exists only in the rendering is a group the next consumer of this surface re-decides, and this surface has three recorded consumers.
- **FR-045**: The excluded group MUST be ordered by need-by date ascending, then by line identifier ascending, and MUST hold that order under every offered sort key. It is scoped by FR-025 exactly as the ranking is, so a line outside the active project scope appears in neither group and the counts still reconcile under SC-023. The order is fixed rather than following the active key because at least one of FR-026's four keys reads a figure an excluded line does not have -- expected harm needs draws it has none of, and with no active run the calendar margin has no as-of date to count from -- and because a group outside the ranking that reordered with the ranking would read as part of it.
- **FR-017**: When a need-by date falls beyond the active run's forecast horizon, the row MUST state that and MUST present the residual tail mass as an upper bound stated in both directions, in the form "at most N% late, at least (100 minus N)% on time", rather than as a point value. Where N would round to 0 or 100 the row MUST degrade to FR-008's bounded wording rather than emit a bound that asserts certainty. The line MUST remain in the ranking unless a higher-precedence state under FR-018a applies, because expected harm is computed from the draws and does not depend on the survival grid. Which of the two measures a displayed probability is -- a point read from the survival grid at the need-by offset, or an upper bound on the residual tail -- MUST be carried with the figure rather than left for the interface to infer from the row's state. The two are rendered in different words, an unmarked figure is one refactor away from being rendered as a point, and inferring the measure from the state makes the two rules that must agree live in different tiers. SC-020 fixes which value each measure carries; this fixes that the consumer is told which one it has.
- **FR-019**: Every populated row MUST display the date the active forecast run was fitted as of, visible without further interaction. "Visible without further interaction" and FR-032's "reachable without hover or expansion" are one obligation and not two: the date is rendered as text inside the row's own element on the initial render, in the visual output and in the accessibility tree alike, with no hover, focus, expansion, click or panel required to bring it into either. Text that is present but revealed only by an interaction fails this, and so does text carried only in page scope, because a row read on its own then carries no anchor.
- **FR-020**: The probability of missing a need-by date MUST be evaluated relative to the active run's as-of date.
- **FR-020a**: A row's figures MUST NOT change other than by a new active forecast run, a coordinator action, or the advance of the day boundary defined in the Glossary. The exception is required rather than conceded: FR-029's run age and FR-030's calendar-passed flag both advance with the date, and forbidding that would forbid behaviour two other requirements mandate. A session-scoped what-if under FR-031 resetting on reload is a coordinator action's expiry, not an unattended change. The claim is over unobserved time and no single response can falsify it, so the verification means is stated here rather than left to inspection: every response MUST carry a validator computed over exactly the admitted inputs and nothing else -- the active run's identity or its absence, today in the configured time zone, the coordinator's applied scope, sort and adjustment set, and the state of the open-line set the response reports, meaning which lines are in it and every stored field the response derives from them: identity, recorded need-by date, criticality, lifecycle state and roster hash -- and the check is two-sided. Holding all of them fixed and repeating the request MUST yield an unchanged validator and unchanged figures; changing each one in turn MUST change it. A validator that survives a change to an admitted input, or that moves without one, is exactly the defect this requirement describes, reduced to one comparison.
  The line set is an admitted input, and stating it is not pedantry. This requirement's subject is *a row's* figures while the response's subject is a *set* of rows, and the two diverge exactly where it matters: a line opened since the last request, one FR-022 has since made terminal, or one whose criticality or recorded need-by date has moved, changes the worklist while every surviving row's figures stand still. A validator blind to that is not merely incomplete but false, because a response withheld as unchanged asserts that the whole response is unchanged and not only that no figure moved -- and the line the coordinator most needs is the one that appeared since they last looked. E017 makes criticality mutable against this same surface, so the input set has to observe it before that lands rather than after.
  Two requests whose admitted inputs are all unchanged MUST return responses equal member for member with exactly one exception: the timestamp recording when the response was produced, which describes the act of answering rather than what was answered. It is the only member permitted to differ and it takes no part in the validator, since a validator moving with the clock would report a change on every request and assert nothing. Naming the one exception is what makes the equality decidable rather than approximately true.
- **FR-021**: When a line's roster hash disagrees with the active run's, the worklist MUST state the mismatch and MUST withhold that line's risk figures, treating it as not covered both for ranking purposes and for what the row still carries under FR-016 -- its identity and its need-by date, and nothing more. A run fitted against a different population is the case where a wrong figure is least visible, so it refuses like every other trust-compromised state rather than annotating.
- **FR-022**: Lines whose lifecycle state is terminal MUST be excluded from the worklist.
- **FR-029**: The worklist MUST report the active run as stale once its age exceeds seven days, and MUST report the run's age when it does. Age is today minus the run's as-of date in whole days -- the as-of date rather than the row's creation time, because FR-019 already puts the as-of date on every row so a coordinator can verify the staleness claim from a figure the screen already shows, and because a backfilled run's creation time diverges from what it was fitted against. The recorded basis for seven days is one refit cadence: a run whose anchor predates the current week has missed at least a week of lifecycle events. The threshold is configuration and the basis MUST travel with it -- into the response that reports the staleness claim, beside the threshold and the run's age, rather than staying in the configuration file that holds the value. A threshold whose basis is not on the same surface as the claim it licenses is indistinguishable from one somebody guessed, which is the shortfall Principle VII forbids leaving unpublished; FR-029 fails if the value arrives without it.
  Staleness annotates and suppresses nothing. A stale run's populated rows keep every figure they would otherwise carry, keep their ranking membership, and keep their own row labels: the figures are the ones that run produced, and they are not less true for the run being old, only less current -- which is precisely what the banner says. FR-018a places stale among the states that annotate a figure that is sound, and withholding figures here would be a refusal the data does not warrant.
  Because a page-level banner alone stops carrying once rows are sorted, filtered, or read one at a time, the row MUST carry the signal too: while the active run is stale, every populated row's as-of date -- which FR-019 already puts on the row -- MUST be marked as stale in the row itself, so a coordinator reading one row in isolation cannot take its figures as current. This needs no new figure and no new field; the response already carries the run's staleness and each row's as-of date.
- **FR-030**: A need-by date at or earlier than the active run's as-of date -- `need_by <= as_of_date` -- MUST be reported as already late rather than carrying a forecast probability, which is 1 by construction and therefore uninformative. The equality case belongs here rather than to the horizon or to the nominal row: the survival grid is one-based over `k = 1..horizon_days` and stores no `k = 0`, so at equality there is no offset to read and no probability exists to display. The storage layer's clamp and FR-033's arithmetic both state the boundary this way, and "earlier than" alone would leave `need_by == as_of_date` owned by no requirement at all. Unless a higher-precedence state under FR-018a applies, the line MUST remain in the ranking and MUST still display its quantile pair. Already late presupposes a line the active run covers with a matching roster hash; where it does not, the higher-precedence state governs and no quantile pair exists to show. The quantile pair is what tells a coordinator how much further slip is still coming -- the harm score for such a line is dominated by the days already elapsed, so it conveys urgency rather than remaining exposure. A need-by date between the as-of date and today MUST carry its forecast probability and be separately flagged as passed relative to Today as the Glossary defines it -- the request-time date in the single configured time zone, not the viewer's device -- so the same line carries the same flag for every coordinator who opens it.
- **FR-054**: A figure a degraded state withholds MUST NOT be carried as a value of any kind. Where the state excludes the line from the ranking, the response carries no member that could hold the figure at all -- FR-016's row has an identity and a need-by date and no property a renderer could fill -- and where the line keeps its other figures and loses one, as an already-late row loses the miss probability under FR-030, the withheld figure is explicitly empty and the row's resolved state travels beside it. A zero, a dash, an empty string, a sentinel date, or a placeholder of any other kind is forbidden in both cases: the dash on a screen is the defect FR-015 exists to prevent, and a zero in a payload is that same defect one renderer earlier, where nobody is looking for it. An empty member is never the sole carrier of the state either -- FR-050 requires the state to be carried by text -- so no consumer has to infer which state suppressed a figure from the bare fact that it is missing, and the two mechanisms are distinguished on purpose: structural absence where nothing may ever be shown, an explicit empty where a figure exists in the general case and this row's state removed it.

### Interaction

- **FR-011**: Adjusting a line's need-by date MUST reorder the worklist without creating any row in the model-invocation record.
- **FR-012**: An adjustment that produces no change in ordering MUST be acknowledged by a persistent inline status message in a live region, stating that it was applied and that the order is unchanged. Persistent rather than a timed notification, because a message that disappears is the documented way an acknowledgement is missed -- and a coordinator unable to tell whether their adjustment applied is the exact failure this requirement exists to prevent. Persistent is bounded rather than permanent, and the bound is stated so "persistent" is not read as "forever": the message remains until the next adjustment replaces it with that adjustment's acknowledgement, the coordinator dismisses it, or the page is reloaded. What it MUST NOT do is expire on a timer.
  Whether the order changed is decided from the response rather than by the interface re-deriving it: every response MUST carry a single value over the ranked group's ordered sequence of line identifiers, equal between two responses exactly when that sequence is equal, and FR-046's acknowledgement is decided by the same comparison. Its domain is stated so the comparison is decidable at the edges rather than only in the middle. It is defined for every response including one whose ranked group is empty, where it takes the value of the empty sequence -- so two responses that rank nothing carry the same value however much else differs between them, and equality of this value alone MUST NOT be read as sameness of state, which travels separately and is what actually distinguishes a worklist with no active run from a filter that matched no line. The comparison is meaningful only between two responses computed under the same scope and sort key, which is precisely the case this requirement governs: an adjustment changes the adjustment set and nothing else.
- **FR-046**: An adjustment that *does* change the ordering MUST be acknowledged in the same live region as one that does not, stating that the adjustment was applied and that the order changed, and naming the adjusted line's new position. The two acknowledgements MUST be distinguishable from each other, so which of the two happened is never left to be inferred from the rows. Keyboard focus MUST remain on the adjusted row's need-by control rather than returning to the top of a list that has just reordered underneath it. FR-012 covers only the unchanged case; a reorder announced to nobody is the same failure for a coordinator reading the page through assistive technology that an unacknowledged no-op is for one reading it visually -- the list moves and nothing is said.
- **FR-025**: The worklist MUST be scopeable to a single project, with the ranking recomputed within that scope. The domain of the scoping control MUST travel with the worklist in every state, not only in the empty-filter state FR-042 names: the full set of selectable projects, each carrying its identifier and its count of open lines, and the full set even while a scope is active, so a coordinator can see where outstanding work sits and can leave a scope without a second request the 1.5-second budget has no room for. The count is what separates a project holding no open line from one the coordinator has simply not scoped to -- two states that are otherwise identical from inside a filtered list -- and summed across the set it is the unscoped total that SC-023's reconciliation is stated against.
- **FR-026**: The available sort keys are exactly four -- expected schedule harm descending as the default, need-by date, criticality, and calendar margin -- and MUST be enumerated on screen with the active key and direction. The rule the set satisfies is that **no offered key may order the list by a forecast-derived figure other than the composite harm score**. The probability of missing the need-by date fails it and is deliberately excluded: it is neither a delivery date nor a quantile, so FR-007's exclusions would permit it, but it is the model's answer for a line reduced to one number, and a list ordered by it presents that number as the priority order while discarding the criticality that decides whether a slip matters. Criticality and calendar margin discard the other inputs just as completely -- which is the objection this paragraph has to answer -- and what admits them is that neither takes any forecast input at all (FR-009), so ordering by one of them cannot be mistaken for the model's ranking: a coordinator sorting by criticality knows they are sorting by a business judgment, and one sorting by calendar margin knows they are sorting by the calendar. Expected harm is forecast-derived and is the default for the opposite reason -- it is the only key that carries the distribution and the criticality at once, so ordering by it collapses nothing. Criticality and calendar margin are FR-009 context and are admitted here as an explicit carve-out from FR-027's rule that context is not offered as a sort key.
- **FR-047**: The tiebreak rule FR-010 fixes MUST be stated on screen alongside the active sort key and direction that FR-026 already requires there. Under the default key it is not a footnote: expected harm is exactly zero for every line whose draws all land on or before its need-by date, so the tiebreak alone orders that entire block, and an order the coordinator cannot account for reads as arbitrary -- the failure the per-row decomposition exists to avoid, reappearing at the level of the list. The rule travels in the response rather than being written into the interface, so what is stated on screen is the rule the server actually applied.
- **FR-055**: The adjustment set FR-031 admits MUST state which adjustments it accepts, and every refusal and every non-application MUST reach the coordinator with its cause.
  **Admissibility.** The number of adjustments in force at once is bounded, at the value the interface contract records, and a set exceeding the bound is refused with the cap stated rather than silently truncated -- a truncated set re-ranks the list against dates the coordinator did not ask for, which is worse than refusing, because the refusal is visible. An adjustment whose date is not a calendar date, a second adjustment naming a line already adjusted, and a date outside the bounded window around Today the contract records are each refused, naming the parameter and the reason. Each is a request the system cannot honour rather than a state of the worklist, which is why these are refusals and FR-018's eight are not. The stored constraint that a need-by date not precede its order date is deliberately **not** applied to an adjustment: that constraint guards the record, this value is never written to the record (FR-031), and enforcing it would refuse a coordinator a question -- what if this had been needed before it was ordered -- that the ranking answers correctly and that costs nothing to answer.
  **Non-application.** An adjustment naming a line the response does not contain -- absent, terminal under FR-022, or outside the active scope under FR-025 -- is not a refusal of the request. It MUST be reported back stating which of those three it was, with the rest of the set applied. Dropping it silently would leave the coordinator believing an adjustment took effect while reading an ordering computed without it, which is FR-012's failure arriving by a different route: an adjustment whose effect the coordinator cannot confirm.

### Boundaries

- **FR-023**: The worklist MUST render completely, with every figure present, when the model provider is unreachable.
- **FR-032**: The obligations expressed as visual relationships -- FR-009's subordination, FR-019's visibility without interaction, FR-026's on-screen enumeration, and FR-027's cap -- MUST be expressed as a presentation contract that automated tests assert: named primary and secondary regions, the four comparison quantities in the primary region in a reading order that is stated rather than assumed -- identity, need-by date, miss probability, quantile pair, and the same order in the rendered document and in the accessibility tree's traversal, so a coordinator hearing the row and one seeing it meet it in the same sequence -- explanatory context in the secondary region at a **smaller** type scale than the primary region's and never a heavier weight, since "distinct" without a direction is satisfied by a secondary region set larger than the primary and would invert the very subordination FR-009 asks for, the offered sort keys being exactly FR-026's four with none ordering lines by a single delivery date or one quantile alone, the as-of date as row text reachable without hover or expansion, and adjustment acknowledgement as a persistent inline status in a live region rather than a timed notification. Several success criteria rest on these words, so they cannot remain a matter of judgment. "Automated tests assert" obliges execution, not existence: the assertions MUST run and pass in the merge gate under FR-040, and a presentation-contract test that is committed but collected by no workflow step asserts nothing. The contract splits across tiers so the obligation does not rest on the rendered page alone -- the offered sort keys, the four comparison quantities and the primary/secondary partition are assertable against the endpoint's response, and only the rendered relationships (type scale, reading order, the as-of date reachable without hover, the live region) require a rendered page. Each tier's subject is named so an assertion is never left without one: the response tier's subject is the endpoint's payload, and the rendered tier's is the rendered document together with the accessibility tree computed from it.
  Two further wordings join the contract because they are otherwise words of judgment, and FR-032's list did not previously reach them. FR-015's "plainly" is a page-scope banner carrying that state's committed copy under FR-044, present before any row content in the reading order, and never discharged by the absence of figures alone. FR-031's "visibly marked as unsaved" is a text mark on the adjusted need-by quantity itself, adjacent to the date it qualifies and present in the accessibility tree under FR-050 -- not a row tint, and not a mark parked elsewhere on the row where it no longer says which value is the what-if.
- **FR-048**: A line's position in the ordering MUST reach a coordinator who is not reading the page visually. Each ranked row MUST carry its one-based position as text within the row, and the ranked group MUST be exposed with a semantic that states both that it is ordered and how many entries it holds, so position is never carried by vertical placement alone. This is not a refinement of SC-001 but the condition on it being true at all: the criterion is phrased visually, the ranking quantity is deliberately absent from the row under FR-041, and position read off the screen's geometry carries nothing to a screen reader -- which leaves the ordering, the product's entire output, conveyed by nothing. The stated position is the position under the active key, never a harm rank retained from a different ordering, so a row never asserts two orderings at once.
- **FR-049**: FR-004's single labelled pair MUST be one labelled unit in the accessibility tree as well as visually: the median, the eightieth percentile, their shared anchor to the as-of date, and their FR-005 labelling MUST be reachable under one accessible name, and the two figures MUST NOT be exposed as adjacent unrelated numbers. A linearised reading of two bare numbers is exactly the independent-quantile reading FR-004 removes, and it reissues the invitation to treat one of them alone as the answer -- with no sort control needed to do it.
- **FR-050**: A row's resolved degraded state and FR-031's unsaved mark MUST each be carried by text present in the accessibility tree. Colour, position, an icon with no accessible name, or the mere absence of a figure MUST NOT be the sole carrier of either. A state carried only by colour is invisible to a coordinator who cannot see it and to every automated check of SC-009's wording obligation, which asserts over wording and finds none; and an unsaved mark carried only by a tint makes a session what-if indistinguishable from the record, which is the single confusion FR-031 exists to prevent.
- **FR-051**: The need-by adjustment, the sort control and the scoping control MUST each be operable by keyboard alone, reachable in the order FR-032 fixes, and MUST expose their current value -- the adjusted date, the active sort key and direction, the active scope -- to assistive technology rather than by visual state alone. FR-008's bounded forms MUST be announced as words, "less than one percent" and "greater than ninety-nine percent": the `<` and `>` glyphs are read inconsistently or dropped outright, and a dropped `<` turns `<1%` into a flat `1%`, which is a false precision of exactly the kind FR-008 exists to remove. FR-012's live region was this specification's only accessibility obligation, and a live region on a surface no one can reach by keyboard announces changes to a coordinator who could not have made them.
- **FR-024**: The worklist MUST obtain its data through the request-serving boundary, observable in that the interface tier opens no datastore connection. Inherited from the epic's constraints and the architecture's primary flow.
- **FR-028**: The system MUST NOT persist changes to a line's criticality; E017 owns that capability.
- **FR-031**: An adjusted need-by date MUST be a local what-if scoped to the coordinator's session. It MUST NOT be written to the purchase-order line, MUST reset on reload, and the adjusted row MUST be visibly marked as unsaved. The worklist therefore exposes no write path, which keeps this feature read-only across FR-024's boundary and leaves a generated field unmutated by a feature that states no provenance obligations. FR-020a's "coordinator action" means an adjustment of this kind and nothing persisted.
  More than one adjustment may be in force at once, each scoped to its own line and at most one per line. A what-if confined to a single line could not answer the question the coordinator actually asks -- what the list looks like once two competing dates have both moved -- and FR-020a already admits the *set* of them as one of its inputs. FR-055 bounds the set and states what happens to an adjustment outside the bound.
  **Session** is defined here in the only terms this feature has, because it establishes no identity of its own (FR-056): the session is exactly the set of adjustments the interface holds and replays on each request until reload. It is carried by the request rather than stored anywhere, and two coordinators are distinct because their requests carry different sets and for no other reason. Two consequences follow and are stated rather than left to a cache directive. A response computed under one adjustment set MUST NOT be served to a request carrying a different one; and because the set lives only in the interface, "resets on reload" is a property of where it is kept rather than an expiry someone has to implement.
- **FR-034**: Every success criterion phrased as a coordinator capability MUST name the observable that discharges it. The recorded risk is that no user is available to validate this surface, so a capability nobody can observe is checked by nobody. SC-001 is discharged by the first element of the ranked sequence being the maximum-harm line under the default key, carrying rank 1, and reachable without expanding or opening anything. SC-004 is discharged by the criticality and the calendar margin that produced a line's position being present within the same row element as its figures, in the subordinate region FR-032 names, alongside the quantile pair in the primary region that summarises the third input FR-009 names -- the three together being the whole decomposition rather than part of it. SC-008 is discharged by the line appearing in the excluded group with its identity and need-by date and being absent from the ranked sequence under every offered sort key. Each observable is a property of the delivered surface rather than a report of what a coordinator managed to do.
- **FR-035**: The read path MUST be structurally incapable of reaching the model provider, and the incapacity MUST be enforced rather than observed. No module serving the worklist may import the provider client or the gateway that wraps it, enforced by the project's import contract so that a later edit introducing a call fails the build; and a worklist request, including one carrying a need-by adjustment, MUST add no row to the model-invocation record. FR-023 and SC-003 rest on this rather than the other way round: with no provider call on the path, an unreachable provider is indistinguishable from a reachable one, so rendering under an unreachable provider is a state no implementation can fail, and the import contract is the part that can.
- **FR-036**: Acceptance evidence for every populated state MUST run against one committed frozen forecast fixture, and that fixture MUST carry a line realising each boundary case this specification names, with one named test per case: a median equal to the eightieth percentile on a near-degenerate posterior; two lines tied exactly on expected harm; a line with no posterior in the active run; a line whose roster hash is a well-formed digest differing from the run's; a need-by date equal to the as-of date and one earlier than it; a need-by date strictly between the as-of date and today; a need-by date on the last in-grid day of the horizon and one the day after it; a residual tail mass that rounds to an extreme at whole percent; a miss probability sitting exactly on a half-percent rounding boundary in each direction; an adjustment that changes no ordering; and an active run whose age equals the staleness threshold exactly alongside one that exceeds it. A boundary case with no fixture line behind it is untested however many tests run.
- **FR-037**: The frozen fixture MUST be loadable only through the committed schema, so that no test can exercise a state the storage layer forbids: draws ascending, non-negative, and of length `draw_count`; a survival array of exactly `horizon_days` entries, non-increasing and within [0,1]; and a residual tail mass equal to the array's last entry within the recorded tolerance. It MUST also carry its own provenance, because it is synthetic data committed to the repository: the identity of the generator that produced it, the seed, the generation date, and the command that regenerates it byte-identically. It is a test fixture rather than a corpus document or a published dataset, so it takes generator provenance and MUST NOT carry retrieval provenance it does not have.
- **FR-038**: "Today", as the Glossary defines it, MUST be an input supplied to the read path rather than a clock read taken inside it, and the value supplied MUST be the value the response reports. FR-029's run age, FR-030's calendar-passed flag and the staleness banner are all functions of it, so a fixture stated in absolute dates renders different states as wall-clock time advances and an acceptance run that passed once fails later with no change to the code or the data. Injecting it is also what keeps the date the figures were computed against and the date the coordinator is shown from being two separate reads of one clock. The zone that fixes the date MUST travel with it, so the reported date is auditable rather than asserted: a bare date states which day the server believes it is and nothing about the rule that produced it, and the rule is the whole content of the Glossary's definition. No consumer of this surface may derive a date-dependent state -- staleness, calendar-passed, already late, or a run's age -- from a clock of its own. The supplied date and every state computed from it belong to the response; a second clock in the interface tier is how one line comes to carry two states at once, which is the outcome the Glossary's single configured zone exists to exclude.
- **FR-039**: The deterministic computation this feature adds -- the harm score and the ordering, and the rounding, bounded forms and complement of a probability -- MUST be developed test-first, with the failing test written before the function, and MUST carry property-based tests over its pure functions. This is the project's standing obligation for deterministic computation modules, carried here as a requirement because a plan hint gates nothing. FR-013 and FR-013a are the properties. Their generated inputs MUST be drawn from the domain the storage layer can actually produce -- survival arrays non-increasing and within [0,1] at length `horizon_days`, draws ascending and non-negative at length `draw_count`, criticality an integer from 1 to 5 -- so that a property is never reported as falsified by an input no stored artifact could hold.
- **FR-040**: A requirement or criterion of this feature counts as met only when the check evidencing it executes in the merge gate. A committed test that no workflow step collects evidences nothing, and as the workflow stands neither of the two tiers this feature adds is collected: the serving boundary's unit, property, integration and benchmark tests have no step, and the rendered-page tests carrying FR-032 have neither a script nor a step. Both MUST land with the code they check. The project's 80% coverage target applies to the code this feature adds on both sides of the request-serving boundary, which the gate's current source list measures on neither side; extending it is part of the same obligation, since a coverage figure that excludes this feature's code is a statement about other epics.
- **FR-056**: The worklist inherits the registered scope decision that this system has no authentication (`specs/sad.md` § Security, recorded there as a deliberate scope decision and carried in the product document with its reversal condition and production-scale alternative). It therefore defines no authentication scheme, no coordinator identity, and no per-reader visibility rule: every reader who can reach the deployment reads the same worklist, and a response is scoped by FR-025's project filter and FR-031's adjustment set and by nothing whatever about who is asking. This is stated rather than inherited silently because the surface is the product's primary one, and an unstated authorisation obligation is the kind a later reader supplies from habit and then implements against. It is also where a reversal would land: were authentication introduced project-wide, FR-025's scope and FR-031's session are the two clauses that would gain an actor, and neither has one today.
- **FR-057**: The response contract this feature establishes is read-only for later epics in the same sense the registered project plan makes the interface shell read-only, and the rule binds the payload and not only the layout. The project plan records E012, E017 and E019 as consumers of this surface. An epic extending it MUST satisfy the constraints stated here rather than re-deciding them -- FR-027's closed content classes, FR-041's prohibition on a derivable delivery date, FR-053's withholding rules, and FR-007's enumeration, which binds every surface later added -- and MUST land its change together with every consumer the project plan records for this surface, under the change rule the plan states. The shell convention was written about routing and layout, but a later epic adding a member to a closed response object changes the contract every other consumer validates against exactly as surely as one moving the navigation, and the payload is where this feature's honesty rules actually live.

## Assumptions & Risks

### Assumptions

- Ranking by expected schedule harm serves the coordinator's real decision. The product document records this as assumed rather than user-validated, and this feature inherits that assumption unchanged.
- Criticality, declared as an ordinal band from 1 to 5, is treated as a ratio-scaled weight by FR-001's multiplication. This is a modelling choice, not a property of the data, and a different weighting would produce a different order.
- A coordinator reading this screen has the authority to act on it, so a ranking changes behaviour rather than merely informing.
- The active forecast run covers most open lines most of the time, so the not-covered group is an exception rather than the common case.
- Roughly two hundred lines is the working scale, so ordering and filtering need no pagination strategy to remain responsive.
- Responsiveness is governed by the registered technical context, which sets a worklist p95 of 1.5 seconds on one shared vCPU. This specification states no separate figure; the plan adopts that one rather than choosing its own, since a looser self-chosen target would be a retroactive adjustment. SC-017 and SC-018 are what make it gating, and the conditions under which it is measured are recorded in the plan so two runs of the same check are comparable.
- Until E007 lands there is no active forecast run, so the no-forecast state is the only one with real data behind it and every populated state is demonstrable only against the frozen fixture FR-036 and FR-037 govern. The fixture is therefore acceptance evidence rather than a convenience: until forecasts exist, a defect in it is indistinguishable from a defect in the surface, which is why its boundary coverage, its schema validity and its provenance are stated as requirements rather than left to the test author.

### Risks

- **Harm definition unvalidated** *(likelihood: medium, impact: high)*: the expected-harm definition may not match what coordinators optimise for, and no user is available to validate it. FR-009's per-row decomposition is the mitigation — a wrong ranking is at least visibly wrong.
- **Row density** *(likelihood: medium, impact: medium)*: two quantiles plus a probability may exceed what is scannable, pushing the coordinator back to sorting on one number. FR-004, FR-026 and FR-027 constrain the row against this.
- **Upstream contract defect** *(likelihood: high, impact: high)*: the lateness formula this feature consumes is inverted in E003's data model — see Stress-Test Findings. Implementing against it as written would rank the safest lines first.

## Clarifications

### Session 2026-07-28

- Q: When two degraded states apply to one line, which wording wins? -> A: A total precedence order, trust-compromising first — roster mismatch, not covered, already late, beyond horizon, calendar-passed — with exactly one row label per line. The three page-scope states render as banners that compose with the row label. Recorded as FR-018a; keeps SC-009's "distinguishable by wording alone" true as written.
- Q: Does an already-late line stay in the ranking, and does it still show its quantile pair? -> A: Both. "Already late" replaces only the miss probability, which is 1 by construction and therefore uninformative; the harm score and quantiles are well defined and say how much further slip is coming. The calendar margin renders negative. Recorded in FR-030 and FR-009.
- Q: Does an adjusted need-by date persist to the record, or is it a local what-if? -> A: A local what-if scoped to the session, resetting on reload and visibly marked unsaved. The worklist exposes no write path, keeping the feature read-only across the request-serving boundary. Recorded in FR-031; resolves the specification's only clarification marker.
- Q: What is FR-010's tiebreak rule? -> A: Need-by date ascending, then criticality descending, then line identifier ascending as the uniqueness terminator. Not an edge case — expected harm is exactly zero for every comfortably-early line, so this rule orders that whole block.
- Q: What is the staleness threshold, and which date defines a run's age? -> A: Seven days, measured as today minus the run's as-of date. The as-of date because FR-019 already displays it, so a coordinator can verify the staleness claim from the screen; the recorded basis is one refit cadence. Recorded in FR-029.
- Q: What display precision triggers FR-008's bounded form? -> A: Whole percent, with `<1%` and `>99%` as the bounded forms, and the complement of a bounded value itself rendered as a bound. Several thousand draws do not support a finer figure, and an unbounded complement would reintroduce the certainty FR-008 removes.
- Q: How do the requirements phrased as visual relationships become observable? -> A: A presentation contract the plan defines and automated tests assert — named primary and secondary regions, the four comparison quantities in reading order, context excluded from the sort-key set, the as-of date reachable without hover, and adjustment acknowledgement as a persistent inline live region rather than a timed notification. Recorded as FR-032 and in FR-012.
- Q: Which sort keys are offered? -> A: Exactly four — expected harm descending as the default, need-by date, criticality, and calendar margin. The probability of missing is excluded despite passing FR-007's stated exclusions, because ordering the whole list by one probability discards criticality. Recorded in FR-026.

## Stress-Test Findings

### Session 2026-07-28

- STF-001: Cross-Artifact Contradiction (CRITICAL) — Affected: FR-013, FR-017, SC-006, US2, E003 data-model.md:418 — E003 defines `survival[k]` as `P(delivery has not occurred by end of day as_of_date + k)` and `residual_tail_mass` as `P(T > horizon_days)`, both survival-function semantics. Its derived row then gives probability of lateness as `1 - survival[d - as_of_date]`, which computes the probability of arriving **on time**. The correct expression is `survival[d - as_of_date]` with no complement. The same inversion appears in the beyond-horizon clamp, where `1 - residual_tail_mass` should be `residual_tail_mass` as an upper bound. Implementing as written inverts the worklist, ranking the safest lines first, and falsifies FR-013 — moving a need-by date earlier would *decrease* the displayed probability. **Resolved 2026-07-28** — corrected upstream in E003 at `data-model.md:418`, `data-model.md:721` (TR-053) and `plan.md:207`. The defect has not reached code: the migration's own comment states the correct semantics. E010 cannot override it locally, because a plan-phase artifact is normative over a specify-phase requirement. FR-013 and FR-017 were blocked on this and are now unblocked: `data-model.md:418` reads `survival[d - as_of_date]` with no complement, `data-model.md:721` and `plan.md:207` state the beyond-horizon answer as bounded above by `residual_tail_mass`, and E003's 1293 schema tests pass unchanged — confirming the defect was confined to prose and never reached the migration.

## Glossary

| Term | Definition |
|---|---|
| Open purchase-order line | A line whose lifecycle state is not terminal — it has not been delivered and remains something the coordinator can act on. |
| Expected schedule harm | The mean delivery overrun past the need-by date across a line's stored draws, counting zero where a draw arrives on time, multiplied by criticality. The ranking quantity. |
| Active forecast run | The one forecast run marked active. At most one exists at a time, and all displayed figures come from it. |
| Draw | One sampled delivery duration from a line's posterior, measured in days from the run's as-of date. Each line stores several thousand, sorted ascending. |
| Survival array | Per line and per day of the horizon, the probability that delivery has not yet occurred by that day. The probability of missing a need-by date is read from it directly. |
| Residual tail mass | The probability still unresolved at the end of the forecast horizon, and an upper bound on the miss probability for a need-by date beyond it. |
| Criticality | A line's consequence weight from 1 to 5, where 5 is most critical. |
| Not covered | A line with no posterior in the active forecast run, typically because it was created after the run was fitted. |
| Today | The request-time date in a single stated time zone, fixed by configuration rather than taken from the viewer's device. FR-018, FR-029 and FR-030 all depend on it, and a per-viewer clock would let the same run be stale for one coordinator and current for another, making the state labels irreproducible. |
| As-of date | The date the active forecast run was fitted, against which probabilities of missing a need-by date are evaluated. |
| Calendar margin | Whole days from the active run's as-of date to a line's need-by date. Takes no forecast input, so it cannot be combined with a displayed figure to reconstruct a predicted delivery date. Distinct from E005's generator-side *slack* and the product document's *float*, which this specification does not use. |
| Comparison quantity | A quantity carried in the primary region FR-032 names — an observable property of the row rather than a presumption about what a coordinator scans, so two reviewers counting one row reach the same total. Distinct from explanatory context, which sits in the secondary region, and from row status. FR-027 caps the first class at four and closes the second at three and the third at three. |
| Row status | The marks a row carries that are neither comparison quantities nor explanatory context: its position in the ordering, its resolved degraded-state label, and FR-031's unsaved mark. None is a figure read from the forecast; none counts against FR-027's cap; the class is closed at those three, and a row carries whichever of them apply to it. |
| Reference class | The population a displayed quantile is a proportion of: comparable orders, the class the line's posterior was fitted over. Stated in those terms on screen rather than as the artifact the figure was computed from, because a single-event figure with no stated reference class is read in mutually contradictory ways. The covariates conditioning a particular line's forecast are E012's to show, not this feature's. |
| Line identifier | A line's stable generated key, unique by construction. Distinct from its human-readable identity — project, purchase order, line number, description — which is what the row displays. FR-010 uses the key as the tiebreak terminator, and the two order differently. |
