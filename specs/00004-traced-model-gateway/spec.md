## Problem Statement

E001 established a seam — one module permitted to import the model provider — and deliberately left it empty. Every obligation that seam exists to carry is still unbuilt: no call is traced, no output is validated, no cost is recorded, and nothing makes a model-dependent result reproducible without a credential and a network. Four later epics (E006, E011, E013, E014) are blocked on that path existing, and the project's two loudest published claims — one hundred percent of model calls traced, one hundred percent of model outputs schema-validated — are currently prose with nothing behind them. Building the traced path after call sites exist is far harder than building it before any exist, so it has to land now, while there are still zero callers to migrate.

## Scope

### Included

- The single module that constructs and calls the model-provider client, with a public surface built from gateway-owned types so no provider type crosses the boundary
- Schema-validated model output with at most one repair attempt, then fail closed
- An `llm_invocation` record written by the gateway itself on every attempt, carrying model identity, token counts, latency, cost, price-table version, and a validation outcome
- A versioned price table and a deterministic cost function, so a stored cost is recomputable from stored token counts
- A build-time computation-boundary contract over the gateway entry, converting the arithmetic-placement convention into a failure
- Content-hash response fixtures with record and replay modes, where replay reaches no network and requires no credential
- Credential redaction and provider-error normalization inside the boundary
- This epic's own schema changes, authored as Alembic revisions in the reserved `0100`–`0199` prefix block inside the arrangement E003 owns in `/src/model` ({SAD:ADR-0013}); no runner or migration tooling of this epic's own

### Excluded

- Any prompt, schema, or extraction logic for a specific task — the gateway carries the mechanism; E006 (extraction) and E011 (chat) bring their own schemas
- The invocation panel that surfaces these records in the interface — owned by E013
- Streaming responses — no consumer in this project needs partial output, and streaming complicates both hashing and token accounting
- Batch and long-lived-cache request modes — the price table accounts for their rates so cost stays correct if they appear, but no call path submits them here
- Retries, backoff, or rate-limit orchestration beyond a bounded transport retry — no production traffic exists to tune against
- Any table other than the invocation record and the price table — E003 owns the rest of the schema
- Span, metric, and collector-exported telemetry — the invocation record is this epic's only telemetry sink, and the OpenTelemetry convention supplies field *names* here rather than a pipeline (TR-075); span and parent-span identifiers are deliberately absent from the record
- The side-by-side publication of replayed and live numbers — E004 supplies both modes and the record; E014 owns the comparison and its disclosure (IP-009)

### Edge Cases & Boundaries

- Model returns syntactically valid JSON that fails a numeric bound or string-length validator — the case constrained decoding does not cover, and where the single repair attempt is actually spent
- Repair returns output that fails validation again, or fails identically — record `failed`, raise, store no value
- Transport failure (rate limit, server error) — consumes the transport retry budget, never the repair budget, and is never recorded as `repaired`
- Replay mode with no matching fixture — an error, never a live call
- Replay mode with a credential present in the environment — an error, so an offline claim cannot be quietly satisfied by a live call
- Prompt, schema, schema version, or sampling parameter changes — the content hash changes with it, so a stale fixture surfaces as a miss rather than a wrong replay
- Provider resolves the requested model name to a different model identifier — both are recorded
- No price row covers the resolved model at the invocation time — cost is recorded as absent with its reason, never as zero or a guess
- Opted-in `record` mode with no credential configured — fails before any request is constructed, with a message that names no secret material
- Two invocations run concurrently — each writes its own record; neither can observe a partial write from the other
- The database is unreachable when the record is written — the record goes to the local spool and the invocation still fails closed, so a billed call is never left with no record anywhere
- A caller's own transaction rolls back after the gateway returns — the record survives, because the gateway committed it independently
- The provider accepts the request and never responds — the per-request deadline expires and the expiry counts as a transport failure

## Technical Objectives

### Objective 1 - Provider-Type-Free Traced Invocation Path (Priority: P1)

One module constructs the provider client and issues every request. Its public surface — arguments, return value, and error type — is built entirely from gateway-owned types, so a consumer can be compiled and tested with no provider package installed. E001's placeholder `client_type()` seam is replaced by a real invocation entry point.

**Why this priority**: Every other objective in this spec attaches to this path, and four downstream epics are blocked until it exists.

**Rationale**: The import contract constrains imports only. A gateway that accepts or returns provider SDK objects satisfies every existing check while still coupling both Python boundaries to the provider, which is precisely the coupling {SAD:ADR-0010} restructured the source layout to prevent.

**Deliverables**:

- Invocation entry point in `src/gateway`, taking a gateway-owned request and returning a gateway-owned validated result
- Gateway-owned error type covering provider, validation, and configuration failures
- Extension of E001's import contract and single-naming-site check to cover the enlarged package
- Extension of the computation-boundary contract to the gateway entry, so the provider-facing module cannot reach the arithmetic modules; an orchestration module above both composes the call, the validation, the computation, and the record
- Provider SDK moved from a hard runtime dependency to an optional extra of the gateway manifest, imported lazily inside the invocation entry so the public surface imports with the extra uninstalled
- Removal of E001's placeholder client-type accessor

**Validation Criteria**:

1. **Given** an environment with the gateway installed *without* its provider extra, **When** a consumer imports the gateway's public surface and type-checks against it, **Then** it resolves and type-checks with no provider package present anywhere in the environment
2. **Given** a change that adds a provider import to any module other than the designated one, **When** the checks run, **Then** the import contract named for the provider client reports the violation and fails, distinct from any lint or type failure the same change may also produce
3. **Given** a change that returns or re-exports a provider SDK type from the gateway's public surface, **When** the checks run, **Then** the public-surface check reports the leaked type by name and fails
4. **Given** a change that imports a gateway arithmetic module from the provider-facing module, directly or through an intermediate module, **When** the checks run, **Then** the computation-boundary contract reports the violation and fails
5. **Given** the released gateway public surface, **When** it is enumerated, **Then** E001's placeholder client-type accessor is absent and exactly one invocation entry point is present

### Objective 2 - Schema-Validated Output with Bounded Repair (Priority: P1)

Every model output is validated against a caller-supplied schema before it is returned. A failure triggers exactly one repair attempt carrying the validation error back to the model. A second failure records the outcome and raises, so no unvalidated value can reach a caller, storage, or the interface.

**Why this priority**: "No unvalidated value reaches storage or interface" is a published product target and a governing constraint on this epic; the gateway is the only place it can be enforced structurally.

**Rationale**: Constrained decoding guarantees JSON syntax, required fields, and types, but not numeric bounds, string length, or pattern — exactly the constraints this domain uses for confidence scores and page numbers. Those live in validators, so a validation failure path is required rather than theoretical. Repair is capped at one because self-repair gains are modest and an uninformative retry entrenches the same error.

**Deliverables**:

- Schema submission using the provider's native structured-output mode, with domain constraints expressed as validators rather than schema keywords
- Single repair attempt that re-prompts with the validation error path and message
- Outcome classification over `valid`, `repaired`, `failed`, separated from the transport retry budget
- Per-request deadline from gateway configuration, with expiry counted as a transport failure rather than a repair
- Fail-closed error raised to the caller after the failure is recorded

**Validation Criteria**:

1. **Given** a fixture whose response violates a validator on first attempt and satisfies it on repair, **When** the gateway is invoked, **Then** the caller receives the validated value, the record shows `repaired`, and the repair request carries the failing field path and validation message
2. **Given** a fixture whose response fails validation twice with no transport failure, **When** the gateway is invoked, **Then** exactly two model requests are issued, the record shows `failed` with a repair attempt count of 1, and a gateway error is raised
3. **Given** a transport failure followed by a valid response, **When** the gateway is invoked, **Then** the record shows `valid`, the transport attempt count is 2, and the repair attempt count is 0
4. **Given** a schema carrying a constraint the provider's structured-output mode does not support, **When** a request is built, **Then** the constraint is applied as a post-decode validator and the submitted schema contains no unsupported keyword
5. **Given** three transport failures in succession, **When** the gateway is invoked, **Then** it stops at the third attempt and raises rather than continuing

### Objective 3 - Invocation Record with Recomputable Cost (Priority: P1)

The gateway writes exactly one `llm_invocation` row per invocation — not per attempt — unconditionally and without caller cooperation, in `replay` mode as well as `record`. Each row carries requested and resolved model identity, resolution mode, fixture key where one applies, token counts summed across every attempt, total wall-clock latency, computed cost, the price-table version used, and the validation outcome. A versioned price table and a deterministic cost function make any historical cost recomputable from the stored counts.

**Why this priority**: The one-hundred-percent tracing claim and the E013 invocation panel both read this table; without it the epic produces an untraced path, which is the state E001 already left behind.

**Rationale**: Storing only a derived cost makes the figure unauditable the moment pricing changes, and pricing does change on a date within this project's horizon. Cost is a multi-term function over billing classes whose token counts are reported separately, so it is deterministic testable code and a property-based-test target, never a constant. Recording is a property of the boundary rather than a caller's responsibility, per {SAD:ADR-0007}.

**Deliverables**:

- This epic's schema changes as Alembic revisions in the reserved `0100`–`0199` prefix block, authored into the arrangement E003 owns in `/src/model` ({SAD:ADR-0013}); no runner, configuration, or migration tooling of this epic's own
- `llm_invocation` table, price-table version and entry tables, and their seed data
- Pure cost function over token counts by billing class, resolved model identifier, price-table version, and pricing timestamp, with property-based tests
- Deterministic price lookup resolving within the pinned version to the entry whose effective-from date is the latest at or before the pricing timestamp, which is the creation timestamp in `record` mode and the fixture's recording date in `replay`
- Gateway-owned database connection, opened from the gateway's own configuration and committing each record in a transaction independent of any caller's
- Local append-only spool holding records whose database write failed after a provider request was issued, with reconciliation on the next successful connection
- Field names aligned to the OpenTelemetry generative-AI semantic conventions, with the convention version pinned and recorded

**Validation Criteria**:

1. **Given** an empty database, **When** E003's runner applies this epic's revisions, **Then** the invocation and price tables exist, and after a second run the revision ledger and the information schema are identical to their state after the first — the postcondition TR-050 requires, not the runner's exit code
2. **Given** any completed invocation, **When** its stored token counts, resolved model identifier, price-table version, and pricing timestamp are fed to the cost function, **Then** the result equals the stored cost
3. **Given** an invocation whose resolved model has no price row effective at its timestamp, **When** the record is written, **Then** cost is absent with a recorded reason rather than zero
4. **Given** an invocation that fails validation twice, **When** the record is written, **Then** exactly one row exists with outcome `failed`, its token counts summed across both attempts, its latency covering both, and its attempt counts populated
5. **Given** a caller supplying a trace identifier, **When** the record is written, **Then** the row carries that identifier; **Given** a caller supplying none, **Then** the row carries a generated one and is never null
6. **Given** the applied migration set, **When** migration numbers are enumerated, **Then** every number this epic applies falls within `0100`–`0199`
7. **Given** the stored field names, **When** they are compared against the pinned OpenTelemetry generative-AI convention version recorded in configuration, **Then** every conventionally-named field matches that version's spelling
8. **Given** a written row from a successful invocation, **When** it is read back, **Then** requested model, resolved response model, provider name, operation name, creation timestamp, trace identifier, token counts, latency, attempt counts, price-table version, and outcome are all present and non-null; cost is conditional per TR-048's closed reason set and error type is populated on the failure path
9. **Given** a price-table version, **When** its entries are read, **Then** each carries separate rates for base input, cache write, cache read, and output, and a cost computed from token counts in all four classes reflects each rate independently
10. **Given** a pinned price-table version holding several effective-from entries for one model, **When** an invocation is priced, **Then** the entry chosen is the one whose effective-from is the latest at or before the pricing timestamp *within that pinned version*, and a newer version outside the pin is never consulted
11. **Given** an invocation resolved from a fixture in `replay` mode, **When** the record is written, **Then** one row exists carrying resolution mode `replay` and the fixture key it resolved from, distinguishable from a `record`-mode row without inference
12. **Given** the database is unavailable when the record is written after a provider request was issued, **When** the gateway is invoked, **Then** the record is appended to the local spool, the invocation fails closed, and no validated value is returned
13. **Given** a caller whose own transaction rolls back after the gateway returns, **When** the invocation table is read, **Then** the record is still present, because the gateway committed it in its own transaction
14. **Given** spooled records from a database outage, **When** the next invocation opens a working connection, **Then** every spooled record is reconciled into the invocation table exactly once and the spool is left empty
15. **Given** one fixture replayed twice, on dates falling either side of an effective-from boundary inside the pinned price-table version, **When** each cost is computed, **Then** both equal the same figure, because the pricing timestamp is the fixture's recording date rather than the replay date

### Objective 4 - Content-Hash Fixtures and Offline Replay (Priority: P1)

Responses are cached as fixtures keyed by a hash over a canonical serialization of the entire request. Exactly two modes exist: `record`, the only mode that reaches the provider, which issues the call and writes the fixture; and `replay`, which resolves from fixtures alone. Neither is the default. `replay` reaches no network, requires no credential, and treats a miss as an error.

**Why this priority**: Reproducing published model-dependent numbers from a clean checkout is a release gate, and hosted decoding cannot be pinned by configuration — the fixture is the only available point of determinism.

**Rationale**: Anything omitted from the hash scope becomes a silent stale replay, which is worse than a miss because it is invisible. The schema and its version belong in the key because changing the output format shifts both the grammar and the input token count. A record-on-miss default would let a "no network" claim be satisfied by a live call nobody noticed.

**Deliverables**:

- Canonical request serialization with a documented, closed list of hashed fields
- Gateway-derived schema version and prompt-template version, each a digest over the resolved artifact — the full schema definition including its post-decode validators, and the resolved template text — rather than a caller-declared string
- Content-hash fixture store with a committed layout and redacted request material
- `record` and `replay` modes only, selected by explicit configuration with no default
- `replay`-mode guard asserting no credential is present in the environment

**Validation Criteria**:

1. **Given** replay mode and a committed fixture, **When** the same request is issued twice, **Then** both return identical validated values with no network access and no credential configured
2. **Given** replay mode and a request with no matching fixture, **When** the gateway is invoked, **Then** it raises a miss error and issues no request
3. **Given** a committed fixture, **When** any hashed field of its request changes, **Then** the key changes and the lookup misses
4. **Given** `replay` mode and a credential present in the gateway's own process environment, **When** the gateway is invoked, **Then** it fails before issuing any request; and **Given** a developer machine holding a credential in its ambient shell, **When** the replay check harness runs, **Then** it spawns a child environment with the credential removed and the full offline suite passes
5. **Given** a request carrying a field absent from the closed hashed-field list, **When** the key is derived, **Then** derivation raises rather than hashing a partial request
6. **Given** a configuration naming no mode explicitly, **When** the gateway is invoked, **Then** it fails on the missing selection rather than defaulting to either mode
7. **Given** any committed fixture, **When** its accompanying provenance record is read, **Then** it carries a recording date, resolved model identifier, gateway revision, and token counts
8. **Given** `record` mode selected without the separate opt-in, **When** the gateway is invoked, **Then** it raises on the missing opt-in and issues no request, rather than falling back to `replay`
9. **Given** a post-decode validator is edited without any caller changing a declared version string, **When** the key is derived, **Then** the gateway-derived schema-version digest changes, the key changes, and the stale fixture misses
10. **Given** a prompt template's resolved text is edited, **When** the key is derived, **Then** the gateway-derived template-version digest changes and the stale fixture misses

### Objective 5 - Credential Redaction and Error Normalization (Priority: P1)

The provider credential is redacted by the boundary itself across every egress path in the closed inventory of TR-059 — log output, the gateway's own exception payload including the local frames a traceback renders, the committed fixture store and its provenance sidecars, the local invocation spool, and check output. Provider exceptions are normalized into a gateway-owned error carrying only status, error type, and request identifier, retaining no chained cause that would re-render the provider body (TR-064).

**Why this priority**: Security-critical, and the failure is silent — a credential in a committed fixture or a captured traceback is discovered by someone else, later.

**Rationale**: A redaction filter installed at the logging handler covers one path of five. Variable-capturing tracebacks dump local frames including a client holding the key, provider error bodies can echo request headers, and assertion messages interpolating the client handle leak through check output rather than application logs. Redaction belongs inside the boundary so it is a property of the path rather than each caller's discipline, per {SAD:ADR-0007}.

**Deliverables**:

- Credential read once at client construction, held off any repr'd or serialized object (TR-061)
- Redaction applied to fixture request material before it is written, fail-closed so unredactable material is not written (TR-059)
- Provider exceptions normalized into a gateway-owned error with a bounded field set and no retained chained cause (TR-064)
- A check scanning every sink in the closed egress inventory for credential-shaped material, carrying a seeded positive case per sink (TR-060)

**Validation Criteria**:

1. **Given** a configured credential, **When** the gateway object graph is repr'd, serialized, or captured in a traceback, **Then** no credential material appears
2. **Given** a recorded fixture, **When** the fixture-scan check runs over the committed store, **Then** it finds no credential-shaped material
3. **Given** a provider error whose body echoes request headers, **When** it propagates to the caller, **Then** it is a gateway error carrying only status, error type, and request identifier
4. **Given** default configuration, **When** an invocation is logged, **Then** the log line carries no prompt or completion content, and content capture appears only when explicitly enabled
5. **Given** the full offline suite, **When** every emitted log event is collected, **Then** the set is exactly the five TR-077 closes it at, and no sink among the six TR-076 names carries a seeded prompt or completion marker

### Objective 6 - Provider-Reaching Smoke and Fixture Refresh (Priority: P2)

An explicitly opted-in run in `record` mode exercises the real provider and refreshes fixtures. It never runs in continuous integration and never runs by default.

**Why this priority**: The fixture-replay path is a complete deliverable without it, but a gateway whose live branch is never executed proves only that replay works.

**Rationale**: Continuous integration stays credential-free and offline, matching the posture E001 established. Keeping the provider-reaching path opt-in and documented makes fixture regeneration a deliberate act with a recorded trigger, which is what keeps prompt changes from silently serving old responses.

**Deliverables**:

- Opt-in gate permitting `record` mode, off by default and separate from mode selection
- Documented fixture regeneration procedure naming its trigger conditions
- Smoke check exercising one provider-reaching invocation end to end, skipped when the opt-in gate is absent, and failing before request construction when the gate is present but no credential is configured

**Validation Criteria**:

1. **Given** no explicit opt-in, **When** the full check suite runs, **Then** no provider request is issued and no credential is required
2. **Given** an opted-in `record` run with a credential, **When** the smoke check executes, **Then** one invocation record is written, one fixture is produced, and the response is validated through the same path `replay` uses
3. **Given** an opted-in `record` run with no credential configured, **When** the smoke check executes, **Then** it fails before constructing a request, with a message naming no secret material

### Technical Constraints

- Exactly one source file under `/src` may name the provider distribution; E001's check asserts a count of one at the designated gateway module, and enlarging the package must not raise that count
- The gateway package carries neither a web framework nor the modeling stack. The database driver is the only *base runtime* dependency this epic may add; the provider SDK moves into an optional extra, not resolvable by a consumer that only invokes the gateway ({SAD:ADR-0014}). No migration tooling enters the gateway at all, since {SAD:ADR-0013} places it in `/src/model`
- Neither Python boundary may declare the other as a dependency; both depend on the gateway
- One PostgreSQL 16 instance, no second datastore of record; the fixture store is files on disk, and the invocation spool is a local durable buffer that no consumer queries and whose steady state is empty ({SAD:ADR-0015}, `project-instructions.md` v1.2.1)
- Alembic revision prefixes `0100`–`0199` are reserved for this epic by {SAD:ADR-0013}; `0001`–`0099` belong to E003, which runs in the same wave and owns the runner and configuration
- All cost, hashing, and duration arithmetic lives in pure modules with tests, enforced by the computation-boundary contract rather than convention; none of it lives in the provider-facing module
- Continuous integration runs with no provider credential present and no outbound network to the provider
- The database-backed criteria (OBJ3 VC1–VC4, VC8, VC11–VC15, SC-005, SC-007, SC-018) execute in a continuous-integration job carrying E001's `db` service, not locally only; the replay harness runs there in a credential-free child environment, so the no-credential and database preconditions are satisfied together rather than trading off
- Prompt and completion content capture defaults to off in log output
- Invocation records are retained without bound and are never deleted or aggregated by this epic; this answers the technical context document's open question on `llm_invocation` retention for the demonstration's data volume, and any cap is E013's to propose. The position is a scope decision rather than an omission, and it reverses on a stated condition: if the invocation table exceeds one million rows, or if E013's panel ordering query stops meeting its own latency budget on the `(created_at DESC)` index, the unbounded position is revisited and E013 proposes a cap or an aggregation path. Neither condition is reachable at this project's stated scale of roughly two to five thousand invocations, which is why no deletion path is built here
- Artifact placement, against `ENFORCE_SRC_ROOT` and the narrow repository-root `/tests` exception: this epic's Alembic revisions live in `/src/model` alongside E003's, per {SAD:ADR-0013}; the fixture store root lives inside the gateway entry under `/src/gateway`, since the gateway owns the fixtures; the fixture-scan check (TR-030) lives with them, since it reads only that entry's artifacts; the consumer type-check harness behind OBJ1 VC1 lives under `/tests` at the repository root, because it must construct a synthetic environment installing the gateway *without* its provider extra — an environment no entry can host from its own lockfile, since each entry resolves the extra it needs — so no single entry owns it. The prefix-block and single-head check (TR-051) sits there on a different but equally narrow ground: it asserts the partition *between* E003's `0001`–`0099` claim and E004's `0100`–`0199` claim, so neither epic owns the assertion, and E004 cannot place a test inside `/src/model`, which is E003's entry. It is not entry-local to the gateway, and it is not E004's to add to E003's suite. Entry-local tests must not migrate under this exception

E004 supplies both resolution modes and the invocation record the comparison reads; it does not perform the comparison. Recorded here as a divergence to resolve: the registered project plan does not yet assign this disclosure to E014 or to any other epic, so the assignment is a proposal from this spec rather than a plan fact

## Requirements

### Technical Requirements

- **TR-001**: System MUST route every model-provider request through a single module, and MUST fail the build when any other module under `/src` imports or names the provider distribution.
- **TR-002**: System MUST expose a gateway public surface whose arguments, return values, and errors are gateway-owned types, with no provider SDK type accepted, returned, or re-exported.
- **TR-003**: System MUST declare the provider SDK as an optional extra of the gateway manifest rather than a hard runtime dependency, and MUST import it lazily inside the invocation entry, so the gateway's public surface imports and type-checks in an environment where the extra is not installed and the provider package is absent.
- **TR-004**: System MUST replace E001's placeholder client-type accessor with the invocation entry point, and MUST remove the placeholder rather than leave a second surface.
- **TR-005**: System MUST submit the caller's schema using the provider's native structured-output mode, and MUST express constraints the mode does not support as validators applied after decoding.
- **TR-006**: System MUST validate every model output against the caller's schema before returning it, and MUST NOT return, persist, or log an unvalidated value.
- **TR-007**: System MUST attempt at most one repair after a validation failure, and that repair MUST carry the failing field path and validation message.
- **TR-008**: System MUST raise a gateway error after a second validation failure, and MUST write the invocation record before raising.
- **TR-009**: System MUST classify every invocation as exactly one of `valid`, `repaired`, or `failed`, and MUST NOT classify a transport failure as `repaired`.
- **TR-010**: System MUST bound transport retries at 2 retries (3 transport attempts maximum) per model request, independently of the repair budget, and MUST record the transport attempt count on the invocation record. A request that succeeds on its first transport attempt MUST issue exactly one request.
- **TR-011**: System MUST write exactly one `llm_invocation` row per invocation — never one per attempt — including invocations that fail validation or transport. The denominator is every invocation that resolved from the provider or from a fixture, and a record counts as written whether it lands in the invocation table or, per TR-041, in the spool awaiting reconciliation. Invocations that fail before a request is constructed are outside that denominator, and the excluded set is closed at eight, carried here rather than only in the data model's row-existence precondition: a `replay` miss (TR-022), a credential present in `replay` (TR-023), an absent mode selection (TR-021), `record` mode without its separate opt-in (TR-027, TR-063), `record` mode without a configured credential (TR-062, OBJ6 VC3), an absent provider extra (TR-003), an unresolvable price-table version pin (TR-048), and a caller-supplied trace identifier outside its value domain (TR-047). Seven of the eight fail before any provider request or fixture lookup. The `replay` miss is the exception: it is *detected by* a fixture lookup, which TR-056 counts as one transport attempt, but the lookup returns nothing to record — no provider was reached, no tokens were consumed, and no cost was incurred — so it is excluded on the same ground as the other seven. Nothing is lost by the exclusion in any of the eight cases.
- **TR-012**: System MUST record on each row: a gateway-generated invocation identifier, requested model, resolved response model, operation name, provider name, resolution mode, fixture key where one applies, input tokens, output tokens, cache-write and cache-read token counts, latency, transport attempt count, repair attempt count, computed cost, the reason cost is absent where it is, the pricing timestamp used, price-table version, outcome, trace identifier, creation timestamp, and error type where applicable. This field list is the read contract E013 consumes and MUST be a superset of the fields any other requirement in this spec mandates.
- **TR-013**: System MUST name recorded fields after the OpenTelemetry generative-AI semantic conventions, and MUST pin and record the convention version the naming follows, since those attributes are not yet stable.
- **TR-014**: System MUST compute cost in a pure function over token counts by billing class, the resolved model identifier, the price-table version, and a pricing timestamp, such that recomputation from a stored row reproduces the stored cost exactly.
- **TR-043**: The pricing timestamp MUST be the invocation's creation timestamp in `record` mode and the fixture's recording date in `replay` mode, so replaying one fixture reproduces the same cost regardless of when the replay happens, even across an effective-from boundary inside the pinned version. The value used MUST be recoverable from the stored row.
- **TR-015**: System MUST store price entries keyed by model identifier and an effective-from date, with distinct rates for base input, cache write, cache read, and output.
- **TR-016**: System MUST record cost as absent with a stated reason when the pinned price-table version holds no entry covering the resolved model at or before the pricing timestamp, and MUST NOT substitute zero or a nearest-match rate.
- **TR-017**: System MUST author this epic's schema changes as Alembic revisions inside the arrangement E003 owns in `/src/model` per {SAD:ADR-0013}, and MUST NOT introduce a migration runner, Alembic configuration, or migration tooling of its own. The runner's forward-only and apply-from-empty properties are E003's to provide and this epic's to verify against.
- **TR-018**: System MUST confine this epic's revisions to the reserved filename-prefix block `0100`–`0199` assigned to E004 by {SAD:ADR-0013}, leaving `0001`–`0099` to E003, and MUST NOT author a revision whose prefix falls outside that block.
- **TR-019**: System MUST derive a fixture key from a hash over a canonical serialization of the request, covering provider, requested model, system and message content, every sampling parameter, the submitted schema, the gateway-derived schema version, and the gateway-derived prompt-template version.
- **TR-020**: System MUST document the hashed field list as closed, and MUST fail rather than silently ignore a request field absent from that list. TR-019's "every sampling parameter" is a category, not an enumeration, so the closure rule is: the hashed set is every field the gateway's own request model declares, and a provider parameter the model does not declare is not passed through — it fails at request construction rather than being hashed or dropped. Adding a parameter therefore means adding a field, which the check sees.
- **TR-021**: System MUST support exactly two resolution modes — `record`, the only mode that reaches the provider, and `replay`, which resolves from fixtures alone — selected by explicit configuration with no default and no implicit fallback between them.
- **TR-022**: System MUST raise a miss error in replay mode when no fixture matches, and MUST NOT issue a network request in replay mode under any condition.
- **TR-023**: System MUST fail in `replay` mode when a provider credential is present in its own process environment. The replay check harness MUST execute in a child environment with the credential variable explicitly removed, so the guard is satisfied by the harness rather than by the developer's ambient shell, and a machine holding a credential can still run the full offline suite.
- **TR-024**: System MUST redact provider credential material from every sink in the egress inventory TR-059 closes — log output, exception payloads including traceback-rendered local frames, committed fixtures and their provenance sidecars, the local spool, and check output. The three sinks named when this requirement was first written are a subset; TR-059 is authoritative on the set.
- **TR-025**: System MUST normalize provider exceptions into a gateway error exposing only status, error type, and request identifier.
- **TR-026**: System MUST default prompt and completion content capture in log output to off.
- **TR-027**: System MUST gate `record` mode — the only provider-reaching path — behind an explicit opt-in separate from mode selection, and the automated check suite MUST pass in `replay` mode with no credential configured and no provider network access.
- **TR-028**: System MUST keep cost, hashing, and duration arithmetic in modules that do not import the provider client, and MUST cover the cost, hashing, and duration functions with property-based tests.
- **TR-029**: System MUST NOT add a web framework or any modeling-stack package to the gateway package's dependency manifest, in either its base requirements or any extra.
- **TR-030**: System MUST provide a check that scans every sink in TR-059's closed egress inventory for credential-shaped material, as TR-060's two detectors define it, and fails when any is found. TR-060 is authoritative on both the scan scope and the detectors; this requirement establishes that the check exists and gates the build.
- **TR-031**: System MUST accept a trace identifier from the caller, record it on the invocation row under a non-null column constraint, and generate one when the caller supplies none, so a record is never untraceable to the request that caused it.
- **TR-032**: System MUST extend the computation-boundary contract to the gateway entry, forbidding the provider-facing module from reaching the arithmetic modules — cost, content hashing, and duration — with indirect detection enabled, and that contract MUST fail the build on violation.
- **TR-033**: System MUST record, alongside each committed fixture, the recording date, the resolved model identifier, the gateway revision that produced it (the git commit SHA of the recording run), and the reported token counts, so the fixture store is labelled rather than anonymous generated data.
- **TR-034**: System MUST apply a per-request deadline from gateway configuration, defaulting to **120 seconds**, MUST NOT delegate the deadline to the provider SDK's own default, and MUST count an expiry as a transport failure against the TR-010 budget.
- **TR-035**: System MUST open its own database connection from gateway configuration and MUST commit each invocation record in a transaction independent of any caller's, so a caller rollback cannot erase a trace.
- **TR-036**: System MUST fail the invocation closed when the record write fails, returning no validated value, so the 100% recording claim cannot be satisfied by a value that outlived its trace.
- **TR-041**: System MUST persist the invocation record to a local append-only spool under the gateway's own root when the database write fails after a provider request has been issued, and MUST reconcile spooled records into the invocation table on the next successful connection. Spooling MUST NOT suppress the fail-closed behaviour of TR-036 — a billed call is never left with no record anywhere.
- **TR-042**: System MUST classify the *invocation* rather than the attempt: exactly one outcome value is carried per invocation, and no attempt-level outcome value exists anywhere in the schema or in the code. Per-attempt disposition is carried only by the transport and repair attempt counts of TR-012. The division of obligation between this requirement and TR-009 is fixed so the two cannot drift apart under a later edit to one of them: **TR-009** owns *which* values exist and the rule that a transport failure is never `repaired`; **TR-042** owns the *unit* being classified and the non-existence of an attempt-level value; **TR-078** owns the total mapping from terminal state and attempt counts onto TR-009's values. This requirement therefore does not restate the value set — a change to the enumeration is a change to TR-009 alone, propagated to TR-078's mapping and to the E013 contract under TR-069.
- **TR-037**: System MUST write an invocation record in `replay` mode as well as `record` mode, and MUST record the resolution mode and, where one applies, the fixture key the invocation resolved from.
- **TR-038**: System MUST derive the schema version as a digest over the full schema definition including its post-decode validators, and the prompt-template version as a digest over the resolved template text, and MUST NOT accept either as a caller-declared string.
- **TR-039**: System MUST resolve a price entry within the pinned price-table version only, selecting the entry for the resolved model whose effective-from date is the latest at or before the pricing timestamp defined in TR-043, and MUST NOT consult a version outside the pin.
- **TR-040**: Token counts on a row MUST be the sum across every transport and repair attempt of that invocation, and latency MUST be total wall clock across them, so the stored cost is the invocation's total spend rather than its final attempt's.
- **TR-044**: System MUST fix, for every field TR-012 lists, whether it is present on every row or conditionally absent, and MUST state the condition for each conditionally-absent field: resolved response model is absent only when the outcome is `failed`; fixture key is absent only in `record` mode when the invocation failed before a fixture was written; computed cost and the reason cost is absent are mutually exclusive with exactly one present on every row; error type is present exactly when the outcome is `failed`. Every other field TR-012 lists is present on every row. This nullability contract is part of the read contract E013 consumes and MUST be carried by column constraints rather than by writer discipline.
- **TR-045**: System MUST mint the invocation identifier once per invocation, in the gateway process, before the first write is attempted, and MUST reuse that identifier unchanged for the spool copy of TR-041 and for the row it reconciles into. That identifier is the uniqueness key that makes TR-011's "exactly one row per invocation" determinable — a second row describing one invocation is unrepresentable because no second identifier is ever minted for it — and the database MUST NOT generate one by default.
- **TR-046**: System MUST declare the invocation-to-price-version and entry-to-price-version foreign keys with restrictive referential action on update as well as on delete, so a price-table version identifier can neither be deleted nor edited while any row references it. The identifier is a mutable natural key by type and an immutable one by rule; a rate change is a new version (TR-055), never an edited identifier.
- **TR-047**: System MUST fix the trace identifier's value domain as 32 lowercase hexadecimal characters excluding the all-zero value, MUST validate a caller-supplied identifier against that domain at the gateway boundary before any provider request is constructed, and MUST refuse a non-conforming identifier there as a caller argument error rather than at the database after a billed call. A gateway-generated identifier MUST satisfy the same domain.
- **TR-048**: System MUST verify that the pinned price-table version identifier resolves to an existing version before constructing any provider request, and MUST fail as a configuration error at that point when it does not — so an unresolvable pin never reaches the record write, where a non-null foreign key would make it a write failure rather than a recorded absence. The reasons cost may be absent on a written row are therefore closed at exactly three: no covering price entry within the pinned version, an unresolved model, and a computed cost outside the stored range of TR-049.
- **TR-049**: System MUST hold every monetary value in United States dollars — the single currency of this epic, whose replacement or extension requires a visible schema change rather than a reinterpretation of an existing column — storing cost at a decimal scale of 10 and each rate at a decimal scale of 6. System MUST compute cost by summing all four billing-class terms at full decimal precision and quantizing exactly once at the end under round-half-even; per-term quantization is a defect, not a variant. System MUST compare a stored cost with a recomputed cost as exact decimals at the stored scale, with no binary-float intermediate on either the read path or the recompute path, so "reproduces the stored cost exactly" is decidable. A computed cost outside the representable range of the stored scale MUST be recorded as absent with its reason under TR-048 rather than truncated, rounded into range, or stored as a different figure.
- **TR-050**: System MUST verify TR-017's idempotency by an observable postcondition — after a second run, the migration ledger and the database schema are identical to their state after the first — rather than by the runner exiting without error, and MUST additionally write every migration file to be re-runnable on its own, so a lost or reset ledger does not turn a re-run into a hard failure. System MUST NOT mandate a mechanism inside E003's ledger — per-file checksums, or any other bookkeeping, are E003's to choose, and stock Alembic keeps a head revision rather than per-file state. This epic verifies the postcondition against whatever E003's runner provides, which is how forward-only is detected rather than merely asserted. A correction to seeded data is therefore a new higher-numbered migration; editing an applied seed file is a checksum failure, never a silent no-op.
- **TR-051**: System MUST enforce TR-018's block claim in a check over the Alembic revision directory E003 owns, asserting that every revision's filename prefix falls inside one of the declared blocks, that the blocks partition the range without overlap, and that no prefix is duplicated — a partition check over the whole directory rather than a per-file epic lookup, since nothing maps a revision to an owning epic except the prefix itself, that no prefix is duplicated, and that the revision graph resolves to a single head. The revision directory not yet existing MUST be reported as not present and skipped rather than failing the check or being silently dropped, so the `0001`–`0099` half is enforced from the moment E003's arrangement lands and its absence before then is visible rather than assumed.
- **TR-052**: System MUST make the reconcile of TR-041 idempotent on the invocation identifier of TR-045, inserting each spooled record with a conflict action that ignores a primary-key conflict and no other conflict, and MUST delete the spool row only after the invocation-table transaction has committed. The exactly-once property TR-041 and OBJ3 VC14 claim is a property of the *effect* — at most one invocation row per invocation identifier — and not of delivery: a spool row re-inserted after a crash inside the reconcile window is the designed recovery path and MUST NOT be read as a violation. "Append-only" as TR-041 uses it means no spooled row is ever updated in place; a row is inserted once and removed once its record is committed.
- **TR-053**: System MUST drain the spool at the start of every invocation that successfully opens the gateway's database connection, and MUST NOT depend on a timer, thread, or background process, because the gateway is a library with no runtime of its own. When no further invocation occurs after an outage ends, spooled records remain durably spooled until one does — nothing is lost and nothing drains unattended — and spool depth MUST be logged on every spool write and every drain so that condition is visible rather than silent. A drain MUST tolerate a second gateway process draining the same spool concurrently: the local store's own transactions serialize the claims, a duplicate reconcile is absorbed by TR-052's conflict action, and a delete of an already-deleted row is a no-op.
- **TR-054**: A reconcile that fails a referential check MUST retain the spool row, MUST surface as a logged error naming the failing constraint and the invocation identifier, MUST NOT be suppressed by widening TR-052's conflict action, and MUST NOT fail the unrelated invocation whose connection triggered the drain — the drain continues with the remaining rows, since one unreconcilable record must not convert a recovery mechanism into an outage. A spooled payload MUST carry its payload schema version, and a drain encountering a version it does not understand MUST retain that row and surface it the same way rather than read it under a different shape.
- **TR-055**: System MUST NOT update or delete any row of the invocation table or either price table after it is written, and a rate change MUST be a new price-table version rather than an edit to an existing entry, because every historical cost recomputation depends on the entry it was priced against still holding its original values. Enforcement is by convention, code review, and the restrictive referential actions of TR-046; no trigger, rule, or revoked grant is specified, because the gateway connects as the schema owner and could remove any control it applied to itself. This limit MUST be disclosed as uncovered at each of the three disclosure sites — this spec's requirement text, the plan's Complexity Tracking table, and the module docstring of the code carrying the limit — rather than presented as enforced.
- **TR-056**: An attempt that reports no usage — a transport failure returning no response body — MUST contribute zero to each billing class in TR-040's sums, so the sum is defined over every attempt rather than only the reporting ones. The aggregated latency of TR-012 MUST be an integer count of milliseconds taken from a monotonic clock, started when the gateway begins the first attempt and stopped when it reaches the terminal outcome, so validation, retry backoff, and repair-prompt construction fall inside the interval and the record write falls outside it. In `replay` mode the token counts MUST be taken from the fixture's provenance record (TR-033) so a replayed cost is reproducible, while the latency MUST measure the replay execution itself rather than the original recording. A fixture lookup counts as one transport attempt, so the attempt-count lower bound of one holds on `replay` rows without inference from the glossary.
- **TR-057**: The lookup of TR-039 MUST compare the pricing timestamp to an entry's effective-from date as calendar dates in UTC, so the zone deciding which side of a boundary an invocation falls on is stated rather than inherited from a session or host setting. In `replay` mode the fixture's recording date MUST be widened to midnight UTC of that date when stored as the pricing timestamp, so one fixture resolves one entry. Model matching MUST be exact, case-sensitive equality on the resolved model identifier, with no normalization, no prefix match, and no fallback. Determinism MUST rest on uniqueness rather than on ordering: within one price-table version the pair of model identifier and effective-from date MUST be unique, so no tie exists for the lookup to break arbitrarily.
- **TR-058**: System MUST surface a pinned price table that has fallen behind, rather than leaving its only symptom an absent cost: every invocation recorded with cost absent MUST emit a warning naming the pinned version identifier, the resolved model, and the recorded reason, so a pin predating a rate change or predating a newly resolved model is visible when it first bites rather than discovered later in the record.
- **TR-059**: The set of egress sinks TR-024's redaction covers MUST be closed and enumerable at exactly five, so completeness is decidable against a list rather than against reviewer judgement: (1) log output the gateway emits; (2) the gateway's own exception payload, which for this requirement means the exception's message, its attributes, *and* every local frame a variable-capturing traceback renders — including the frame holding the client handle, so the term is not read as message-and-attributes only; (3) the committed fixture store, its per-fixture provenance sidecars (TR-033) included; (4) the local invocation spool file of TR-041; (5) check output, including assertion messages that interpolate the client handle or a raw request, which leak through the check runner rather than through application logging. The provider-echoed error body is deliberately **not** a sixth sink here: it has a different origin (the provider, not the gateway) and a different control (suppression under TR-025 and TR-064, not transformation), and collapsing the two under one sink would let one control stand for both. Redaction MUST be fail-closed: material that cannot be redacted is not written, so an unredactable value produces a refused write rather than a written value someone must later notice. Redaction removes **credential** material only — it is not a content control, and no claim about proprietary or corpus content may rest on it (see TR-067). These obligations are held against OWASP ASVS **5.0.0** chapters V16 (Security Logging and Error Handling), V14 (Data Protection), and V13 (Configuration), pinned at that version because 5.0.0 renumbered exactly those chapters and a bare chapter number reads differently under 4.0.3.
- **TR-060**: System MUST define *credential-shaped material* as a closed pair of detectors derived from the provider credential's actual shape rather than leaving it an undefined term the scan requirement rests on: (a) exact match on the configured credential value, whenever one is present in the environment the scan runs in; and (b) a prefix-anchored pattern over the provider's published key format — `sk-ant-` followed by at least 16 characters drawn from `[A-Za-z0-9_-]`. The implementing task MUST take the prefix from the provider's current documentation and correct this spelling if the two differ, since a detector matching a shape the credential does not have is the failure mode this definition exists to prevent. The scan of TR-030 MUST run both detectors over **every** sink in TR-059's closed inventory — the committed fixture store including each provenance sidecar, captured log output, the normalized error payload, the local spool file, and captured check output — so TR-030 and SC-010 share one denominator rather than two. Each scanned sink MUST carry a negative case: a synthetic, never-live value matching detector (b), seeded into a temporary instance of that sink, which the scan is asserted to report — so a zero-finding result distinguishes a clean sink from a detector that matches nothing. The scan MUST fail the build on any finding outside a seeded case.
- **TR-061**: System MUST read the provider credential exactly once, at client construction, and MUST hold it off every object the gateway reprs, serializes, logs, or spools — the client handle included, which MUST expose no attribute carrying the credential value — so the property is carried at requirement level rather than only as an OBJ5 deliverable and its validation criterion. Credential material MUST NOT enter the committed repository by any path, the fixture store and its provenance sidecars included; this obligation is stated here rather than inherited from E001 without a link, so the committed store has a requirement of its own for TR-060's scan to be checked against. Confidentiality rests on these controls inside the boundary and never on the credential's environment variable, which is a transport readable by every process that inherits it and present in any process dump — it is not a control and no requirement in this spec rests a confidentiality property on it.
- **TR-062**: System MUST read the credential from exactly one configuration key, `ANTHROPIC_API_KEY` — the name the provider SDK itself resolves, chosen so TR-023's guard and the SDK's own resolution cannot disagree — and TR-023's presence check MUST be an exact-name lookup of that key in the gateway's own process environment, treating the key as absent when unset or set to an empty or whitespace-only value and as present for any other value. No prefix match, no case-insensitive match, and no scan of neighbouring names is performed, so the guard has one checkable subject rather than an intent. **Disclosed limit**: the guard observes the gateway's own process environment and nothing else. A credential reaching the provider SDK by another path — an SDK configuration file, a credential passed as an explicit argument, or a platform keychain the SDK consults — is neither observed nor blocked, so `replay` mode's no-credential property is a property of the process environment rather than an unqualified offline claim. This limit MUST be disclosed at each of the three disclosure sites — this spec's requirement text, the plan's Complexity Tracking table, and the module docstring of the code carrying the limit — rather than presented as closed.
- **TR-063**: System MUST carry TR-027's `record`-mode opt-in as one named control with a fixed form — the environment variable `GATEWAY_ALLOW_PROVIDER_CALLS`, permitting `record` mode only when set to `1`, with absence or any other value denying it — so the opt-in is a control a check can assert on rather than an unfixed "separate from mode selection". The control MUST be absent from every continuous-integration environment, and a check MUST assert that absence, so both halves of the CI posture are stated and enforced rather than the credential-free half asserted and the opt-in-free half assumed.
- **TR-064**: System MUST NOT retain the original provider exception on the normalized gateway error of TR-025 — neither as an explicit chained cause nor as an implicit context — because a chained exception re-renders the provider's echoed body in the very traceback the normalization exists to suppress, which would leave TR-025's "only status, error type, and request identifier" true of the error's fields and false of its rendering. Status, error type, and request identifier are extracted from the provider exception before the chain is broken; nothing else survives it. The request identifier MUST be a provider-issued correlation value taken from the provider's response metadata — never an echo of request material — and MUST be omitted rather than substituted when the provider issues none, so the one field carried through cannot itself become a leak path. The `error_type` value recorded on the invocation row MUST be drawn from the closed set of normalized gateway error classes (`validation_failed`, `transport_failed`, `deadline_exceeded`) and MUST NOT be a provider exception's class name or message, so TR-012's field list is bounded by this domain at requirement level rather than only by the data model's column detail.
- **TR-065**: A configuration failure — no mode selected, a missing opt-in, a missing credential, a missing provider extra, or an unresolvable price-table pin — MUST fail before any request is constructed with a message whose content is bounded by a stated exclusion set, so "names no secret material" is a rule a reviewer can return a verdict on rather than a sentiment. The message MUST NOT contain the credential value, nor any substring, truncation, prefix, suffix, hash, or length of it, nor any other value read from the credential configuration key. The message MUST name the configuration key that is missing or unusable — `ANTHROPIC_API_KEY`, `GATEWAY_MODE`, `GATEWAY_ALLOW_PROVIDER_CALLS`, or `GATEWAY_PRICE_TABLE_VERSION` — and MAY name the remedy, because a key's *name* is not secret and naming it is what makes the message actionable. This obligation is carried here as a requirement rather than only by Edge Cases, OBJ6 VC3, and the plan's error table.
- **TR-066**: System MUST fix the fields the gateway writes to log output as a closed list — TR-012's record field set, the spool depth of TR-053, and the absent-cost warning fields of TR-058, and nothing else — so TR-026's and OBJ5 VC4's "carries no prompt or completion content" has an enumerable denominator rather than being a prohibition over an open set. TR-026's default-off content capture is scoped to log output, and that scoping is stated here rather than inferred: the invocation record (TR-012) and the normalized gateway error (TR-025, TR-064) carry no prompt or completion content at any setting of the toggle, because both field sets are closed and neither names one. Committed fixtures deliberately retain prompt and completion content — that is what a fixture is — which is not an exception to the prohibition but a different sink under a different control: fixture request material is redacted for credentials (TR-024, TR-059) and fixture content is bounded by the corpus rule of TR-067, while TR-026 governs log output alone. Where content capture is explicitly enabled, the enabled state MUST NOT be unconstrained: capture remains subject to TR-024 redaction and TR-059's fail-closed rule, MUST NOT be enabled in continuous integration or in any run that writes to the committed repository, and its output MUST NOT be committed.
- **TR-067**: System MUST carry IP-007's sole-egress claim as a requirement rather than as an integration note: the model provider is the only external network destination this epic's code reaches, and the only path reaching it is the provider-facing module in opted-in `record` mode. The claim's **reach** MUST be stated rather than assumed — TR-001's contract constrains import edges, not sockets, so a module that reached the provider without importing the client would satisfy every contract in this spec; that is a disclosed limit with code review as its only guard, not an assumed impossibility. The observation point establishing SC-008's "0 outbound provider requests" MUST be a network guard installed for the whole automated check suite that fails any outbound connection attempt from the check process, so the count is observed rather than inferred from an absence nothing watched. Only corpus material E002 labels public-domain or synthetic may be sent across this boundary, and no proprietary or customer content may cross it; the bound is stated here rather than inherited, because this epic owns the only egress path over which it could be broken.
- **TR-068**: TR-012's field list MUST be **closed** in the sense TR-020 closes the hashed field list, rather than merely enumerated: the fields TR-012 names are exactly the fields the invocation record carries — nothing is recorded on the row outside that list, and no field is added to it, removed from it, or renamed within it without amending TR-012 itself. TR-012's existing superset claim is therefore an equality rather than a lower bound. Closure is what makes the E013 read contract of IP-005 *checkable*: a column present in the schema but absent from TR-012's list is a defect in one of the two, detectable by comparing the two sets rather than by inspection, and MUST fail the build. The same closure covers the two other sets IP-005 names as part of the contract — TR-009's outcome enumeration and TR-048's absent-cost reason set — and the nullability conditions of TR-044, so "the contract" is three closed sets and one condition table rather than an open notion.
- **TR-069**: A change to the E013 read contract MUST follow one stated procedure rather than being made in a migration alone. The changes this covers are: adding, removing, or renaming a field in TR-012's closed list; changing a nullability condition in TR-044; adding or removing a value from TR-009's outcome enumeration or TR-048's absent-cost reason set; and renaming a column under a convention pin bump (TR-074). The procedure is: (1) amend the owning requirement, because the sets are closed at requirement level under TR-068; (2) apply the change in a **new higher-numbered migration**, never by editing an applied file — TR-050's checksum rule refuses that, and it would not migrate existing rows in any case; (3) record the change against IP-005 as a contract change. Steps (1) and (2) suffice for an addition, which is backward-compatible for an existing consumer; a removal or a rename additionally requires **E013's agreement before merge**, because E013 reads the table directly and a removed or renamed column breaks it at query time rather than at build time. A consumer that needs a field the list does not carry MUST raise it as a contract change under this procedure, and MUST NOT read a column outside the list or infer the value from one: a column outside TR-012's list is not part of the contract and carries no compatibility promise.
- **TR-070**: The OpenTelemetry generative-AI semantic-convention version TR-013 requires to be pinned MUST be recorded as a **concrete version**, not named only as a configuration key, so that OBJ3 VC7's comparison has a fixed referent and TR-013 is falsifiable rather than a check against a moving document. The pinned version is **1.37.0**, selected as the version carrying `gen_ai.provider.name` under that spelling — the attribute the data model flags as renamed across recent convention versions — so the classification of TR-071 resolves against one document. **Corrected from 1.36.0 on 2026-07-26 by the implementing task (T026), under the correction duty this requirement states below.** The registry published at tag `v1.36.0` does **not** define `gen_ai.provider.name`; it defines `gen_ai.system`, which `v1.37.0` marks deprecated and replaced by `gen_ai.provider.name`. So 1.36.0 was a pin whose stated selection reason was false of it, and OBJ3 VC7 would have failed against it — which is the pin working as designed rather than an unforeseen problem. 1.37.0 is the *first* release satisfying the criterion, chosen over a later one so the correction changes as little as the evidence requires. The value MUST be recorded in exactly three places that MUST agree, with their agreement asserted by the OBJ3 VC7 check: the gateway configuration key `otel_genai_semconv_version`, the `COMMENT ON TABLE llm_invocation` mirror, and this requirement. The implementing task MUST verify that the pinned version is a published release defining every attribute TR-071 classifies as convention-named, and MUST correct this requirement's version together with that classification if it is not — a pin naming a version that does not define the attributes is precisely the failure the pin exists to prevent, and the same correction duty TR-060 places on the credential prefix applies here.
- **TR-071**: Naming provenance MUST be carried **per field** rather than as one blanket rule, because TR-013 reads as applying to every recorded field while most of TR-012's closed list is gateway-local and no convention attribute covers it. Every field in that list MUST be classified as exactly one of: **convention-named**, meaning the pinned version of TR-070 defines an attribute for it and the column takes that attribute's transformed spelling (TR-073); or **gateway-local**, meaning it does not, and the column encodes this epic's own semantics. A gateway-local column MUST NOT carry the `gen_ai_` prefix, so the prefix is a reliable signal of set membership and neither half of the classification can be satisfied by inspection alone. A field whose provenance is a source **other than** the generative-AI convention MUST name and pin that source individually rather than inherit TR-070's pin silently: `error_type` derives from `error.type` in the OpenTelemetry **general attribute registry shipped with the same 1.37.0 release** (corrected with TR-070's pin on 2026-07-26; verified present and marked *Stable* there, which is what TR-072's Stable classification for this field rests on), and `trace_id` derives from the trace identifier of **W3C Trace Context Level 1** (W3C Recommendation), which is the source of both the 32-lowercase-hex domain and the invalidity of the all-zero value that TR-047 already fixes. The per-field determination lives in `data-model.md` §Field Naming Alignment; OBJ3 VC7 is its enforcement point, and a mismatch on either half fails the build.
- **TR-072**: Each field in TR-012's closed list MUST additionally carry a **stability class**, which is a different property from TR-071's provenance split — provenance records where a name came from, stability records how likely it is to change and what happens when it does. Exactly two classes exist. **Stable**: the spelling changes only through the contract-change procedure of TR-069 — every gateway-local column other than `cache_read_input_tokens`, plus `error_type` and `trace_id`, whose upstream sources carry their own stability guarantees. **Development**: the upstream convention guarantees no attribute-key stability, so a pin bump under TR-074 may rename or reclassify the field — every `gen_ai_`-prefixed column, plus `cache_read_input_tokens`, which is gateway-local today and moves into the convention-named set if the pinned version defines a cached-input-tokens attribute. Recording the class is what makes a pin's blast radius readable *before* a bump rather than after it: a development-class field is one E013 must not hard-code without reading this class first.
- **TR-073**: The attribute-to-column transform MUST be stated as a **forward-only** rule with an injectivity check, because lowercasing and replacing `.` with `_` is not invertible — several convention attributes carry underscores inside their own segments, so `gen_ai.usage.input_tokens` and a hypothetical `gen_ai.usage_input.tokens` transform to one column name. The rule: a column name is derived from an attribute by lowercasing the attribute and replacing every `.` with `_`. The OBJ3 VC7 check MUST apply the transform in that direction only — transforming every attribute the pinned version defines and comparing the results against the column set — and MUST NOT attempt to recover an attribute from a column name. The check MUST additionally fail when two attributes in the pinned version transform to the same column name, so a collision introduced by a pin bump surfaces as a build failure rather than as a silently ambiguous match.
- **TR-074**: A pin bump under TR-070 that renames a field or moves it between TR-071's two classes MUST follow a stated procedure, because the data model's "cheap edit" position holds only while no row exists. (1) The rename is applied in a **new higher-numbered migration** as a column rename, which preserves existing rows; editing the applied `0102` file is refused by TR-050's checksum rule and would not migrate data in any case. (2) The configuration key `otel_genai_semconv_version`, the `COMMENT ON TABLE` mirror, and TR-070's recorded version are updated in the same change, so the three never disagree. (3) TR-071's classification and TR-072's stability class are updated for every field the bump touches. (4) The change is a read-contract change under TR-069 and requires E013's agreement, since a renamed column breaks its queries at query time. A bump that renames nothing requires step (2) alone. No bump may be applied by adding the new column and leaving the old one in place, which would put a field outside TR-012's closed list and violate TR-068.
- **TR-075**: The invocation record MUST be the **only** telemetry this epic emits: the gateway emits no spans, no metrics, and no collector-consumable events, installs no exporter and no context propagator, and takes no dependency on an OpenTelemetry SDK — the convention of TR-013 supplies field *names* here, not a pipeline. Two consequences are stated rather than left to inference. First, the high-cardinality values carry **no** obligation to appear as metric dimensions and none may be added as one without a scope change: the trace identifier and the fixture key are record columns, and the gateway-derived schema and prompt-template digests (TR-019, TR-033, TR-038) are fixture-key inputs and fixture provenance fields rather than columns at all — cardinality that is unremarkable in a row is a defect in a metric. Second, the absence of a span identifier and a parent-span identifier from TR-012's closed list is a **scope decision, not an omission**: the field names follow a span convention because the naming is borrowed, while the record is a table row with no span to identify. Reversal: if a collector is ever introduced, span and parent-span identifiers enter TR-012's list under the change procedure of TR-069.
- **TR-076**: The material this epic deliberately does **not** capture MUST be stated as its own closed obligation rather than inferred from the absence of fields in TR-012's list. The not-captured set is: prompt text, completion text, system-prompt text, credential material, and end-user identity — the last of which no requirement in this spec collects, accepts, or requires, so its absence is a recorded decision rather than a gap. The obligation is stated **per sink**, because the sinks differ and a single global claim would be false at one of them: the **invocation record** carries none of the five at any setting of any toggle, its field list being closed by TR-068; the **spool payload** carries none, its field list being exactly the record's (TR-041); the **normalized gateway error** carries none, its field set being closed at status, error type, and request identifier (TR-025, TR-064); **log output** carries none by default, and only prompt and completion content may ever appear there, only when content capture is explicitly enabled under TR-066, never credential material and never end-user identity; **check output** carries none (TR-059 sink 5, TR-060); and the **committed fixture store** deliberately *does* retain prompt and completion content — that is what a fixture is — while carrying no credential material (TR-024, TR-059, TR-061), no end-user identity, and only corpus material bounded by TR-067. The fixture store is therefore the single sink at which the not-captured position does not hold in full, and it is named as such here so the position is never read as a global claim about the feature.
- **TR-077**: Logging MUST be specified by what it *carries* as well as by what it omits, since TR-026 and TR-066 fix only the omission and a closed field list over an unstated set of events supplies no denominator. The gateway's log event set is closed at five: (1) one invocation-completion line per invocation at its terminal outcome; (2) the absent-cost warning of TR-058; (3) a spool-write line carrying spool depth (TR-053); (4) a drain line carrying spool depth and the number of records reconciled (TR-053); (5) a reconcile-failure line naming the failing constraint (TR-054). The gateway logs no other event, and adding one is an amendment to this list. Every line whose event belongs to a particular invocation — (1), (2), (3), and (5) — MUST carry the invocation identifier of TR-045 as its correlating field, and lines (1) and (2) MUST additionally carry the trace identifier of TR-031, so a line resolves to a row and to the caller's trace without a text search. TR-066's closed field list applies over exactly these five events.
- **TR-078**: The mapping from an invocation's terminal state and attempt counts onto TR-009's three values MUST be **total and exhaustive**, rather than stated only as the negative rule that a transport failure is never `repaired`. An invocation that reached a schema-valid value with `repair_attempt_count = 0` is `valid`, whatever its transport attempt count. An invocation that reached a schema-valid value with `repair_attempt_count = 1` is `repaired`, again whatever its transport attempt count — including the invocation that both consumed transport retries **and** then repaired successfully, which is `repaired` because the repair is what produced the returned value, and which the negative rule alone leaves unclassified. An invocation that reached no schema-valid value is `failed`, whether it exhausted the repair budget (TR-008), exhausted the transport budget (TR-010), or expired its deadline (TR-034); `error_type` distinguishes those three causes from one another (TR-064). The three cases are mutually exclusive and jointly exhaustive over every row that exists at all — TR-011's denominator — so no terminal state is unclassified and none maps to two values.
- **TR-079**: The repaired rate the Risks mitigation commits to publishing MUST be defined as a ratio over stored columns rather than left to the reader. **Numerator**: rows with `outcome = 'repaired'`. **Denominator**: rows whose invocation reached validation at all — `outcome` in (`valid`, `repaired`), or `outcome = 'failed'` with an `error_type` of `validation_failed`. Rows that failed transport or expired a deadline are excluded, because an invocation whose response never arrived never exercised the schema and would dilute the very signal the mitigation exists to protect. **Ownership**: E004 MUST make the rate computable from the invocation table alone and MUST NOT publish it; publication, alongside the constraint context below, is E013's obligation, recorded in IP-005, so the mitigation rests on a requirement and a criterion (SC-023) that can fail rather than on a risk-table cell alone. **Constraint context**: this epic records **no** per-row field naming which constraints were enforced by post-decode validators rather than by the submitted schema, and that is a decided position rather than an omission — the split is a property of the caller's schema and the provider's supported keyword set (TR-005), identical for every invocation submitting that schema, so a per-row field would store one fact once per row. The context is published from the schema definition the gateway digests (TR-038), whose digest changes whenever the validator set changes. **Disclosed limit**: a row alone therefore does not carry the split, and a consumer joining rate to context must resolve the schema artifact separately; if E013 cannot, a validator-enforcement field is added to TR-012's list under the change procedure of TR-069. **Estimate condition**: the rate is a *measurement* over the rows counted and attracts no interval obligation while presented as such; it becomes a quality *estimate*, and Principle II's interval obligation attaches at the epic presenting it, the moment it is presented as an estimate over a population wider than the rows counted — which is any of a projection to future invocations, a claim about a schema other than the ones the counted rows submitted, or a claim about a model or a convention pin other than the ones those rows carry.
- **TR-080**: The trace identifier of TR-031 MUST be propagated as an **explicit optional field on the gateway-owned request type**, never through ambient or contextual propagation: the gateway reads no thread-local, no context variable, and no inbound HTTP header, and installs no propagator — consistent with TR-075's position that this epic installs no tracing pipeline, and with TR-002's gateway-owned public surface being the only place a caller can supply one. The gateway generates a conforming identifier when the field is absent (TR-031, TR-047). **Disclosed limit**: the stored row does **not** distinguish a caller-propagated identifier from a gateway-generated one — both are 32 lowercase hex characters in one column — so the fact that an invocation joined no external trace is not recoverable from the row. This is a decided position: distinguishing the two by *shape* would break the single value domain TR-047 fixes, and the alternative is a provenance field, which would sit outside TR-012's closed list. Reversal: if E013 or a caller needs the distinction, a provenance field is added under TR-069's procedure; until then the limit is disclosed at each of the three disclosure sites — this spec's requirement text, the plan's Complexity Tracking table, and the module docstring of the code carrying the limit — rather than presented as closed.
- **TR-081**: A price-table version MUST carry its own provenance at requirement level rather than only in the schema: the **date the published rates were captured** and the **published source they were captured from**, both mandatory on every version, so a recomputed cost resolves to an attributable rate table rather than to a bare identifier (Principle I). The capture date is distinct from an entry's effective-from date — one snapshot may legitimately carry several effective-from rows for one model, including a scheduled future change — and neither may be substituted for the other. A version whose source is unrecorded MUST NOT be seeded or pinned.

### Key Entities

- **ModelInvocation**: One invocation through the gateway — not one attempt — whether it succeeded, was repaired, or failed, and whether it resolved from the provider or from a fixture. Carries requested and resolved model identity, provider and operation names, resolution mode, the fixture key where one applies, token counts by billing class summed across every attempt, total wall-clock latency, transport and repair attempt counts, computed cost with its price-table version, validation outcome, error type where applicable, a trace identifier propagated from the caller or generated when absent, and a creation timestamp. Written in a transaction the gateway owns, so it survives a caller rollback. Read by E013; never updated and never deleted after write (TR-055) — a rule held by convention, code review, and the restrictive referential actions of TR-046, not by a database trigger or a revoked grant, and disclosed here as uncovered rather than presented as enforced.
- **PriceTableVersion**: A dated, identified snapshot of provider pricing, and the only scope a price lookup searches — an invocation resolves within the version pinned in configuration and never against a newer one. Referenced by every invocation so a historical cost stays recomputable after rates change. Versions are added, never edited (TR-055) — append-only by the same convention-and-review enforcement disclosed for ModelInvocation, with `ON DELETE`/`ON UPDATE` restriction (TR-046) as the only database-level part of it.
- **PriceTableEntry**: One rate row within a version — model identifier, effective-from date, and separate rates for base input, cache write, cache read, and output. Within one version the model identifier and effective-from date are unique, so the lookup can never face a tie (TR-057). A version may hold several entries for one model; the one selected is the latest effective-from at or before the pricing timestamp. Absence of a covering entry is a recorded condition, not a default. A rate change is a new version, never an edit to this row (TR-055), under the same disclosed convention-and-review enforcement.
- **ResponseFixture**: A committed provider response keyed by the content hash of its canonical request, together with the redacted request material and the token counts the recording call reported. Its key incorporates gateway-derived digests of the schema (validators included) and the resolved prompt template, so no declared version string can go stale. The unit of offline reproducibility; regenerated when its key changes, never edited in place.

## Assumptions & Risks

### Assumptions

- E003 lands its Alembic arrangement in `/src/model` before this epic needs to apply a revision. The blocks are reserved by {SAD:ADR-0013} rather than negotiated, so authoring is unblocked from the start; only applying waits (IP-008).
- The PostgreSQL 16 service from E001's local orchestration is the database used for this epic's integration checks; no new datastore is introduced.
- The provider's native structured-output mode is available for the pinned model. If it is not, the gateway falls back to prompt-and-parse with identical validation, repair, and recording semantics — the outcome contract does not change.
- No consumer of the gateway exists yet, so its public surface is designed against the recorded decisions rather than against a live call site; E006 is the first real caller.
- A provider credential is available to the developer for recording fixtures and never to continuous integration.

### Risks

- **Incomplete hash scope produces silent stale replays** *(likelihood: low, impact: high)*: A request field omitted from the canonical serialization makes a changed request resolve to an old fixture, and the resulting numbers look normal. Mitigation: the hashed field list is closed and an unknown field is an error rather than an omission (TR-020), and the schema and template versions are gateway-derived digests rather than caller-declared strings (TR-038), so the two most likely staleness paths — an edited validator and an edited prompt — cannot survive a forgotten bump. Likelihood lowered from medium at clarification.
- **Migration-number collision with E003 in the same wave** *(likelihood: medium, impact: medium)*: Both epics add migrations in parallel; a collision surfaces only when both are merged. Mitigation: ranges are claimed and recorded at epic start (TR-018), and the runner is forward-only and idempotent.
- **Repair rate is misread as a quality signal it is not** *(likelihood: medium, impact: low)*: With constrained decoding, `repaired` should be rare; a high rate more likely indicates schema keywords silently dropped by the provider than a weak model. Mitigation: publish the repaired rate alongside which constraints are enforced by validators rather than by the schema. **Owner and definition**: the rate, its numerator and denominator over stored columns, the constraint context and the disclosed limit on recovering it from a row alone, and the condition on which the rate becomes a quality *estimate* are all fixed by TR-079 and checkable under SC-023; publication belongs to E013 under IP-005. The mitigation therefore rests on a requirement and a criterion that can fail rather than on this cell alone.

## Glossary

| Term | Definition |
|------|------------|
| Gateway | The shared package under `/src/gateway` holding the only module permitted to import the model-provider client, together with its validation, recording, and caching support. |
| Invocation | One call through the gateway, comprising up to one repair and a bounded number of transport attempts, producing exactly one stored record whose token counts and latency aggregate across all of them. |
| Attempt | One request issued to the provider or one fixture lookup within an invocation. Attempts are counted on the record but never stored as rows of their own. |
| Repair | A single re-prompt issued after a schema validation failure, carrying the failing field path and message back to the model. |
| Fail closed | Recording the failed outcome and raising rather than returning a partially valid or unvalidated value. |
| Replay mode | Resolution of responses exclusively from committed fixtures, with no network access and no credential; a miss is an error. |
| Record mode | The only resolution mode that reaches the provider: it issues the request and writes the resulting fixture. Requires an explicit opt-in separate from mode selection, and is used to seed and refresh the fixture store. |
| Content hash | The key derived from a canonical serialization of the whole request, over a closed and documented field list, including gateway-derived digests of the schema and the resolved prompt template. |
| Pricing timestamp | The instant a price entry is resolved against: the invocation's creation timestamp in `record` mode, the fixture's recording date in `replay`. Chosen so a replayed fixture reproduces one cost regardless of when it is replayed. |
| Spool | The local store holding invocation records whose database write failed after a provider request was issued, reconciled into the invocation table on the next successful connection. *Append-only* here means no spooled row is ever updated in place (TR-052): a row is inserted once and removed once its record has committed to the invocation table, so the reconcile's delete is not an exception to the property but its terminal step. |
| Price-table version | The identified pricing snapshot in force for an invocation, stored on the record so historical cost stays recomputable. |
| Outcome | The classification of an invocation as `valid`, `repaired`, or `failed`. |
| Egress sink | One of the five destinations credential material could leave the boundary through, closed and enumerated by TR-059: log output, the gateway's own exception payload (message, attributes, and the local frames a variable-capturing traceback renders), the committed fixture store and its provenance sidecars, the local invocation spool file, and check output. The provider-echoed error body is not a sink under this term — it is suppressed by normalization (TR-025, TR-064) rather than transformed by redaction. |
| Repaired rate | The ratio TR-079 defines: rows with outcome `repaired` over rows whose invocation reached validation at all. A *measurement* over the rows counted, not an estimate — it becomes an estimate, and attracts Principle II's interval obligation at the epic presenting it, only when projected beyond that population. Published by E013, never by E004. |
| Pinned convention version | The concrete OpenTelemetry generative-AI semantic-convention release the recorded field names follow — `1.37.0` (TR-070) — recorded identically in gateway configuration, in a table comment, and in the requirement itself, so OBJ3 VC7 compares against a fixed referent rather than a moving document. |

## Clarifications

### Session 2026-07-25

- Q: OBJ1 VC1 / SC-002 require the public surface to type-check with no provider package present, but the gateway declares the provider SDK as a hard runtime dependency. How is provider absence achieved? -> A: Move the provider SDK to an optional extra of the gateway manifest and import it lazily inside the invocation entry, so the public surface imports with the extra uninstalled.
- Q: Does a replayed invocation write an `llm_invocation` row, and is it distinguishable from a live one? -> A: Yes — replay writes a row, and the field list gains a resolution-mode field and the fixture key, so replayed and live rows are separable and joinable to their fixture.
- Q: The gateway is a shared library, not a service. Where does its database connection come from, and what happens when the record write fails? -> A: The gateway opens its own connection from its own configuration, commits the record in an independent transaction before returning, and a failed record write fails the invocation closed.
- Q: Is a row written per attempt or per invocation, and are stored token counts summed across attempts or only the successful attempt's? -> A: One row per invocation; token counts summed across every transport and repair attempt and latency total wall clock, so stored cost equals the invocation's total spend.
- Q: TR-019 puts a schema version and a prompt-template version in the fixture key but never says who produces them. How are they derived? -> A: The gateway derives both — a digest over the full schema definition including its post-decode validators, and a digest over the resolved prompt template text — so a caller cannot forget to bump them.
- Q: Does an invocation resolve its price entry within the pinned price-table version or against the newest one? -> A: Within the pinned version only, selecting the entry whose effective-from is the latest at or before the invocation timestamp; recomputation replays the same rule.
- Q: No request timeout appears anywhere in the spec, so a hung provider request blocks indefinitely and the retry budget never engages. What governs a per-request deadline? -> A: A per-request timeout in gateway configuration with a stated default; expiry counts as a transport failure against the TR-010 budget.
- Q: Technical Constraints fixes the migration runner inside `/src/gateway` while IP-008 says whichever epic merges first contributes it. Where does it live? -> A: Under `/src/gateway` unconditionally; E003 consumes it through the gateway dependency both boundaries already declare, regardless of merge order. **Superseded 2026-07-26 by {SAD:ADR-0013}**, accepted on the default branch while this branch was open: `/src/model` owns the Alembic configuration, the runner, and every schema asset, and E004 contributes revisions in its reserved `0100`–`0199` prefix block rather than building a runner. The answer is retained because it explains why the artifacts read as they did before the reconciliation.
