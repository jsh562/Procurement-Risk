# Feature Specification: Document Ingestion and Extraction

**Feature Branch**: `00006-document-ingestion-and-extraction`
**Created**: 2026-07-27
**Status**: Draft
**Spec Type**: product
**Spec Maturity**: clarified
**Epic ID**: E006
**Epic Sources**: {PRD:CAP-002}{SAD:ADR-0008}
**Product Document**: `specs/prd.md`

## Problem Statement *(mandatory)*

Fifty-one corpus documents sit on disk as PDFs and a database sits empty beside them: the tables that hold chunks, extracted values, and extraction failures exist, and nothing has ever written a row to them. Until something does, every capability the product is built on — retrieval, cross-document identity, grounded answering, and the source-traceability view a coordinator uses to check a number — has no input. Dana, the coordinator this product is designed for, distrusts any tool that produces a number she cannot trace back to a document; the mechanism that earns that trust is a page citation attached to every extracted value, and that mechanism starts here. Left undone, five downstream epics have nothing to consume and the product's central claim stays unbacked.

## Scope *(mandatory)*

### Included

- Reading the corpus through its manifests and creating one `document` row per corpus document, with the layer, license basis, and layer-appropriate provenance carried across unchanged
- Layout-aware parsing of all 51 documents, with every page number derived from the parser
- Structure-aware chunking of all 51 documents, each chunk confined to a single page and to the embedding encoder's input window
- Local embedding of every chunk into the 384-dimension vector the schema declares
- Schema-validated line-item extraction from the 25 synthetic submittal transmittals, with each value's page citation inherited from its source chunk and a per-field confidence recorded
- Multi-page provenance for a value whose label and value straddle a page boundary
- Routing values that fail validation, or fall below the confidence floor, to failure records rather than storing them
- A queryable ingestion-run record giving every chunk, value, and failure an attributable origin
- Total verification that each chunk's recorded page matches the page its text actually came from
- A deterministic template-based extractor over the same transmittals, serving as the baseline every extraction figure is reported against
- An ingestion report committed with this epic at a fixed path, carrying a closed list of contents (FR-071) — the corpus-resident figures, the figures scoped to the run that wrote it, and the conventions downstream epics must account for, each labelled with which it is (FR-072)

### Excluded

- **Line-item extraction from the 26 real UFGS specifications** — they are requirement prose, not item records: no manufacturer, no part number, no quantity, and unresolved bracketed alternatives (`[on-off] [high-low-off] [modulating]`) that a model asked for "the" value would resolve into a project requirement the document never states. They are still parsed, chunked, and embedded, so retrieval and grounded answering reach them in full.
- **Vector search, ranking, and retrieval evaluation** — E008 owns the read path. E006 populates the column and the index the schema already declares.
- **Cross-document identity resolution and merge decisions** — E009 owns them. E006 produces the extracted values they operate on and deliberately asserts no identity between two spellings of one manufacturer.
- **Any change to an E003-owned table this epic populates** — all six of them, not only the three the append-only revoke names: `document`, `chunk`, `field_vocabulary`, `extracted_value`, `extracted_value_contributing_chunk`, and `extraction_failure`. E003 owns every one and `specs/00003-core-data-schema/data-model.md` is normative over this spec ({SAD:ADR-0017}). E006 populates all six, alters none of them, and adds only the records it owns in its own migration block (FR-065). Being populated and being owned are separate facts, and the boundary follows ownership.
- **Optical character recognition** — every document in the corpus carries a real text layer, including the ones rendered to look scanned.
- **Correcting or re-typesetting source documents** — the corpus is byte-for-byte what E002 vendored.

### Edge Cases & Boundaries

- A structural unit that exceeds the encoder's 256 word-piece window: the encoder truncates silently and still returns a well-formed vector, so a too-long chunk is indistinguishable from a complete one at query time. Measured over the real layer, 476 of 9,020 leaf units breach a conservative proxy for the window and the largest is 592 words, so this is the common case rather than the exception. Splitting descends to the sentence, and only a single over-long sentence fails the run.
- A field whose label ends one page and whose value begins the next — E002's `PAGE_SPLIT_FIELD` irregularity class. A chunk may not span pages, so this is a multi-source value with one contributing chunk per page, not a chunk that straddles the break.
- A UFGS section written as an unedited master, carrying bracketed alternatives nobody has chosen yet. Chunk text preserves the brackets verbatim so a downstream reader can see the choice is open.
- The PART 1 REFERENCES article: a dense list of ASTM designations that embeds poorly and looks near-identical across unrelated sections.
- Agency variants of one MasterFormat number are separate documents whose chunks are near-duplicates of each other.
- A `document_id` collision between two corpus files whose stems normalize to the same identifier.
- A manifest entry whose recorded content hash no longer matches the file on disk — the corpus changed underneath the run.
- A field printed with an alternate label (`Mfr` rather than `Manufacturer`), or absent entirely — both are seeded irregularity classes and neither may be defaulted into a value.
- Two documents in one resubmittal chain differing only by revision suffix, whose chunks retrieve as duplicates.
- A run interrupted part-way: the extraction tables are append-only by privilege, so the run cannot delete what it wrote. Per-document transactions make this survivable — an abort rolls back only the document in flight and every earlier document stays whole.
- The provider is unreachable, or a fixture is missing in replay: a named run-level failure, distinct from per-field extraction failure, since none of the seven per-field outcomes means the invocation could not be made.
- A page carrying no detectable structural marker at all — 175 of them in the real layer — where the page itself becomes the terminal structural unit.

## User Scenarios & Testing *(mandatory for product specs only)*

### User Story 1 - Corpus becomes citable chunks (Priority: P1)

Every document in the corpus is parsed and cut into chunks that follow the document's own structure, and each chunk records which document, project, page, and specification section it came from, along with the vector that will later let it be found. A coordinator never sees a chunk directly, but every citation she does see resolves through one, so the page a chunk claims must be the page its words are actually on.

**Why this priority**: Nothing else in the epic or in five downstream epics can begin without populated chunks — retrieval, grounded answering, and the traceability view all read this table.

**Independent Test**: Run the ingestion job against the committed corpus, then pick any chunk at random, open the PDF it names at the page it names, and find its text there.

**Acceptance Scenarios**:

1. **Given** the 51-document corpus and an empty database, **When** the ingestion job runs, **Then** every document has a `document` row and every chunk carries a non-null document, document type, project, page number, and ordinal.
2. **Given** a chunk, **When** its text is compared against an independent extraction of the page it names, **Then** the text is found on that page — checked for every chunk in the corpus, not a sample.
3. **Given** a specification section whose article exceeds the encoder's input window, **When** the chunker processes it, **Then** the ladder descends — paragraph, subparagraph, sentence — until each fragment fits, and no chunk is embedded whose tail the encoder would discard.
4. **Given** a single sentence that exceeds the window, **When** the chunker reaches it, **Then** the run fails and names it, because below a sentence there is nothing left to split; a leaf that is merely long does not fail the run.
5. **Given** a real UFGS specification containing unresolved bracketed alternatives, **When** it is chunked, **Then** the bracket markup is preserved verbatim in the stored text.
6. **Given** a completed run, **When** it is run again against unchanged inputs, **Then** the same chunk boundaries and ordinals are produced.
7. **Given** a manifest entry whose recorded content hash no longer matches the file on disk, **When** the run reaches that document, **Then** the run fails and no rows are written for it.
8. **Given** any chunk, **When** its page attribution is read, **Then** it names exactly one page — a structural unit crossing a page break is cut at the break into two chunks that each keep that unit's structural identifier, never one chunk spanning the break.
10. **Given** a page on which no structural marker is detectable at all, **When** it is chunked, **Then** the page itself is the terminal structural unit, and the ingestion report names every document chunked that way with its count rather than leaving the fallback invisible.
9. **Given** the ingestion report, **When** it is read, **Then** it names the shared-library project convention, the chunk-identity contract, and the zero-recognition-error upper bound.

### User Story 2 - Every extracted value points at its page (Priority: P1)

Line items are extracted from the 25 submittal transmittals — the manufacturer, part number, quantity, dates and descriptor codes a vendor actually proposed. Each value carries the page it came from, and that page is not something the model was asked for: it is inherited from the chunk the text was read out of. When Dana questions a part number, one click puts her on the page that prints it.

**Why this priority**: This is CAP-002's stated outcome and the product's core claim. E009 has nothing to match without extracted line items, and the 100% traceability target is measured on exactly these rows.

**Independent Test**: Pick any extracted value, read its cited page, open that document at that page, and find the printed value.

**Acceptance Scenarios**:

1. **Given** a submittal transmittal chunk, **When** extraction runs, **Then** every value produced carries a source chunk, a cited page equal to that chunk's page, a field name, and a confidence.
2. **Given** any extracted value in the database, **When** its cited page is compared against its source chunk's page, **Then** they agree — because a value whose citation disagrees with its chunk cannot be stored at all.
3. **Given** an extraction request, **When** it is issued, **Then** it goes through the single traced model path and no other module reaches the provider.
4. **Given** a manufacturer printed as `EMBERDYNE CONTROLS`, **When** it is extracted, **Then** the stored value is that text unaltered, and no normalized or canonicalized form is stored beside it — normalization is the join key identity resolution owns, not a record this epic keeps.
5. **Given** a field name the model proposes that is not in the seeded vocabulary, **When** persistence is attempted, **Then** the write is refused rather than the vocabulary being widened at run time.
6. **Given** the 26 real specifications, **When** the run completes, **Then** they have chunks and embeddings and zero extracted values, and that exclusion is recorded rather than left to be inferred from an empty result.
7. **Given** a generated document, **When** its record is written, **Then** it carries its generator identity, seed, and generation date and carries no retrieval provenance, while a retrieved document carries its source, issuing body, and retrieval date and carries no generator fields.
8. **Given** an extracted value whose kind is numeric or a date, **When** the typed form is produced, **Then** it was coerced by deterministic code from the printed text rather than accepted as a typed value the model returned.
9. **Given** the same transmittals, **When** the deterministic baseline extractor is run over them, **Then** its figures are published beside the model's on the same documents, with the baseline labelled strong or weak.

### User Story 3 - An untrustworthy value is absent, not wrong (Priority: P1)

When the model returns something that does not fit the schema, the system tries once to repair it and then stops. When it returns a value it is barely confident in, that value does not enter the record either. In both cases a failure record is written naming the chunk, the field, and the cause. Dana sees a gap she can investigate rather than a number that looks like every other number and is wrong.

**Why this priority**: Precision over recall where a mistake is silent is a project principle, and a wrongly-stored extracted value is the silent mistake — it propagates into matching, ranking, and the forecast with no symptom.

**Independent Test**: Drive extraction over a chunk whose response fails validation twice, then confirm zero extracted values and exactly one failure record naming the cause.

**Acceptance Scenarios**:

1. **Given** a model response that fails schema validation, **When** one repair attempt also fails, **Then** no value is persisted and a failure record is written with outcome `repair_budget_exhausted`.
2. **Given** an extracted value whose confidence falls below the published floor, **When** it is processed, **Then** it is not persisted and a failure record is written with outcome `confidence_below_threshold`.
3. **Given** an extracted value whose confidence is at or above the floor, **When** it is persisted, **Then** its confidence is stored with it and carried through to anything that displays it.
4. **Given** any failure record, **When** it is inspected, **Then** it carries no value text and no confidence — a failure cannot smuggle a partial answer.
5. **Given** a field the document simply does not print, **When** extraction runs over its chunk, **Then** the outcome is `no_value_found` rather than a defaulted or inferred value.
6. **Given** a completed run, **When** its confidence figures are published, **Then** the distribution is published rather than the mean, and the score is stated to be computed from parse signals and uncalibrated.
7. **Given** any stored extracted value, **When** its confidence is recomputed from the signals recorded with it, **Then** the result equals the stored score exactly.
8. **Given** the confidence floor, **When** the run's distribution is inspected afterwards, **Then** the floor is the value declared before the run and has not been moved to fit what the distribution turned out to be.

### User Story 4 - A value split across a page break keeps both pages (Priority: P2)

Some fields in the corpus have their label at the foot of one page and their value at the head of the next — a deliberate irregularity E002 seeded. The extracted value records both pages rather than picking one, so the citation stays honest about where the evidence actually is.

**Why this priority**: A real corpus condition with a designed representation already waiting in the schema; without it these fields either lose half their provenance or are dropped, but P1 remains viable because the majority of fields sit on one page.

**Independent Test**: Extract from the document carrying the seeded page-split irregularity and confirm the value records two contributing pages.

**Acceptance Scenarios**:

1. **Given** a field whose label and value straddle a page boundary, **When** it is extracted, **Then** the value is recorded as multi-chunk, anchored on the page that prints the value, with one contributing chunk for each *additional* page it drew on — the anchor is contributor 1 and never appears in the contributing set.
2. **Given** a multi-chunk value, **When** its declared source count is compared against its recorded contributors, **Then** they agree.
3. **Given** a value drawn from a single chunk, **When** it is recorded, **Then** it is marked single-chunk and has no additional contributors.

### User Story 5 - Every value names the run that produced it (Priority: P2)

Each ingestion run records what produced it: which agent and model, which chunker and embedding model at which revision, which corpus content, and when. Any chunk, value, or failure resolves to its run, so "what produced this number" is a query rather than an archaeology exercise.

**Why this priority**: The schema deliberately omits a per-row agent column on the grounds that E006 records this at run granularity; nothing else in the project holds it. P2 because a value is already citable to a page without it.

**Independent Test**: Take any extracted value, join to its ingestion run, and read the agent, model, chunker version, and embedding model revision that produced it.

**Acceptance Scenarios**:

1. **Given** a completed ingestion run, **When** its record is read, **Then** it names the agent identity, the provider model, the chunker version, the embedding model identity and revision, the corpus manifest digests, the resolution mode, and its start and finish.
2. **Given** any chunk, extracted value, or failure record, **When** it is queried, **Then** exactly one ingestion run is reachable from it.
3. **Given** two runs over the same corpus with different chunker versions, **When** their outputs are compared, **Then** each row is attributable to the run that wrote it.

### User Story 6 - Re-ingesting is safe and repeatable (Priority: P3)

Running ingestion again does not duplicate what is already there, and correcting a mistake is a documented remove-and-reload rather than an edit, because the provenance tables refuse in-place updates by design. Repeatability is also what lets continuous integration run the whole pipeline offline against committed responses, reaching no provider and no network.

**Why this priority**: Operational quality that matters the second time the job is run, not the first; P1 and P2 are demonstrable from a single clean run.

**Independent Test**: Run ingestion twice against an unchanged corpus and confirm the row counts are unchanged and no chunk identity moved.

**Acceptance Scenarios**:

1. **Given** a populated database, **When** ingestion runs again over unchanged inputs, **Then** no duplicate chunks, values, or failures are created.
2. **Given** a document needing re-ingestion, **When** it is reloaded, **Then** its dependent rows are removed in an order the restricting foreign keys permit and reloaded, with no row updated in place.
3. **Given** a run that fails part-way, **When** the database is inspected, **Then** no document is left half-ingested.

## Requirements *(mandatory)*

### Functional Requirements *(product specs only)*

**Corpus intake and document records**

- **FR-001**: System MUST enumerate corpus documents through the committed manifests, resolving each entry's location with the repository's existing containment-checked path resolution, and MUST NOT ingest a PDF that no manifest lists.
- **FR-002**: System MUST create exactly one document record per corpus document, deriving its identifier from the file stem by a stated transformation — lower-case the stem, replace every run of characters outside `[a-z0-9]` with a single hyphen, and strip a leading or trailing hyphen — yielding `ufgs-23-52-00`, `prj-001-t0002-r0`. The result MUST satisfy the identifier format E003 declares, `^[a-z0-9]+(-[a-z0-9]+)*$` with a length of 3 to 128 characters, and a stem whose transform does not satisfy it MUST fail the run naming the file rather than being truncated, padded, or coerced further. The whole transformation is stated because it is what FR-052's collision case presupposes: two stems differing only in case, or only in which separator they spell, normalize to one identifier, and a normalization left unstated makes the collision unreproducible. This closes the disclosed gap that left E003's format unadopted.
- **FR-003**: System MUST record real specifications under the reserved shared-library project `PRJ-000` and synthetic documents under their own project, and MUST record `PRJ-000` in the ingestion report as a named convention project-scoped readers have to account for, since a reader filtering on project alone would silently miss every governing specification. `PRJ-000` MUST be treated as reserved corpus-wide — barred from being minted as an ordinary project identifier by this epic or any other producer — and the report MUST state that nothing structural enforces the reservation: the project identifier is a format-checked text column with no referent table, so a second producer minting `PRJ-000` for a real project would give the sentinel a second meaning that no constraint rejects.
- **FR-004**: System MUST carry each document's layer, license basis, and layer-appropriate provenance from the manifest into its record unchanged, and MUST NOT give a generated document retrieval provenance it does not have.
- **FR-005**: System MUST verify each document's recorded content hash against the file on disk before parsing it, and MUST fail the run without writing rows when they differ.
- **FR-006**: System MUST classify each document by type from a closed set, recording real specifications as specifications and synthetic transmittals as transmittals, and MUST NOT invent a type outside that set.
- **FR-052**: System MUST fail the run, naming both files, when two corpus files yield the same derived identifier, rather than overwriting one document record with another or attaching one document's chunks to the other — a collision silently resolved would give a citation a referent it never came from. The check MUST complete over the **whole enumerated corpus before the first document transaction commits**: identifiers derive from manifest entries alone and need no parsing, so there is no reason to discover at document forty a collision that leaves thirty-nine documents durable and the run dead. A collision found before any write means zero rows are written by that run at all, which is a stronger outcome than FR-042's per-document guarantee and is available here for free.

**Parsing and page provenance**

- **FR-007**: System MUST derive every page number from the parser and MUST NOT accept, request, or store a page number produced by a language model.
- **FR-008**: System MUST derive page text under the same extraction tolerances and normalization form the repository already fixes for corpus derivation, so that page attribution and the corpus's own structural derivation cannot reach different answers about what text a page contains. **One reader, not two readers configured alike.** Page text MUST be obtained by calling the committed reader the repository already provides — its pinned word tolerances, its line grouping, and its normalization — rather than by a second assembly of words into lines and lines into page text that happens to be configured the same way: the tolerances and the normalization form are only two of the three things that decide what text a page contains, and the third is how words are grouped and joined. System MUST declare no second tolerance mapping, no second normalization, and no second page-text assembly anywhere in the ingestion package. It follows that **SC-037 is a contract check over the absence of a second reader, not a measured agreement between two derivations**: under one reader the two sides cannot disagree, and a criterion comparing one function's output against its own would assert nothing. What this requirement does *not* establish is that the shared reader reads any page correctly — that residual is carried in part by FR-010's containment check and in part by FR-011's inspected sample, and is disclosed rather than left to be inferred from the word "same".
- **FR-009**: System MUST NOT require optical character recognition for any document, and MUST disclose in the ingestion report that the corpus text layer carries zero recognition error, so every accuracy figure measured here is an upper bound a genuinely scanned corpus would not reproduce. **The claim MUST be stated per layer, because its evidence differs by layer and the corpus datasheet governs only one of them.** For the **synthetic** layer the text layer carries zero recognition error *by construction* — the text is composed before it is rendered and the datasheet records it — and this is the layer every extraction accuracy figure is measured on (SC-012), so it is the layer the upper-bound caveat attaches to. For the **real** layer the claim is narrower and MUST be published as the narrower one: no recognition step is performed at any point, because each retrieved document carries an embedded text layer, so no recognition error is *introduced* here; whether that embedded layer already disagrees with the printed page is unmeasured, outside this epic's control, and affects chunk and page figures rather than extraction accuracy, since no value is extracted from that layer at all. A corpus-wide "zero recognition error" stated without that split would claim the datasheet's evidence over 26 documents the datasheet says nothing about.
- **FR-010**: System MUST verify, for every chunk in the corpus rather than a sample, that the chunk's text is present in an independent extraction of the page it names. **What the extraction is independent of, and who performs it, are both stated, because neither is recoverable from the word "independent".** The verifying extraction is a **fresh read of that document's own bytes, taken after the run and addressed by the chunk's recorded page number**; it MUST NOT consult the chunker's cached page text, its page-to-chunk mapping, or any other in-memory artifact of the run that wrote the chunk, since a comparison against the text a chunk was cut from is a comparison of the parse with itself and is silent on whether the recorded page number is the right one. It is **not** independent of the parser: both sides read through the one reader FR-008 fixes, so this check cannot detect that reader misreading a page, and that limit is disclosed rather than implied. The obligation is discharged in two named places, because "System MUST verify" otherwise names no actor: the **ingestion job** re-checks containment for each chunk inside that document's transaction before it commits, so a chunk whose text is not found on its named page is never written; and the **verification suite** re-asserts containment corpus-wide against the fresh post-run extraction and publishes the population it enumerated (FR-068). The first is a write-time guard against the run's own state and is deliberately not the independent one; the second is the check this requirement is about.
- **FR-011**: System MUST record in the ingestion report, for any claim resting on human inspection rather than the total check of FR-010, the number of items inspected, the number of defects found, and the error bound that sample supports, computed by a stated method. **The set of such claims MUST be enumerated rather than left to be populated by whoever writes the report**, and the enumeration MUST be published even when a claim's inspected count is zero, so "nothing was inspected" is a statement rather than an absence. The set is non-empty and its known member is named here: **structural detection on the 26 real specifications** — section, part, and article identification — for which no reference exists at all, since the corpus datasheet governs only the synthetic layer (Assumptions), so the only available oracle is human inspection of sampled pages. Every other claim in this epic MUST either appear in this enumeration with its inspected count, or name the total check that carries it instead. The **method is fixed rather than left to the report's author**, so two runs publish comparable bounds: for a sample of *n* items with zero defects, the published bound is the rule-of-three 95% upper bound **3/n**, stated with *n* and never quoted for *n* ≤ 30, where the approximation does not hold; for a sample with one or more defects, the published bound is the **continuity-corrected Wilson 95% interval** on the observed defect proportion, the same variant FR-060 fixes, with its denominator printed.

**Chunking**

- **FR-012**: System MUST place every chunk boundary in one of three named classes — a structural boundary the parser identified, a page break, or a sentence boundary inside a leaf that exceeds the encoder window — and MUST place zero boundaries at a fixed character, word, or token offset. A fragment produced by a page or sentence boundary MUST keep the structural identifier of the unit it came from, so the fragment remains attributable to a structure even though the cut was not made at one.
- **FR-013**: System MUST confine each chunk to a single page.
- **FR-014**: System MUST measure chunk length in the embedding encoder's own tokenizer and MUST descend the boundary ladder — article, then paragraph, then subparagraph, then sentence — until a unit fits, rather than embedding a chunk the encoder would silently truncate. System MUST fail the run naming the unit only when a single sentence exceeds the window, since below that there is nothing left to split.
- **FR-015**: System MUST record on each chunk the document, document type, project, page number, and a zero-based ordinal unique within its document, together with the specification section and heading where the document supplies them. Ordinals MUST be assigned in the document's own reading order — ascending page number, then position within the page — and MUST be contiguous from zero: a page that yields no storable text produces no chunk and therefore consumes no ordinal. Both halves are stated because SC-003's contiguity and SC-007's re-run determinism are otherwise decidable only by inspecting a run rather than by reading the rule.
- **FR-016**: System MUST store chunk text as it appears in the source, including unresolved bracketed alternatives in unedited specification masters, so a downstream reader can see that a choice has not been made.
- **FR-017**: System MUST produce the same chunk boundaries and ordinals for **the same input tuple** — that document's content hash, the chunker version, *and* the embedding encoder identity and revision (FR-043) — and MUST record the chunker version so a boundary change is attributable rather than mysterious. The guarantee is stated over the tuple and not over the chunker version alone because chunk length is measured in the encoder's own tokenizer (FR-014): a tokenizer revision moves boundaries with the chunker version unchanged, so a guarantee conditioned on the chunker version alone would be false exactly when a reader most needed it. Attribution follows the same rule — a boundary change is attributed to whichever tuple member moved, which is why both are recorded on the run. **What obliges a chunker-version bump MUST be stated rather than inferred**, since a version that only moves when someone remembers is not an attribution mechanism: the version MUST change when any of the boundary-class rules (FR-012), the structural detection the ladder descends (FR-014), the ordinal assignment rule (FR-015), or the identity or pinned version of the sentence segmenter changes. The encoder identity and revision are deliberately **not** in that list — they are their own tuple members, and folding them into the chunker version would make one number answer two questions.
- **FR-018**: System MUST record in the ingestion report the chunk-identity contract downstream consumers depend on — specifically that **a chunk identifier is minted by the run that writes it** and is stable only for as long as that generation is resident, so a retrieval evaluation set frozen on chunk identity is invalidated by any legitimate re-chunk and must instead be keyed on document, page, and quoted span. The contract is stated over the *run* rather than over the chunker, because that is the wider and the true population: FR-043's input tuple includes the provider model and the prompt and schema digests, so a change to any of them re-ingests a document and mints new chunk identifiers for it **even though its boundaries are byte-for-byte identical**. A consumer told only that identifiers move "on a re-chunk" would conclude an unchanged chunker keeps them stable, which is false. Chunk identity is deliberately **not** required to be a function of the chunk's content and position: making it one would be a change to a column E003 owns, and the keying contract already gives E008 a stable alternative that survives both re-chunk and re-ingest.

**Embedding**

- **FR-019**: System MUST embed every chunk locally with a pinned model identity and revision, reaching no network at run time. **Where the encoder artifact and its tokenizer resolve from MUST be stated, because a pinned upstream revision is a network resolution unless the bytes are local**: both MUST resolve from a repository-committed artifact path whose contents are integrity-checked against recorded digests before the encoder session is created, and the run MUST fail naming the artifact rather than fall back to a remote fetch when a digest does not match or a file is absent. The recorded revision names the upstream revision the committed export was taken from; it is an attribution record, not a resolution instruction. Committing the bytes is forced rather than chosen: SC-023 requires a full run in continuous integration with zero network access, and an artifact fetched at environment setup is a network resolution that the criterion's own observation window (SC-023) would have to be narrowed to exclude. The tokenizer MUST be pinned to the same revision as the encoder, since chunk boundaries are measured in it (FR-014) and a count that disagrees with the model's own truncation moves boundaries silently.
  **The exported encoder is accepted only against a parity tolerance declared before the comparison runs.** {SAD:ADR-0018} makes this epic the owner of the export and of proving it, on the grounds that the export is a reimplementation — pooling and normalization become repository code — of the thing every retrieval number depends on. The obligation is stated here as three parts, because a tolerance is only a tolerance if all three hold. **Declared first**: the bounds are recorded before the comparison is run, which is Principle VI applied to an artifact rather than to an evaluation set — a bound chosen after seeing the divergence is not a bound, it is a description of the divergence. **Measured over a committed probe set spanning both corpus layers**, so the parity claim covers the specification prose the real layer is made of as well as the transmittal text, and the set is committed rather than assembled at comparison time. **Published with its observed maxima beside the declared bounds**, so a reader sees how much headroom the export actually had rather than only that it passed.
  The bounds are **cosine similarity ≥ 0.999999 between the exported and the reference embedding for every probe**, and **maximum absolute per-dimension difference ≤ 1e-5**. Both are chosen against the numeric stack rather than picked: the vectors are L2-normalized `float32`, whose machine epsilon is roughly 1.2e-7, so 1e-5 sits about two orders of magnitude above representation noise and far below any difference that could reorder a retrieval result. A run MUST fail rather than embed when either bound is breached. **If an observed maximum lands near either bound, that is a finding about the export and MUST be published as one** — never absorbed by widening the bound, which would be adjusting a target to match a result (Principle VII).
- **FR-020**: System MUST record the embedding model identity and revision on every chunk, so vectors from two model versions are never silently mixed.
- **FR-021**: System MUST take the vector dimension from the value the schema publishes at run time, so that changing the dimension does not require changing this epic's code.

**Extraction**

- **FR-022**: System MUST extract line items from the synthetic submittal transmittals only, and MUST record that exclusion explicitly rather than leaving an empty result to be interpreted.
- **FR-023**: System MUST issue every model request through the single traced model path, and MUST NOT import or reach the provider client from any other module.
- **FR-024**: System MUST draw every extracted field name from the seeded field vocabulary **and only from terms that are unretired at run time** — those carrying no retirement date — and MUST refuse a value naming a term outside that set rather than widening the vocabulary at run time. The unretired filter is stated as this epic's obligation because retirement is advisory in the normative schema: a foreign key checks that a term exists, not that a sibling column is null, so E003 records the filter as E006's to apply (E003 §Disclosed Gaps G-7) and nothing enforces it if this epic does not claim it.
- **FR-025**: System MUST validate every model output against the caller's schema before persisting it, and MUST NOT persist, return, or log an unvalidated value.
- **FR-026**: System MUST attempt at most one repair after a validation failure and then fail closed.
- **FR-027**: System MUST store manufacturer and part-number values exactly as printed, and MUST NOT store a normalized, cleaned, or canonicalized form in place of them or alongside them. Normalization is the join key identity resolution operates on and belongs to the epic that owns that decision; E006 preserves the evidence the citation points at.
- **FR-028**: System MUST NOT assert that two differently-spelled manufacturer names are the same manufacturer; recognizing identity across documents belongs to a later epic.

**Citation and confidence**

- **FR-029**: System MUST give every extracted value a page citation inherited from the chunk it was read from, and MUST make a citation disagreeing with its source chunk unstorable rather than merely detectable. Where a field's label ends one page and its value begins the next, the anchor — the single chunk whose page becomes the citation — MUST be **the chunk carrying the printed value**, never the chunk carrying only the label. The cited page is a scalar and downstream traceability resolves through it, so a citation landing a reader on a page that prints `Manufacturer:` and no manufacturer defeats the one-step verification the product exists to provide; the label's page is not lost, it is recorded as an additional contributing chunk. Because the anchor is then the *later* page, the anchor is not the earliest page a multi-chunk value draws on, and every comparison that reassembles such a value orders its chunks by page rather than by contributor position (SC-027).
- **FR-030**: System MUST record a per-field confidence on every extracted value, with no exemptions.
- **FR-031**: System MUST compute each per-field confidence deterministically from three observable parse signals — whether the printed field label matched the canonical form or a known alternate, whether it was read from one chunk or assembled across a page break, and whether the invocation validated on the first attempt or only after a repair — and MUST NOT store a confidence a language model asserted about its own output. These are the same three signals FR-057 deducts against and the same three FR-063 records; a fourth signal originally listed here — whether the value was printed or absent — was withdrawn during clarification and MUST NOT be computed, because an absent value is a failure record rather than a stored value with a confidence and the signal can therefore never fire on a row this requirement ranges over. System MUST NOT present the resulting score as a calibrated probability, publish it as a frequency, or compare it across different fields as though the values shared a scale; it is a heuristic ordering, and nothing in this epic measures it against ground truth.
- **FR-032**: System MUST fix the confidence floor as a declared value chosen before the first run and MUST NOT move it in response to the distribution that run produces; a value below it is not persisted and is recorded as a failure, and a value at or above it is persisted with its confidence intact. Re-deriving the floor from observed data is fitting a threshold to the set being measured, which requires a frozen and hashed labelled set and is therefore out of this epic's scope.
- **FR-033**: System MUST record in the ingestion report the declared floor together with the observed distribution of confidence values rather than a mean, since a distribution piled at one value makes any threshold either accept-all or reject-all and a mean conceals that. The distribution is published as disclosure, not as an input to choosing the floor. **The distribution MUST be denominated on every confidence the run computed, including every score the floor rejected**, with the two populations labelled and counted separately. A distribution over stored values alone is confined to the three combinations the floor admits (SC-045) and therefore conceals precisely what the floor excluded, which is the one thing the publication exists to show. A rejected score has no stored home — FR-036 forbids a confidence on a failure record, deliberately — so the rejected half is a count per computed score carried in the report from the run's own tally, not a query over the database, and the report MUST say so rather than leaving a reader to assume the figure is recomputable from rows.
  **The distribution's form is fixed: all eight scores, with their counts, including the ones nothing took.** FR-057's three binary signals admit exactly eight distinct scores, so the domain is enumerable in advance and MUST be printed in full — a score no computed value took appears as a **zero**, never as an absent row. An absent row and a zero are different claims, and only the zero says the combination did not occur; over a domain this small, omitting the empty cells is what turns a distribution into a list of what happened to happen. System MUST also print, beside the distribution and not only in a limitations table a reader of the figures may never reach, the statement that the score is a heuristic ordering rather than a calibrated probability **together with the condition that would reverse it** — a frozen, hashed labelled sample of extracted fields, against which the score could be calibrated and a threshold fitted. A caveat whose reversal trigger lives elsewhere reads as an apology rather than as a scope decision.

**Failure handling**

- **FR-034**: System MUST classify every extraction failure with one outcome from the closed set of seven the schema defines, and MUST NOT introduce a new outcome value. **The seven are enumerated here rather than referred to by count and owner**, because three of them happen to appear in US3's acceptance scenarios and four appear nowhere in this document, so a reader could not say which outcome a given failure takes without leaving it: `no_value_found`, `unparseable_value`, `type_coercion_failed`, `schema_violation`, `missing_citation`, `confidence_below_threshold`, `repair_budget_exhausted`. The list restates E003's `ck_extraction_failure__outcome` and adds nothing to it; where the two disagree that document governs and this list is the defect ({SAD:ADR-0017}). System MUST publish the failure count **broken down by each of the seven**, denominated per attempt (FR-069), with an outcome no failure took published as a zero rather than omitted — a run dominated by `no_value_found` and a run dominated by `repair_budget_exhausted` are different runs with different causes, and a single failure total conceals which one happened.
- **FR-035**: System MUST record on each failure the source chunk, the attempted page, the field, the repair attempt count, and a diagnostic detail.
- **FR-036**: System MUST NOT attach a value or a confidence to a failure record.
- **FR-037**: System MUST record a field the document does not print as not found rather than defaulting, inferring, or omitting it silently.

**Run attribution**

- **FR-038**: System MUST write one ingestion-run record per run naming the agent identity, the provider model, the chunker version, the embedding model identity and revision, the corpus manifest digests, the resolution mode, and the run's start; and MUST record the run's finish **when the run completes**. A run that aborted MUST carry no finish, and a run that recorded a run-level failure (FR-056) MUST NOT carry one at all: recording a finish for a run that stopped part-way would assert a completion that did not happen, which is what SC-044 forbids. Every field other than the finish is present on every run record, aborted or not (SC-022). **The resolution mode takes one of exactly two values, `record` and `replay`**, spelled as the traced path spells them so a reader comparing a run against its invocations does not have to translate; the set is closed here rather than only where the column is declared, since a third mode would be a third answer about where a response came from.
  **Agent identity is a composite of the invoking principal and the executing build, and its grammar is declared rather than conventional.** E003's TR-082 dropped its per-row agent column on the explicit grounds that this epic would hold agent identity at run granularity, so this field is the project's only answer to "who is responsible for this citation" — and neither half answers it alone: a build cannot be asked why a run was started, and a person cannot be asked what code executed. The value MUST therefore name both, in a form that parses rather than one a reader interprets:

  ```text
  principal=<human|automation>:<identifier>; build=<distribution>@<version>+<vcs-revision>
  ```

  — for example `principal=automation:ci-ingest; build=procurement-model@0.6.0+9f8a702` or `principal=human:d.karras; build=procurement-model@0.6.0+9f8a702`. The grammar is enforced by a format check on the column rather than by convention (`ck_ingestion_run__agent_id_format`), so a record naming only one half is refused on write rather than discovered later by whoever needed the other half. **The provider model is deliberately not a member**: it has its own column on this record, and a second copy inside a text field is a second answer that can disagree with the first while nothing checks it.

  **Three run states are readable from the record, and the fourth case is disclosed rather than claimed away.** A run in flight carries no finish and no failure kind; an aborted run carries a failure kind and no finish (FR-056); a complete run carries a finish and no failure kind. A reader therefore never has to infer completion from elapsed time. What the record cannot distinguish is a run whose process died before it could write its failure columns — that leaves no finish and no kind, and so reads as in flight forever. It is disclosed here rather than papered over with a heartbeat this epic does not have: the recovery is the same as for any abort, since per-document transactions (FR-042) leave the committed documents durable and their generations active regardless of what the run record says.
- **FR-039**: System MUST make every chunk, extracted value, and failure record resolve to exactly one ingestion run through association records this epic owns in its own migration block, since those three tables carry no run column and adding one would change a schema this epic does not own. **Attribution is specified for every row kind this epic writes, not only the three that need an association**, so that "every row resolves to a run" ranges over a stated population rather than three named tables and an unexamined remainder. The two value-level records this epic owns — the line-item association (FR-059) and the parse-signal record (FR-063) — carry the run and document **directly**, held equal to their value's own attribution rather than re-derived, so neither can name a run its value does not. Contributing-chunk rows (`extracted_value_contributing_chunk`) carry **no** attribution of their own and resolve through their parent value: E003 owns that table, it takes no new column, and a contributing row cannot outlive its value, so the parent's attribution is the row's without a second copy that could disagree. That is stated rather than left to inference, because a reader who finds attribution on four row kinds and not on the fifth has to guess whether the omission is a decision or a gap.
- **FR-040**: System MUST claim migration prefix block `0300`–`0399` for any schema object it adds, leaving `0200`–`0299` to the epic sharing its wave, and MUST NOT place an object inside another epic's block. System MUST **enumerate by name every database object its migrations create** — table, view, index, and constraint — so that "zero schema objects are placed outside the claimed block" (SC-034) ranges over a stated population rather than an open one; the enumeration is maintained in `data-model.md` §Named Object Inventory and any object absent from it is a defect whether or not its prefix is in range. System MUST also amend the build-gating migration-block partition check to declare **both** `0300`–`0399` as this epic's block and `0200`–`0299` as reserved-and-empty for the concurrent epic, so the reservation is machine-checked by a file the build runs rather than asserted by this specification alone; the check is not owned by this epic, and the amendment is recorded here as a requirement rather than left as a design note.
- **FR-065**: System MUST add **zero columns, zero constraints, and zero indexes** to any of the six E003-owned tables it populates — `document`, `chunk`, `field_vocabulary`, `extracted_value`, `extracted_value_contributing_chunk`, and `extraction_failure` — and MUST make that verifiable by comparing those tables' catalog entries before and after this epic's migrations rather than by review. Three of the six are named in E003's append-only revoke and three are not, which is exactly why the boundary is stated over all six: a table is out of bounds because E003 owns it, not because a privilege was taken away on it.

**Re-running and correction**

- **FR-041**: System MUST NOT update an extracted value, a contributing-chunk record, or a failure record in place; a correction is a remove-and-reload of the whole affected document. The removal order is stated here rather than deferred to whatever the foreign keys happen to permit: **capture the generation's chunk, value, and failure identifiers first** — the associations that answer "which rows were this generation's" are themselves removed early — then delete strictly leaf-up: (1) the line-item and parse-signal associations, (2) the three run-output associations, (3) the failure rows, the contributing-chunk rows, and the extracted values, (4) the chunks, (5) the generation record. The run record is never removed. The one edge where the restricting-foreign-key rationale does **not** hold is `extracted_value_contributing_chunk → extracted_value`, which E003 declares `ON DELETE CASCADE`: step 3 deletes the contributing rows explicitly anyway, because a step that leans on a cascade in a table this epic does not own changes meaning silently if that table changes.
  The two roles this rule turns on are named rather than described. The ingestion job connects as the **application role `procurement_app`**, whose `UPDATE` and `DELETE` are deliberately revoked on the three provenance tables; the removal MUST be executed under the **schema-owning role** — the migration role that owns the tables and retains those verbs, and which in the delivered configuration is the superuser `procurement`. The removal MUST NOT be reachable from the ingestion job, and this epic does not weaken the revoke.
- **FR-066**: System MUST carry the same append-only posture onto **every table it adds** — the generation record, the three run-output associations, the line-item association, and the parse-signal record — granting the application role `SELECT` and `INSERT` and withholding `UPDATE` and `DELETE`, because those rows are themselves provenance: an association silently repointed at another run makes run attribution true and meaningless. System MUST enumerate the updates that remain permitted anywhere in this epic's object set, so the prohibition is bounded by a list rather than by an undefined table group: on the ingestion-run record only the **finish timestamp** and the **two run-failure columns**, and nothing else; `DELETE` is withheld there too. The `active`-to-`superseded` mark is not an exception to this rule for the ingestion job — it names the generation the promotion then removes, so it moves to the schema-owning role together with the removal (FR-055).
- **FR-042**: System MUST leave no document half-ingested when a run fails part-way. System MUST also state the standing of the documents already committed when a run aborts — whether the abort came from a hash mismatch (FR-005), an identifier collision (FR-052), an over-long sentence, or a run-level invocation failure (FR-056): those documents remain durable, **their generations remain active**, and the corpus is consumable in that state, since per-document transactions make each commit independent of the ones that follow. The run record carries its failure and no finish, so a partially ingested corpus is identifiable as partial rather than being either invalidated or mistaken for a complete one.
- **FR-043**: System MUST define a document's inputs as the tuple of **that document's own** recorded content hash, the chunker version, the embedding model identity and revision, the provider model, and the extraction prompt and schema digest; MUST skip a document whose tuple is unchanged, creating no rows for it; and MUST reload only the documents whose tuple differs. The digest is per document, not corpus-wide — a corpus-wide digest would reload all 51 whenever any one changed. The provider model is in the tuple because a run under a different model would otherwise skip unchanged documents and replay fixtures recorded against the previous one. **Reloading a document that already holds a generation is the promotion FR-055 defines and the remove-and-reload FR-041 defines — one behaviour, not two**: the same removal, in the same order, inside the transaction that writes the successor. It follows that a run which replaces any existing generation is executed under the schema-owning role for its whole length, while a run in which every document is a first ingest or a skip runs unattended under the application role. First ingestion and re-ingestion are the same code path and different privilege, and that is stated rather than discovered.

**Execution environment**

- **FR-044**: System MUST run ingestion offline only, never on a request path.
- **FR-045**: System MUST complete a full ingestion run in continuous integration with no provider call and no network access, resolving every model response from committed fixtures. **The resolution key is stated rather than assumed, because a key narrower than the request is what makes a stale fixture replay silently.** A fixture resolves under the traced path's own key, whose hashed inputs include the request — provider model and prompt text among them — the output schema's digest, and the prompt template's digest; E004 owns that key and E006 inherits it rather than declaring a second one. It follows that **a changed prompt or a changed schema constraint resolves to a miss and to FR-056's named run-level failure**, never to a response recorded under the previous prompt. **The re-record trigger is therefore structural rather than remembered**: fixtures MUST be re-recorded whenever the prompt text or an output schema constraint changes, the trigger fires as a replay miss rather than requiring an observer to notice it, and the re-record is a `record`-mode run whose fixtures are committed with the change that invalidated them. The same two digests are recorded on the run (FR-038) and are input-tuple members (FR-043), so the change also re-ingests every document rather than leaving stored values scored under one prompt beside values scored under another.

**Boundary enforcement and baseline**

- **FR-046**: System MUST record in the ingestion report the signals a computed confidence is derived from and the weight each carries, so a given score is explainable and recomputable from the stored row rather than being an opaque number.
- **FR-048**: System MUST bring its model-facing modules under the enumerated computation-boundary contract, so that date, ranking, and probability arithmetic cannot be reached from them. The single-provider-import rule is enforced by a repository-wide scan and needs no extension; the computation boundary is enforced by a contract that names its modules one by one, so a new model-facing module is outside it until named.
- **FR-049**: System MUST coerce an extracted value to its numeric or date form in deterministic code rather than accepting a typed value the model produced, since a coercion the model performed is arithmetic done where it cannot be tested.
- **FR-050**: System MUST report every extraction quality figure against a deterministic baseline extractor run over the same transmittals, and MUST label that baseline as strong or weak rather than presenting an unlabelled comparison. **Two labels are published, not one, and the criterion for each is stated so the label is not the author's judgement.** The **declared** label is fixed **before any figure exists**, on the same discipline FR-032 imposes on the confidence floor and FR-061 on the similarity grid: the baseline is declared **strong** when it is authored under the independence contract below *and* is template-driven over a corpus the generator produced from a fixed set of per-vendor templates — the construction under which it could plausibly win — and **weak** otherwise. The **observed** label is read off the published table afterwards: strong where the baseline beats or ties the model on at least one per-field figure, weak where the model dominates it on every field. **Where the two disagree, the disagreement is published as a finding and MUST NOT be reconciled by revising either label.** A baseline declared strong that the model then dominates on every field is information about the baseline — that the templates were less recoverable from rendered text than expected — and silently relabelling it weak after the fact is the move Principle VIII exists to prevent; relabelling it strong after a surprise win is the same move in the other direction. **"Extraction quality figure" is a named set, not a description**, because SC-029 admits no such figure without a baseline figure beside it and a set left open would either make the criterion unsatisfiable or let a figure escape it by not being called one: the set is **the per-field precision and recall figures FR-060 publishes, per field and per layer** — exactly the figures for which a baseline counterpart exists over the same documents. Three figures a reader might reasonably expect here are **outside** it, and each is outside for a reason rather than by omission: the **repaired rate** (SC-018) counts invocations of the model path, and the baseline issues none; the **confidence distribution** (FR-033) is computed from parse signals of a model invocation, and the baseline has no invocation to score; the **near-duplicate cluster counts** (FR-061) are a property of chunks, not of extraction. None of the three has a baseline value that could be printed beside it, so requiring one would be requiring an empty cell. The synthetic layer uses a fixed set of per-vendor templates, so a template-driven extractor is a baseline that could plausibly win, which is the only kind whose defeat carries information. System MUST publish every such figure with an interval, since a bare point estimate over 25 documents claims a precision that sample does not support. **The baseline MUST be authored independently of the generator's own definitions, and the boundary is named rather than described**: it MUST read only the rendered documents' text, and MUST NOT import, read, or transcribe the generator's per-vendor layout templates, its rendering code, or the pre-render document model FR-067 fixes as the reference. A template extractor written from the templates the corpus was generated from is not a strong baseline, it is the answer key wearing a baseline's label — it would score at or near 100% by construction, and the model's defeat by it would carry no information about the model at all, which is the one thing Principle VIII asks a baseline to carry. The independence is enforced by an import contract naming the forbidden modules, not by review, so a later edit that reaches for the templates fails the build. **One shared input is deliberately permitted and is not an exception**: the committed field-label vocabulary, which FR-057 already gives the model path. It is the published set of labels a transmittal may print — a schema, not an answer — and denying it to the baseline while granting it to the model would weaken the opponent rather than keep it honest.

**Cross-epic obligations**

- **FR-047**: System MUST record, without performing it, the amendment that computing confidence requires: E003's TR-081 fixes per-field confidence as "a self-reported score asserted by the extracting agent", and a deterministically computed score is not that. The non-calibration half of TR-081 survives unchanged and is restated in FR-031; the self-reported half does not. Amendments to registered documents serialize on the default branch, so this branch records the need and does not carry it out — and implementation MUST NOT begin until the amendment lands, because writing computed scores into a column the normative document describes as agent-asserted would mislead every reader who trusts that document.
- **FR-063**: System MUST record, in a table this epic owns, the parse signals each value's confidence was computed from — whether the printed label was canonical or a known alternate, whether the value was assembled across a page break, and whether the invocation validated on the first attempt or after a repair. The value table belongs to another epic and takes no new column, and two of the three signals are recoverable from nowhere else; without them, recomputing a stored score reduces to comparing it with itself.
- **FR-064**: System MUST perform the drop and rebuild of the vector index around a full-corpus load as an operator procedure under the schema-owning role, and MUST NOT reach it from the ingestion job, which holds no privilege to alter an index another epic owns. System MUST state that similarity queries fall back to a sequential scan while the index is absent, and that a run aborting mid-load leaves it absent until the procedure is re-run.
- **FR-051**: System MUST claim decision-record numbers ADR-0018 through **ADR-0020**, since decision-record numbers are allocated by scanning for the highest in use and a concurrent epic branching from the same baseline would otherwise allocate the same number and be equally right. Two were claimed at epic start; the third was claimed during the Checklist phase when a requirements-quality pass found that ADR-0019's retention clause could not be implemented, and that allocation is recorded here rather than left implicit in the directory.

**Measured rather than assumed**

- **FR-053**: System MUST measure and record in the ingestion report the distribution of leaf-unit lengths across all 51 documents in the encoder's own tokenizer, together with the count of leaves that required a sentence-level split and the list of documents chunked at the page-terminal fallback, **each named document carrying its own count of page-terminal chunks** — the list alone says which documents lost their structure and not how much of them did, and US1 scenario 10 already requires the count, so the two statements are made to agree here rather than leaving a reader to reconcile them. The 26 real specifications are structurally uncharacterized, so this distribution MUST be measured rather than inferred from the standard's format rules.
  System MUST also publish **the chunk count in each of FR-012's three boundary classes** — structural, page break, and sentence-within-an-oversized-leaf — with a class holding no boundaries published as a zero. SC-038 asserts that every boundary falls in one of the three and would pass identically on a corpus cut entirely at page breaks, which is the outcome the structure-aware claim exists to exclude; the share each class took is what makes the assertion informative rather than merely true.
  **Every figure this requirement obliges is published per layer as well as pooled.** The leaf-length distribution, the sentence-split count, the boundary-class counts, and the page-terminal list all range over both layers, and the layers are structurally unlike — 25 templated transmittals against 26 uncharacterized specification masters — so a pooled figure over them conceals which layer produced it. The Risks entry already binds every extraction figure to a layer label; this states that the obligation is on every published figure whose population spans both, not on the extraction figures alone (FR-072).
- **FR-061**: System MUST record in the ingestion report the count of near-duplicate chunk clusters by cause — the dense reference-designation lists, agency variants of one MasterFormat number, and resubmittal chains differing only by revision suffix — counted both as exact matches on normalized text and above a declared similarity threshold, so retrieval inherits a measured figure rather than a surprise. **The measure and the thresholds MUST be fixed before the run and MUST NOT be chosen after the clusters are observed**, which is the discipline FR-032 imposes on the confidence floor and for the same reason: a threshold picked once the clusters are visible makes the published count a fitted figure rather than a measured one. The measure is **cosine similarity over the chunk embeddings this epic already computes** — no second similarity is introduced, since a second one would be a second answer about what "near" means. The threshold is not a single number chosen in advance and defended afterwards: the count MUST be published **at every threshold in the declared grid 0.80, 0.85, 0.90, 0.95, 0.99**, so what is published is a curve rather than a point and no threshold is privileged by having been selected. Publishing the curve is also what lets E008 pick the threshold its own retrieval work needs without re-running this measurement.

**Run integrity**

- **FR-054**: System MUST commit **every** row of one document in a single transaction, in a stated order that names each row the transaction contains rather than a subset of them: where the document already holds a generation, first the mark, the identifier capture, and the leaf-up removal FR-041 fixes; then **the document's generation record**, which every association points at and which therefore precedes them all; then its chunks, extracted values, contributing-chunk records, failures, the three run associations, and finally the **line-item association and the parse-signal record**, both of which reference a run association rather than the value directly and so cannot be written before it. An aborted run therefore rolls back only the document in flight — restoring its prior generation intact where it had one — and needs no deletion privilege to clean up after itself.
- **FR-055**: System MUST mark a run's work **per document** as active or superseded rather than marking the run as a whole, since a run re-ingests only the documents whose input tuple changed and a run-level mark would supersede generations it never replaced. At most one generation per document is active, and downstream readers MUST filter on it. The readers this binds are named — **E008 (retrieval), E009 (identity resolution), and E012 (source-page traceability)** — together with the outcome when one does not filter, because the obligation falls on epics outside this one and nothing here can compel it: a reader that queries the base tables directly still gets the resident generation's rows, since none other exists, but obtains **no run attribution** with them (which chunker version, which embedding revision, which run) and cannot distinguish "this document has no live generation" from "this document has one". Both failures are silent, which is why the filter is a named obligation on named epics rather than a note. **Promotion MUST remove the prior generation's rows for that document rather than retaining them**: chunk ordinals are unique within a document, not within a generation, so two retained generations for one document are unstorable. Reverting a promotion is therefore a re-run of the previous chunker version, not a status change, and no retention bound is needed because no superseded rows accumulate.
- **FR-056**: System MUST treat a missing fixture in replay, or an unreachable provider, as a named run-level failure that aborts the run and is reported distinctly from per-field extraction failure. It MUST NOT be recorded under any of the seven per-field outcomes, none of which means the invocation could not be made; recording it as one would say the model produced something unusable when nothing was ever asked. The record explaining an aborted document MUST be written **after the rollback, in a fresh transaction**, and MUST be a run-level failure on the ingestion-run record: a row written inside the document's transaction to explain why that document failed rolls back with it, and it **cannot** be a per-field failure row at all, because such a row requires a source chunk that the rollback has just removed and is therefore unstorable. That is the structural reason a run-level failure needs its own home rather than a new outcome value.
  **The run-level set is closed at five, enumerated here, and each aborting requirement is mapped to the kind its abort is recorded under** — three requirements in this specification abort a run without naming a kind, and a taxonomy whose members are discoverable only from a schema check is not closed at requirement level: `corpus_digest_mismatch` (FR-005, a manifest content hash that no longer matches the file), `document_id_collision` (FR-052, two stems yielding one identifier), `oversized_sentence` (FR-014, a single sentence above the encoder window), `fixture_missing` (FR-045, a replay miss), and `provider_unreachable`. **One abort is deliberately outside the set and the reason is stated rather than left as an omission**: FR-019's encoder-artifact integrity check runs before the ingestion-run record is written, so a digest mismatch or an absent artifact ends the process with no run record to carry a kind and no rows anywhere — it is a startup refusal, not a run that failed, and inventing a sixth kind for it would require writing a run record for a run that never began.
  **Disjointness is a property of the two sets, not a prohibition on one recording path.** The five run-level kinds and the seven per-field outcomes (FR-034) share zero values, and that MUST be checked as a set intersection over the two declared domains rather than inferred from the spellings happening to differ, so a later revision adding an overlapping value to either side fails rather than quietly making a run-level failure representable as a per-field one.
  **The diagnostic detail has a required content, because FR-035 fixes five fields for a per-field failure and a run-level one would otherwise be free text.** Every run-level failure MUST record, beside its kind, the subject its own aborting requirement already names — the document in flight and the offending file for `corpus_digest_mismatch`, **both** colliding files and the identifier they produced for `document_id_collision`, the document, page, and structural unit for `oversized_sentence`, the resolution key that missed for `fixture_missing`, and the provider and model addressed for `provider_unreachable` — and MUST name the document in flight wherever one exists, since "the run aborted" without it leaves a reader with 51 candidates and the disposition ledger (FR-073) with no way to mark one `rolled_back`.

**Extraction policy**

- **FR-057**: System MUST compute confidence as 1.0 less declared deductions — 0.15 where the printed field label matched a known alternate rather than the canonical form, 0.10 where the value was assembled across a page break, and 0.25 where the invocation validated only after a repair — resolving alternate labels against the field-label vocabulary E002 committed rather than a list invented here. The floor is **0.80**, and MUST be stated as the combinations it excludes: any repaired invocation, and any value that is both alternate-labelled and page-split. Three signals over a discrete scale admit only eight distinct scores, so the floor is meaningful only when named by what it rejects. System MUST record the three deduction weights on the run record alongside the floor, for the same reason the floor is recorded there: left as code constants they are whatever is currently checked out, so a score recomputed after a weight change silently disagrees with the row that produced it. System MUST also declare the order the deductions are applied in — alternate label, then page split, then repair, left to right — because floating-point subtraction is not associative, and without a fixed order "reproduces the stored value exactly" means "within a tolerance nobody stated".
- **FR-058**: System MUST attempt only the declared transmittal field subset per chunk rather than all twenty-two vocabulary terms, roughly ten of which cannot appear on a transmittal at all, and MUST record a field absent from an entire document once per document rather than once per chunk. **The subset MUST cover every vocabulary term the generator can print on a transmittal**, so that no printed field goes unattempted by construction and the narrowing removes only terms that cannot appear. This is stated because FR-060 denominates recall on everything the generator recorded as printed: a printed field the extractor never attempts is counted in that denominator as a miss, exactly as a field it attempted and failed on is, since a denominator narrowed by the system's own choice of what to attempt is the same defect as one narrowed by the confidence floor. Where a printed field nevertheless falls outside the declared subset, its count MUST be published in the ingestion report as unattempted-but-printed rather than absorbed into the miss total, so the choice is visible rather than paid for silently. Attempting every term everywhere would fill the failure table with structural absences and make its figures unreadable. That single record still carries the source chunk and attempted page every failure requires (FR-035), and the referent is stated rather than left to the writer: it names the **lowest-ordinal chunk the field was attempted on** and that chunk's page. The rule is deterministic under FR-015's ordinal assignment, so the same absence produces the same failure row on a re-run; it is a stated convention rather than a claim that the field would have been printed there, and the ingestion report records it as such.
- **FR-062**: System MUST keep the printed text of a value as the evidence its citation points at, and MUST hold any coerced numeric form in the column the schema provides for it. Where the schema stores a canonical form that differs from the printed text — a date normalized to ISO-8601 — the printed form remains recoverable from the cited chunk, which holds the page text verbatim. Comparisons asserting agreement with the printed document therefore apply to text-kind values.
- **FR-059**: System MUST associate every extracted value with the line item it belongs to, through an association this epic owns in its claimed migration block, keyed on the **value alone** — so a second membership is unrepresentable rather than merely wrong — and grouped by **run, document, and item ordinal**. Membership is therefore scoped to a generation, not to a document: the association's run and document are held equal to the value's own run attribution, so two generations of one document can never be read as one item three, and a promotion can find a generation's line-item rows by key rather than by scan. The value table carries no line-item key and this epic does not change it; without the association, a transmittal listing five items yields five manufacturers and five part numbers with nothing joining them, which is the association identity resolution matches on. **Item ordinal 0 is a named group meaning "printed once for the whole document"**, and real items are numbered from 1: a transmittal prints its submittal number, submittal date, approval date and the rest once for the document rather than per item, and those values belong to group 0 rather than to no group at all. That keeps SC-046 literally absolute — every extracted value belongs to exactly one line item — instead of narrowing the criterion's population to the values that happen to fit it, and it costs nothing at the E003 boundary because the ordinal is a column on an association this epic owns. Group 0 is a declared membership, not a sentinel to be pattern-matched: a reader asks which group a value is in, never whether an ordinal looks special. Per-field cardinality *within* an item — one manufacturer, one part number — is deliberately **left unasserted**: it is not universally true (an item may legitimately cite two compliance standards), and holding it would require a field key on a value table this epic may not alter. It is disclosed as uncovered and left to the epic that owns identity, rather than half-enforced here.

**Measurement**

- **FR-067**: System MUST score every extraction accuracy figure against the corpus generator's **pre-render document model** as the reference set — the per-document record of the fields and the page text the generator composed before rendering — and MUST verify that reference is the committed one before any figure is computed, by reproducing it from the committed seed and generation inputs and requiring it to equal the document-model digest each synthetic manifest entry already carries. The reference is therefore fixed by a requirement rather than named only inside SC-013 and SC-027, and no new evaluation artifact is created: it already exists, frozen and hash-verifiable. System MUST NOT score a stored value against the chunk text it was read out of, against the page text this epic's own parse produced, or against any other artifact of the run being measured. Such a comparison agrees whenever the parse is self-consistent and is silent on whether the parse is right — it is the derived-oracle-against-itself defect, and it is the one the citation-to-page mechanism is most exposed to, because the chunk text and the stored value come from the same read. The real layer has no such reference, which is one of the two reasons FR-060 publishes it as not measured rather than as a figure.
- **FR-068**: System MUST publish, with every total check it claims, the population that check enumerated and the count of items in it, and MUST fail rather than report success when that count is zero. A containment check over zero chunks and a text-agreement check over zero text-kind values both return "no failures", which is indistinguishable from a check that ran and passed; a total claim whose population is not printed is therefore not yet a claim. This binds every criterion in this specification phrased as "100%" or "zero" over an enumerated population — page containment (SC-002), text agreement (SC-013, SC-027), citation agreement (SC-009), ordinal contiguity (SC-003), line-item membership (SC-046), and the rest — and it is the rule that makes the difference between a corpus that was checked and a query that found nothing to check.
- **FR-069**: System MUST record the number of field extractions it attempted and MUST resolve every attempt to exactly one of a stored extracted value or an extraction failure record, with zero attempts unaccounted for. **The counting units MUST be named beside every published figure**, because this epic counts in three of them and a figure whose unit is inferred will be compared against one carrying a different unit. An **attempt** is one field on one chunk (FR-058), except a field absent from a whole document, which is one attempt per document (FR-058). An **invocation** is one model request covering one chunk's declared field subset, and is the unit FR-025's validity and FR-026's repair budget are counted in. A **document** is the unit of the whole-document absence record and of the transaction (FR-054). The valid, repaired, and failed counts of SC-018 are published **per invocation**; per-field outcomes and any failure rate are published **per attempt**; and the two are published as two tables with their units named rather than as one table whose rows do not share a denominator.
- **FR-070**: System MUST issue every extraction invocation of a run under a single run-scoped trace identifier, MUST record that identifier on the ingestion-run record, and MUST reconcile in the ingestion report the number of invocations the run attempted (FR-069) against the number recorded on the traced path under that identifier, publishing both counts and requiring them equal. The static import contract (FR-023, FR-048) establishes that no other module *can* reach the provider; it produces no count of the requests that were actually made, so it cannot on its own carry SC-011 — a run that reached the provider through the traced path and failed to record an invocation would satisfy every import contract and still leave a billed call untraced, which is the exact failure the tracing claim exists to exclude.
- **FR-060**: System MUST publish per-field precision and recall with Wilson 95% intervals, per field and per layer, beside the deterministic baseline's figures on the same documents. **The variant is fixed as the continuity-corrected Wilson score interval, and it MUST be named with the figures rather than left to a reader's default.** Research records that the uncorrected interval under-covers at extreme proportions for very small denominators; per-field denominators here are frequently under 20 with precision expected near 1, which is exactly the regime named, so the correction is applied rather than the caveat published. The direction of the remaining error is the point: the corrected interval errs toward over-coverage, and for a project whose second principle is that uncertainty is the product, a slightly-too-wide interval is the honest failure and a too-narrow one is the dishonest one. The same variant is used everywhere an interval on a proportion is published in this epic, including FR-011's defect bound, so two figures in one report are never computed by two methods. System MUST NOT publish F1. Wilson inverts the score test for a **binomial proportion**; F1 is a harmonic mean of two proportions with different denominators and is not one, so no Wilson interval for it exists to publish, and SC-029 admits no figure without an interval. Precision and recall fully determine F1, so a reader who wants it can compute it — what is lost is a convenience number, and what is avoided is either a bare point estimate or a second interval method introduced on denominators already too thin for the first. The omission MUST be published with this reason, so it reads as a decision rather than an oversight. Recall MUST be denominated on the full set of fields the generator recorded as printed, not on the values that were stored — a denominator of stored values would make a stricter confidence floor register as better quality by discarding the hard cases. **Both denominators MUST be stated and printed beside their figures, not left to be inferred from the one that is fixed.** Precision is denominated on **the values the run stored for that field and layer** — the population a reader of the database actually meets — and its numerator is those that match the reference FR-067 fixes. Recall is denominated on the generator's printed-field set, as above. The two are different populations, which is why each figure carries its own denominator rather than the report carrying one; it is also the reason no third figure derived from both is published, since a single number inheriting two denominators invites a reader to assume one. **"Per layer" MUST NOT be published as a figure over an empty denominator.** The real layer yields zero extracted values by design (SC-012) and has no generator record to denominate recall on at all, so both its denominators are undefined rather than zero: it MUST be published as **not measured, with the reason** — no extraction attempted and no reference exists — and MUST NOT be published as `0/0`, as `0%`, or as a blank cell, each of which reads as a measured result. The partition therefore has exactly one measured layer, and saying so is the disclosure; leaving the row empty is not.
  **Each interval MUST be labelled descriptive rather than inferential, and the label is not a hedge.** An interval on a proportion presupposes a random sample from a population; the 25 transmittals are a deliberately seeded set carrying designed irregularities, and no population was sampled to produce them. The interval therefore states the variability the observed denominator supports and MUST NOT be read as a confidence statement about extraction on documents outside this corpus. The interval is still published — SC-029 admits no figure without one, and a bare point estimate over these denominators would claim a precision they cannot support — but publishing it unlabelled would let a reader carry a number off this corpus that was never measured on anything else.

**The ingestion report as a published artifact**

- **FR-071**: System MUST publish the ingestion report as **one committed artifact at `specs/00006-document-ingestion-and-extraction/ingestion-report.md`** — one per repository rather than one per run — regenerated in full by any run that writes or replaces a generation. Scope §Included commits only to "an ingestion report committed with this epic" and the path existed only in the plan, so identity, location, form, and cardinality are fixed at requirement level here: a reader has to be able to tell whether a figure is missing or merely somewhere else, and neither question is answerable against an artifact whose existence is asserted and whose address is not.

  **The report's required content is a closed list.** More than twenty requirements and criteria each oblige this one artifact to carry something, scattered across every section of this document, and a report assembled by walking that scatter is a report whose completeness nobody can check — least of all the person writing it. Each item below names what obliges it; an item published in the report but absent from this list is a defect in this list, and a list entry with nothing under it in the report is a defect in the report:

  **The run's account is closed at two artifacts and no third.** Everything the repository retains about what a run did is the ingestion-run record with its associations, plus this report. No published figure may rest on console output, a log line, or any artifact the repository does not commit; where a figure is not recomputable by query — FR-033's rejected-score tally, FR-069's attempt ledger, FR-073's dispositions — it is carried in the report from the run's own ledger and is labelled as such (FR-072), so a reader knows which figures survive the report being deleted and which do not.

  **Regeneration replaces.** A regenerated report replaces the prior one wholesale rather than being appended to, and is never left standing beside figures it no longer describes. The superseded text stays recoverable from version control, which is why replacement loses nothing that matters; accretion would leave one artifact carrying two accounts of one corpus with no rule for which governs, which is the same defect {SAD:ADR-0020} removed from the generations themselves.

- **FR-072**: System MUST label every figure the ingestion report publishes with **the run it was computed under, the generation set it ranges over, and its kind**, and MUST name in the report, by identifier, the ingestion-run record the report describes. Three labels, because three different misreadings are otherwise available and none of them is visible:
  - **Run and generation set.** FR-043 lets a run ingest 3 of 51 documents while the other 48 documents' resident rows belong to earlier runs, so "the run's figures" is false of every corpus-wide figure in a report a partial re-run produced. Each figure therefore declares itself either **corpus-resident** — computed by query over the generations resident when the report was written, naming the set of runs those generations belong to — or **run-scoped**, computed over the work of the one run named and not recomputable from rows. A corpus-resident figure attributed to a single run would credit that run with 48 documents it never opened.
  - **Kind.** Every figure is published as a **census** — a total check over an enumerated population, carrying its population and count (FR-068) and **no** interval, there being nothing to infer — or as a **sampled estimate**, one of FR-011's enumerated claims with its inspected count, defect count, and bound, or as a **descriptive figure over a designed set**, which is what the per-field extraction figures are (FR-060). A total check published with an interval and an estimate published without one are the two errors this label exists to make visible, and Principle II is satisfied by neither a bare estimate nor a census dressed as one.
  - **Unit and layer.** Every figure names its counting unit — attempt, invocation, or document (FR-069) — and every figure whose population spans both corpus layers is published per layer as well as pooled (FR-053, SC-005, FR-061). The extraction figures are already per layer under FR-060.

- **FR-073**: System MUST publish, for every run, a **per-document disposition** drawn from a closed set of four together with the count of documents in each: **`ingested`** — a generation was written for it; **`skipped_unchanged`** — its input tuple was unchanged, so FR-043 created no rows for it; **`rolled_back`** — it was the document in flight when the run aborted and its transaction was discarded; and **`not_reached`** — it was enumerated but never begun, because the run had already aborted. The four MUST partition the enumerated corpus, their counts MUST sum to the enumerated document count FR-068 publishes, and a disposition holding zero documents MUST be published as a zero rather than omitted.
  **A partially completed run has to report what it did not attempt as distinct from what failed.** FR-042 guarantees only that no document is left half-ingested, which says nothing at all about the documents *after* the one that aborted: ingested-plus-rolled-back cannot separate "skipped by rule" from "never reached", and a reader who cannot separate them cannot tell a healthy re-run that legitimately did almost nothing from a run that died on document four. The `skipped_unchanged` count is published for the same reason and is not recoverable from SC-025, which measures that zero rows were added rather than how many documents produced none — under FR-043 skipping is the *expected* outcome of a re-run, and an expected outcome that is never counted is indistinguishable from a silent one. A run that completes carries zero `rolled_back` and zero `not_reached`; a run that recorded a run-level failure (FR-056) carries at most one `rolled_back`, since the abort ends the run, and the document it names is the one that failure's detail names.

- **FR-074**: System MUST make every figure the ingestion report publishes reproducible by a replay-mode run from a clean checkout (FR-045) against a committed results manifest, **within a tolerance printed with the figure** — the reproduction gate {SAD:ADR-0009} fixes and that the project's CI requirements make a condition of a release tag. The tolerance is stated rather than assumed to be zero, and it is stated per class because the classes genuinely differ. Every **count, every rate derived from counts, every interval computed from them, and every stored confidence** reproduces **exactly**, as bit equality rather than agreement within an unstated band: chunk boundaries are deterministic given the input tuple (FR-017, SC-007), confidences are computed left to right from weights recorded on the run (FR-057, SC-026), and replay resolves every model response from a committed fixture under a key that admits no near miss (FR-045), so there is no source of variance left to budget for. The one class **not** claimed exact is the near-duplicate cluster counts (FR-061), whose inputs are floating-point vectors from the exported encoder: they reproduce within the encoder parity tolerance FR-019 declares — cosine similarity ≥ 0.999999 and maximum absolute per-dimension difference ≤ 1e-5, declared before the comparison and measured over the committed probe set — and that tolerance MUST be printed with the counts, beside the maxima actually observed, rather than left in an architecture decision record. A reproduction landing outside the stated band is a failure of the gate and is published as one; widening the band to admit the observed difference is adjusting a target to match a result, which Principle VII forbids.

### Key Entities *(include for product or technical specs if feature involves data)*

- **Document**: One corpus PDF as a record — its identifier, type, project, title, layer, license basis, and layer-appropriate provenance. Real specifications attach to the shared-library project; synthetic transmittals attach to their own. The table exists; E006 populates it.
- **Chunk**: A contiguous run of text from exactly one page of one document, cut on the document's structure, carrying its document, type, project, page, ordinal, specification section, heading, and its embedding with the model identity and revision that produced it. The unit every citation resolves through.
- **ExtractedValue**: One field read out of one chunk — its field name, value, kind, confidence, and the page citation inherited from its source chunk. Marked single-chunk or multi-chunk according to how many chunks it drew on.
- **ContributingChunk**: For a value assembled across a page break, the additional chunks beyond the anchor that it drew on, each with its page. The representation that keeps a split field's provenance whole.
- **ExtractionFailure**: A field that could not be extracted — its source chunk, attempted page, field name, one outcome from the closed set, the repair attempts spent, and a diagnostic detail. Carries no value and no confidence, by construction.
- **IngestionRun**: One execution of the pipeline — agent identity, provider model, chunker version, embedding model identity and revision, corpus manifest digests, resolution mode, the trace identifier its invocations were issued under (FR-070), and start and finish. The record E006 owes because the schema deliberately left per-row agent identity out. New; every other entity here already has a table.
- **RunOutput**: The association between an ingestion run and each chunk, extracted value, and failure it wrote. New, and owned by this epic rather than added as a column, because the three tables it links belong to a schema this epic does not own.
- **ParseSignal**: The three signals one value's confidence was computed from — whether the printed label was canonical or a known alternate, how many chunks the value was assembled from, and whether the invocation validated only after a repair. New, and owned by this epic (FR-063), because two of the three exist in no column anywhere and the value table takes no new one; without it, recomputing a stored score compares it with itself.
- **BaselineExtraction**: What a deterministic template-driven extractor produced from the same transmittals, held so that every model figure can be reported against it rather than on its own. Authored from the rendered documents alone and barred from the generator's own template definitions and pre-render model (FR-050), since an extractor reading the templates the corpus was generated from is the answer key rather than an opponent.
- **LineItem**: One proposed material or equipment entry on a transmittal, and the association binding the values read out of it — manufacturer, part number, quantity and the rest — into a single item. New, and owned by this epic, because the value table carries no line-item key and this epic does not change it. Survives an item entry being split across two chunks, which is what makes it worth a record rather than a convention.

## Assumptions & Risks *(mandatory)*

### Assumptions

- Real specifications carry `PRJ-000` as a shared-library project identifier; the value fits the project-identifier format the schema already enforces and needs no schema change, but downstream project-scoped readers must union it.
- A synthetic document's required fixture hashes are the digests of the four generation inputs its manifest entry already records; nothing declares this mapping, so E006 fixes it here.
- The 26 real specifications are uncharacterized structurally — the corpus datasheet governs only the synthetic layer — so section, part, and article detection must be validated against the real documents rather than assumed from the standard's format rules.
- The single traced model path fixes the repair budget at one attempt, so a recorded repair count is always zero or one even though the schema leaves it unbounded; and extraction prompts and output schemas are stable enough to make committed fixtures worth keeping, since any change to prompt text or to a schema constraint invalidates every existing fixture and forces a re-record.
- Computing confidence rather than having the model report it changes what E003's TR-081 says the stored number is; the column, its type, and its range are untouched, so this is a change to a requirement's meaning and not to a schema object. It is recorded as an amendment request under FR-047 rather than performed on this branch, and implementation waits on it.

### Risks

- **Parser page attribution is correctness-critical** *(likelihood: medium, impact: high)*: deterministic provenance is only as good as the page mapping beneath it, and a wrong page number is the most damaging failure the product has. Mitigation: verify containment for every chunk rather than a sample, reusing the tolerances and normalization form already pinned in the repository.
- **Computed confidence is unvalidated** *(likelihood: high, impact: medium)*: the score is reproducible and explainable, but nothing in this epic checks it against ground truth, so a floor set against it may reject values that were correct and admit values that were not. Mitigation: declare the floor before the run rather than fitting it to the result, record the signals and their weights so any score is recomputable, and state that it is a heuristic ordering rather than a probability.
- **Extraction accuracy is measured only on generated documents** *(likelihood: high, impact: medium)*: line items come from the synthetic layer alone, and the corpus datasheet already records that its text layer carries zero recognition error. Mitigation: label every extraction figure by layer and publish the upper-bound caveat with it rather than after being asked.

### Disclosed Limitations

Each limitation below is recorded with its scope decision, the evidence behind it, the condition that would reverse it, and what a production-scale system would do instead. A limitation stated without the last two is a shortfall dressed as a decision.

| Limitation | Scope decision & evidence | Reversal trigger | Production-scale alternative |

## Glossary *(include when spec introduces 2+ domain-specific terms)*

| Term | Definition |
|------|------------|
| Chunk | A contiguous run of text from exactly one page of one document, cut on the document's own structure, and the unit through which every page citation resolves. |
| Line item | A single proposed material or equipment entry read out of a submittal transmittal — manufacturer, part number, quantity and related fields — numbered from 1 in printed order. Ordinal **0** is the one group that is not an entry: it names the values a transmittal prints once for the whole document, so every extracted value has a group (FR-059). Distinct from a purchase order line, which is a procurement record and the unit the forecast operates on. |
| Specification section | A MasterFormat-numbered division of a construction specification, identifying what a document governs; recorded on chunks and cited by transmittals. |
| Citation anchor | The page number and document identifier that together make a page citable — the project's fixed form for a citation. |
| Reference set | The corpus generator's **pre-render document model** — the fields and page text it composed before rendering — reproduced from the committed generation inputs and pinned by the digest the manifest records. The expected side of every accuracy comparison (FR-067). It is not the parsed page text and not the chunk a value was read out of: comparing a stored value against the text it came from agrees whenever the parse is self-consistent and says nothing about whether the parse was right. |
| Attempt | One field on one chunk, the unit per-field outcomes and failure rates are counted in — except a field absent from a whole document, which is one attempt for that document (FR-058, FR-069). Distinct from an **invocation**, which is one model request covering a chunk's declared field subset and is the unit validity and the repair budget are counted in. Three units exist in this epic and a figure that does not name its own is not comparable with one that does. |
| Confidence floor | The value below which an extracted value is recorded as a failure rather than stored. Declared before the first run and not moved to fit the distribution that run produces — a policy number, not a calibrated or fitted threshold. |
| Ingestion run | One execution of the parse, chunk, embed, and extract pipeline, recorded so that every row it wrote is attributable to the agent, models, and corpus state that produced it. |
| Shared-library project | The reserved project identifier `PRJ-000` under which real specifications are recorded, since a public specification belongs to no single project but the schema requires one. |
| Word piece | The sub-word unit the embedding encoder counts; its 256-unit window is a hard cap on chunk length and is not equivalent to a word or character budget. |
| Page-split field | A field whose label ends one page and whose value begins the next — a seeded corpus irregularity, and the reason a value may draw on more than one chunk. Its citation anchors on the page carrying the **printed value**, not the label (FR-029), so its anchor is the later of the two pages and any reassembly of its text is ordered by page rather than by contributor position (SC-027). |
| Structure-aware chunking | Cutting a document at boundaries the document itself declares — section, part, article, paragraph — rather than at a fixed size. |
| Boundary class | One of the three kinds of cut a chunk boundary may be: a structural boundary the parser identified, a page break, or a sentence boundary inside a leaf too long to embed. None of them is a fixed offset, and a fragment cut at a page or sentence boundary keeps the structural identifier of the unit it came from. |
| Input tuple | What a **document's** inputs are defined to be for the purpose of deciding whether to re-ingest it: **that document's own recorded content hash**, the chunker version, the embedding model identity and revision, the provider model, and the extraction prompt and schema digest (FR-043). The corpus-wide manifest digests are recorded on the run for attribution and are deliberately *not* the tuple's first member — a corpus-wide digest would reload all 51 documents whenever any one changed. A change to any element makes that document's existing rows a superseded generation, which promotion removes as it writes the successor. |

## Clarifications

### Session 2026-07-27

- Q: `document.project_id` is required on every document, including real specifications belonging to no single project. How should they attach? → A: A reserved shared-library project `PRJ-000`. One document record per specification, chunked and embedded once. Accepted cost: project-scoped readers must union `PRJ-000` with their own project, which makes the sentinel a contract downstream epics have to know about.
- Q: What happens when a field's extraction confidence is low? → A: Two bands. Below a published floor the value is not persisted and a failure is recorded; at or above it the value is persisted with its confidence carried through for display. Uses both the confidence column and the below-threshold failure outcome as designed, and avoids collapsing a graded signal into a binary one.
- Q: Which corpus layers get line-item extraction, as opposed to only being chunked and embedded? → A: The synthetic submittal transmittals only. All 51 documents are still parsed, chunked, and embedded. Real UFGS specifications are requirement prose containing unresolved bracketed alternatives, so asking a model for "the" value would fabricate a requirement the document does not state. Accepted cost: extraction accuracy is measured on generated material only, and must be published with that caveat.
- Q: Where does the ingestion-run agent identity live, given the schema deliberately omits a per-row agent column? → A: A new ingestion-run table, claiming migration prefix block `0300`–`0399` and leaving `0200`–`0299` for the epic sharing this wave.
- Q: Should per-field confidence be the model's own self-reported number, or computed from parse signals? → A: Computed deterministically from parse signals — label matched canonical or alternate, value printed or absent, single-chunk or page-split, validated first try or after a repair. Reproducible, explainable, and on the code side of "the model extracts, code computes"; the research finds self-reported confidence collapses toward all-positive at practical thresholds, which would make the chosen floor reject nothing. Consequence recorded rather than absorbed: E003's TR-081 fixes confidence as agent-asserted, so this needs an amendment, raised in FR-047 and not performed on this branch.
### Session 2026-07-27 (Clarify)

- Q: 476 of 9,020 leaf units in the real layer exceed the encoder window and 175 pages carry no structural marker at all, so no legal chunking existed. How should boundaries be made legal? → A: Three named boundary classes — structural, page break, and sentence within an oversized leaf — with each fragment keeping the structural identifier of the unit it came from, so a boundary is still never a fixed offset. The ladder descends article → paragraph → subparagraph → sentence; where no structural level is detectable the page is the terminal unit, named in the report with its count. The run fails only when a single sentence exceeds the window. The leaf-length distribution is measured and published rather than inferred (FR-012, FR-014, FR-053).
- Q: SC-024 forbade the removal FR-041 defines as the only correction path, and an aborted run could not clean up after itself under append-only privilege. → A: All rows for one document commit in a single transaction in a stated order, so an abort rolls back only the document in flight and no deletion privilege is needed. Deletion happens solely through the documented whole-document remove-and-reload executed under the schema-owning role, never from the ingestion job (FR-041, FR-054, SC-024, SC-042).
- Q: Does a chunker version change count as "changed inputs"? → A: A run's inputs are the tuple of corpus manifest digests, chunker version, embedding model identity and revision, and extraction prompt and schema digest. Runs carry active or superseded state, at most one is active per document, readers filter on active, and superseded runs have a stated retention bound and purge procedure (FR-043, FR-055, SC-025, SC-043).
- Q: A missing fixture in replay has no home in the closed set of seven per-field outcomes. → A: It is a named run-level failure that aborts the run, reported distinctly from per-field extraction failure. Recording it under a per-field outcome would say the model produced something unusable when nothing was ever asked (FR-056, SC-044).
- Q: A "line item" is this epic's output, but the value table has no line-item key — five items yield five manufacturers and five part numbers with nothing joining them. → A: An association this epic owns in its claimed migration block, keyed by value, document, and item ordinal. Chosen over treating the source chunk as the key because an over-long item entry split across two chunks would silently become two line items (FR-059, SC-046).
- Q: What are the confidence weights and the floor? → A: 1.0 less declared deductions — alternate label 0.15, page-split assembly 0.10, repaired invocation 0.25 — resolved against E002's committed field-label vocabulary. Floor **0.80**, stated as the combinations it excludes: any repaired invocation, and any value both alternate-labelled and page-split. The floor was raised from the 0.70 originally proposed because 0.70 admits both combinations it claimed to exclude, each scoring exactly 0.75. The "value printed or absent" signal was dropped: an absent value is a failure record, not a stored value with a confidence, so it can never fire (FR-057, SC-045).
- Q: Which fields are attempted, given roughly ten of the twenty-two vocabulary terms cannot appear on a transmittal? → A: Only the declared transmittal field subset, attempted per chunk, with a field absent from a whole document recorded once per document rather than once per chunk (FR-058).
- Q: FR-050 requires an interval and a baseline but names no figures and no denominator. → A: Per-field precision and recall with Wilson 95% intervals, per field and per layer, beside the baseline. Recall is denominated on the generator's full printed-field set, not on stored values — a stored-value denominator would make a stricter confidence floor register as better quality (FR-060, SC-047).
- Q: A Wilson interval is not defined for F1, which is a harmonic mean of two proportions with different denominators rather than a proportion — but SC-029 admits no figure without an interval. → A: Publish precision and recall only, and publish the omission with its reason. They fully determine F1, so a reader who wants it can compute it. Rejected: a bootstrap interval for F1 alone, which puts two interval methods in one report on denominators already thin for the first; and exempting F1 from the interval rule, which is softening a target to match a result and would carve the exemption out of the one criterion whose purpose is preventing bare point estimates.

- **STF-001**: Constraint Impossibility (CRITICAL) — Affected: FR-012, FR-013, FR-014, SC-004, SC-031, SC-038, US1 — No legal chunking existed for a structural unit crossing a page break, and a too-long leaf aborted the run in a corpus the spec admits is structurally uncharacterized. - **STF-003**: Concurrent-Trigger Ambiguity (HIGH) — Affected: FR-017, FR-039, FR-041, FR-043, SC-005, SC-007, SC-021, SC-025, US5, US6 — A re-run at a new chunker version had to both produce different boundaries and write zero rows, nothing marked a run superseded, and the corpus would grow by a full chunk set per revision with no bound. **Resolved**: input tuple defined, active/superseded run state, one active run per document, readers filter on active, retention bound and purge procedure stated.
- **STF-004**: Constraint Impossibility (HIGH) — Affected: FR-027, FR-049, SC-013, SC-020, SC-027, SC-040, US4 — A criterion quantified at zero over a population where an exception is guaranteed: a date printed `3/14/26` is stored canonically as ISO-8601, and a page-split value matches the pre-render text of neither page alone. **Resolved** without a question, since the schema already provides both a text and a numeric column: comparisons against printed text are scoped to text-kind values, the printed form stays recoverable from the cited chunk, and a page-split value is compared against the concatenation of its contributing chunks in contributor order — **amended during the Checklist phase to ascending page order**, once FR-029 fixed the citation anchor on the chunk carrying the printed value: the anchor is then the later of the two pages, so contributor order would have reversed the value's own text (SC-027).
